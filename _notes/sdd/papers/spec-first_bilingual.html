Abstract

摘要

LLM-based agents excel at software engineering tasks where an existing codebase provides context, but constructing a program from scratch remains fundamentally harder. Recent benchmarks such as ProgramBench quantify this gap: given only natural-language documentation and an execute-only binary as a behavioral oracle, even frontier models solve fewer than 1% of instances. Existing frameworks conflate documentation reading, behavioral exploration, and code synthesis into a single pass, causing agents to probe insufficiently, lose behavioral intent as context drifts, and propagate early misinterpretations into the final implementation. Inspired by classical requirements engineering, we argue that behavioral specification elicitation should be a first-class phase that precedes implementation. We present SpecFirst, a two-stage framework that forces the specification elicitation before code synthesis. A dedicated spec agent first probes the binary and combines observations with documentation into a structured specification. Next, a code synthesis agent then uses this specification to drive implementation. This decomposition resolves documentation ambiguities before coding begins and provides a stable behavioral reference throughout synthesis. We evaluate SpecFirst on all 200 ProgramBench instances across four models spanning two families and an order of magnitude of capability. SpecFirst consistently outperforms the single-loop baseline, improving test pass rates by 6.9%–21.3% and binary exploration coverage by 9.4%–18.5%, all statistically significant. Behavioral analysis on code synthesis further shows that a prior specification enables earlier and more sustained code construction. Our results demonstrate that an explicit requirements-engineering phase is an effective paradigm for from-scratch program construction.

基于大语言模型（LLM）的智能体（agent）在有既有代码库提供上下文的软件工程任务上表现出色，但从零开始构建一个程序仍然要困难得多。ProgramBench 等新近基准量化了这一差距：仅给定自然语言文档和一个只能执行的二进制程序作为行为预言机（oracle），即便是前沿模型也只能解决不到 1% 的实例。现有框架把文档阅读、行为探索与代码合成揉进同一遍流程，导致智能体探测不足、行为意图随上下文漂移而丢失，并把早期的误解一路传播到最终实现中。受经典需求工程启发，我们主张：行为规约获取应当成为先于实现的一等阶段。我们提出 SpecFirst——一个强制在代码合成之前完成规约获取的两阶段框架。专职的规约智能体首先探测二进制程序，并把观测结果与文档合并为一份结构化规约；随后，代码合成智能体使用这份规约来驱动实现。这一分解在编码开始前就消解了文档中的歧义，并在整个合成过程中提供了稳定的行为参照。我们在全部 200 个 ProgramBench 实例上、跨两个模型族、能力相差一个数量级的四个模型上评估 SpecFirst。SpecFirst 一致优于单循环基线，测试通过率提升 6.9%–21.3%，二进制探索覆盖率提升 9.4%–18.5%，且全部具有统计显著性。针对代码合成的行为分析进一步表明，事先具备规约能让代码构建启动得更早、持续得更久。我们的结果表明，显式的需求工程阶段是从零构建程序的一种有效范式。

I. Introduction

I. 引言

LLM-based agents have demonstrated strong performance on software engineering tasks such as bug fixing [1], feature implementation [2], and code completion [3], [4]. Those tasks share a common structure: an existing codebase anchors the agent's work. Building a program entirely from scratch is fundamentally harder: the agent must decide everything (e.g., architecture and programming language) and reconstruct the full behavioral envelope of a target program from limited information alone. ProgramBench [5] makes this concrete: given only natural-language documentation and an execute-only binary as a behavioral oracle, an agent must produce a faithful re-implementation from scratch. Even the strongest frontier models (e.g., GPT-5.5) can only fully resolve fewer than 1% of instances, confirming that from-scratch program construction remains an open challenge.

基于 LLM 的智能体已在缺陷修复 [1]、特性实现 [2] 和代码补全 [3]、[4] 等软件工程任务上展现出强劲性能。这些任务有一个共同结构：既有代码库为智能体的工作提供了锚点。而完全从零构建一个程序则要困难得多：智能体必须决定一切（例如架构与编程语言），并且只能依据有限信息重建目标程序的完整行为包络。ProgramBench [5] 把这一点具体化了：仅给定自然语言文档和一个只能执行的二进制程序作为行为预言机，智能体必须从零产出一份忠实的重实现。即便是最强的前沿模型（如 GPT-5.5）也只能完全解决不到 1% 的实例，这印证了从零构建程序仍是一个开放挑战。

Existing agent frameworks such as SWE-agent [2] and OpenHands [6] approach this task by providing the agent with natural-language documentation as the primary specification and an execute-only binary as a behavioral oracle [5]. While this setup permits behavioral discovery through probing, these frameworks mix specification elicitation and code synthesis into a single undifferentiated loop — the agent switches freely between planning, reading documentation, probing the binary, and writing code within the same turn budget, with no mechanism forcing comprehensive elicitation before implementation begins. This entanglement leads to three systematic limitations.

SWE-agent [2] 和 OpenHands [6] 等既有智能体框架处理该任务的方式，是把自然语言文档作为主要规约、把只能执行的二进制程序作为行为预言机交给智能体 [5]。虽然这种设定允许通过探测来发现行为，但这些框架把规约获取与代码合成混合进了同一个未加区分的循环——智能体在同一轮次预算内自由地在规划、读文档、探测二进制程序和写代码之间来回切换，没有任何机制强制它在实现开始前完成充分的获取。这种纠缠会导致三类系统性局限。

❶ Ineffective exploratory probing. Without a dedicated phase for behavioral discovery, the agent rarely probes the binary thoroughly enough to construct a complete behavioral model before committing to implementation. Edge cases, error paths, and flag interactions that are absent from the documentation but present in the binary are frequently missed, because the agent shifts to coding before its exploration is complete.

❶ 无效的探索性探测。 缺少专门的行为发现阶段，智能体很少会在投入实现之前把二进制程序探测得足够彻底，以构建出完整的行为模型。文档中没有、但二进制程序中确实存在的边界情况、错误路径和标志位交互经常被遗漏，因为智能体在探索完成之前就转向了编码。

❷ Specification loss over long horizon. Without explicit upfront elicitation, behavioral intent must be maintained implicitly across turns and is susceptible to drift as context grows [7], [8]. Compression mechanisms such as reasoning token stripping (i.e., removing the reasoning content between agent turns) and context summarization exacerbate this by selectively discarding tokens that encode the original specification [9], [10], so later-turn outputs increasingly reflect a degraded approximation of the target behavior.

❷ 长程下的规约丢失。 缺少显式的前置获取，行为意图必须跨轮次隐式维持，并且会随上下文增长而漂移 [7]、[8]。推理 token 剥离（即在智能体轮次之间移除推理内容）和上下文摘要等压缩机制会选择性地丢弃编码了原始规约的 token [9]、[10]，从而加剧这一问题，使后期轮次的输出越来越体现为目标行为的一种退化近似。

❸ Error Propagation without anchoring. Without an elicited specification as a stable reference, errors introduced early in the run accumulate and propagate across subsequent turns without correction. When the agent misinterprets the documentation or makes an incorrect behavioral assumption, it continues building on that assumption turn after turn — each dependent decision compounding the original error with no artifact to anchor against.

❸ 缺乏锚定的错误传播。 没有一份获取到的规约作为稳定参照，运行早期引入的错误会不断累积并跨轮次传播而得不到纠正。当智能体误读文档或做出错误的行为假设时，它会一轮接一轮地在该假设之上继续构建——每个依赖决策都在放大最初的错误，而没有任何制品可供锚定。

In traditional software engineering, these limitations are addressed by treating specification elicitation as a first-class phase that precedes implementation [11], [12]: requirements engineers exercise prototypes and construct scenarios to surface behavioral detail that written artifacts never capture, before a single line of code is written [13], [14]. We argue the same decomposition should apply to agentic program construction. Spec-driven frameworks such as OpenSpec [15] and spec-kit [16] adopt a similar philosophy, but rely solely on prompting human stakeholders for specification input, and do not support automated behavioral elicitation through binary probing.

在传统软件工程中，这些局限的解法是把规约获取当作先于实现的一等阶段 [11]、[12]：需求工程师会试用原型、构造场景，在写下第一行代码之前就把书面制品永远无法覆盖的行为细节挖掘出来 [13]、[14]。我们主张，同样的分解也应当应用于智能体式的程序构建。OpenSpec [15] 和 spec-kit [16] 等规约驱动框架采纳了类似理念，但它们仅依赖向人类干系人提问来获得规约输入，并不支持通过二进制探测进行自动化的行为获取。

We present SpecFirst, a two-stage pipeline that explicitly separates behavioral specification elicitation from code synthesis. In the first stage, a dedicated spec agent receives the documentation and execute-only binary and focuses exclusively on understanding the target program's behavior through systematic black-box probing, producing a structured behavioral specification artifact (i.e., SPEC.md). In the second stage, an existing code synthesis agent receives the documentation, the binary, and SPEC.md, and focuses exclusively on implementation, now equipped with a behavioral model that goes beyond what the documentation alone provides. This decomposition directly addresses each limitation above: the spec agent explores freely without competing with coding, documentation ambiguities are resolved through probing before implementation begins, and the behavioral gap between documentation and binary is explicitly addressed rather than left to chance.

我们提出 SpecFirst——一条显式地把行为规约获取与代码合成分离开来的两阶段流水线。第一阶段，专职的规约智能体接收文档与只能执行的二进制程序，并且只专注于通过系统化黑盒探测来理解目标程序的行为，产出一份结构化的行为规约制品（即 SPEC.md）。第二阶段，一个既有的代码合成智能体接收文档、二进制程序和 SPEC.md，只专注于实现，此时它已经具备了超出文档本身所能提供的行为模型。这一分解直接针对上述每一项局限：规约智能体可以自由探索而不必与编码争夺预算，文档歧义在实现开始前就通过探测得到消解，文档与二进制程序之间的行为落差被显式处理而不再听天由命。

We evaluate SpecFirst on the full 200-instance ProgramBench suite [5] across four models spanning two families and an order of magnitude of capability (Qwen3.5-397B-A17B, Qwen3.6-35B-A3B, GPT-5.5-high, and GPT-5.4-mini). Across all settings, SpecFirst consistently outperforms the baseline (i.e., mini-SWE-agent), with test pass rate improvement of 6.9%–21.3% and binary exploration coverage gains of 9.4%–18.5%, all statistically significant. Behavioral analysis further confirms that the decomposition restructures how the code synthesis agent allocates its budget: with a prior specification, the agent commits to writing code earlier and produces larger, more complete implementations.

我们在完整的 200 实例 ProgramBench 套件 [5] 上评估 SpecFirst，涵盖两个模型族、能力相差一个数量级的四个模型（Qwen3.5-397B-A17B、Qwen3.6-35B-A3B、GPT-5.5-high 和 GPT-5.4-mini）。在所有设定下，SpecFirst 都一致优于基线（即 mini-SWE-agent），测试通过率提升 6.9%–21.3%，二进制探索覆盖率提升 9.4%–18.5%，且全部具有统计显著性。行为分析进一步确认，这一分解重塑了代码合成智能体分配预算的方式：有了事先的规约，智能体会更早投入写代码，并产出更大、更完整的实现。

II. Background and Motivation

II. 背景与动机

A. Problem Formulation

A. 问题形式化

Let \(P\) denote a target program that is a deterministic command-line program. The agent \(L\) observes \(P\) through two artifacts: (i) documentation \(D\) (e.g., a readme file) that describes \(P\) in natural language, and (ii) an execute-only binary \(B\) that instantiates \(P\)'s observable behavior but whose source code and internal structure are inaccessible. The agent \(L\) task is to produce an implementation \(\hat{I}\) containing source code and necessary files to build an executable file, that reconstructs the behavior of \(P\). The implementation \(\hat{I}\) may be written in any programming language and architecture chosen by the agent. Next, it builds a candidate executable \(\hat{B}\) from \(\hat{I}\), and evaluates \(\hat{B}\) against a given hidden test suite \(T = \{t_i\}_{i=1}^{N}\), where each test \(t_i = \big(a_i, s_i, B(a_i, s_i)\big)\) consists of a command-line argument string \(a_i \in \Sigma^*\), a standard-input stream \(s_i \in \Sigma^*\), and the ground-truth output \(B(a_i, s_i)\) produced by \(B\) on that input. The objective is to produce \(\hat{I}\) that maximizes test pass rate:

令 \(P\) 表示一个确定性命令行目标程序。智能体 \(L\) 通过两类制品观察 \(P\)：(i) 以自然语言描述 \(P\) 的文档 \(D\)（例如 readme 文件），以及 (ii) 一个只能执行的二进制程序 \(B\)，它实例化了 \(P\) 的可观测行为，但其源码与内部结构不可访问。智能体 \(L\) 的任务是产出一份实现 \(\hat{I}\)，其中包含源码以及构建可执行文件所需的必要文件，用以重建 \(P\) 的行为。实现 \(\hat{I}\) 可以采用智能体自行选择的任意编程语言与架构。随后，系统从 \(\hat{I}\) 构建候选可执行文件 \(\hat{B}\)，并针对给定的隐藏测试套件 \(T = \{t_i\}_{i=1}^{N}\) 进行评估，其中每个测试 \(t_i = \big(a_i, s_i, B(a_i, s_i)\big)\) 由一个命令行参数串 \(a_i \in \Sigma^*\)、一个标准输入流 \(s_i \in \Sigma^*\)，以及 \(B\) 在该输入上产生的真值输出 \(B(a_i, s_i)\) 组成。目标是产出使测试通过率最大化的 \(\hat{I}\)：

\[\mathrm{TestRate}(\hat{I}, T) = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\Big[\hat{B}(a_i, s_i) = B(a_i, s_i)\Big] \tag{1}\]
\[\mathrm{TestRate}(\hat{I}, T) = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\Big[\hat{B}(a_i, s_i) = B(a_i, s_i)\Big] \tag{1}\]

which measures the fraction of test cases where \(\hat{B}\) reproduces the observable behavior of \(P\) exactly. A submission achieves \(\mathrm{PassRate} = 1.0\) if and only if \(\hat{B}\) is behaviorally equivalent to \(B\) on \(T\). Figure 1 (blue box) presents the general pipeline of existing code synthesis agents [2], [5], [6]. The agent operates in an iterative probe-then-build loop: it invokes \(B\) on selected inputs and reads \(D\) to build an understanding of the program's behavior, then progressively writes, tests, and refines source code until it judges the implementation sufficiently complete. The final output is a repository containing source code and a build file (e.g., compile.sh), which the evaluation harness compiles into a candidate executable \(\hat{B}\) and scores against hidden tests.

该式度量的是 \(\hat{B}\) 完全复现 \(P\) 可观测行为的测试用例占比。当且仅当 \(\hat{B}\) 在 \(T\) 上与 \(B\) 行为等价时，提交才能取得 \(\mathrm{PassRate} = 1.0\)。图 1（蓝色框）给出了既有代码合成智能体的一般流水线 [2]、[5]、[6]。智能体运行在一个"探测—构建"的迭代循环中：它在选定输入上调用 \(B\) 并阅读 \(D\) 以建立对程序行为的理解，然后逐步编写、测试并精化源码，直到它判断实现已经足够完整。最终输出是一个包含源码和构建文件（如 compile.sh）的仓库，评测框架据此编译出候选可执行文件 \(\hat{B}\) 并针对隐藏测试打分。

B. Limitations of Existing Code Synthesis Agent

B. 既有代码合成智能体的局限

In practice, \(D\) provides only a surface-level description of \(P\) — primary features, typical usage, and representative examples — while remaining ambiguous or silent on edge cases, output formats, and error behavior [17], [18]. Figure 1 shows the README for gomplate, a command-line template renderer in ProgramBench (https://github.com/hairyhenderson/gomplate). The README describes the tool's purpose and lists common flags, but gomplate extends Go's text/template engine with a large library of built-in functions spanning namespaces such as coll, math, net, crypto, and strings. No README can enumerate the precise semantics, argument types, error conditions, and output formats of every function; faithful re-implementation therefore requires extensive behavioral exploration of the binary. We use this instance to illustrate the limitations of the existing single-loop framework.

实践中，\(D\) 只给出对 \(P\) 的表层描述——主要特性、典型用法和代表性示例——而对边界情况、输出格式和错误行为则含糊其辞甚至只字不提 [17]、[18]。图 1 展示了 ProgramBench 中命令行模板渲染器 gomplate（https://github.com/hairyhenderson/gomplate）的 README。该 README 描述了工具用途并列出了常用标志位，但 gomplate 在 Go 的 text/template 引擎之上扩展了一个庞大的内置函数库，覆盖 coll、math、net、crypto、strings 等命名空间。没有任何 README 能穷举每个函数的精确语义、参数类型、错误条件和输出格式；因此，忠实的重实现必然需要对二进制程序进行大量的行为探索。我们用这个实例来说明既有单循环框架的局限。

Ineffective exploratory probing. Without a dedicated exploration phase, the baseline agent interleaves probing with coding, allocating only a fraction of its turns to behavioral discovery before committing to an implementation. For gomplate, this is particularly damaging: the agent must understand not only the top-level CLI interface but also the semantics of functions across ten namespaces, each with its own argument conventions and edge-case behavior. In practice, we observe that the general code synthesis agent (i.e., mini-SWE-agent using Qwen3.6-35B-A3B) confines its probing to the functions explicitly mentioned in the README — primarily the env and data namespaces — while leaving the behavior of coll, math, net, and random largely unverified.

无效的探索性探测。 缺少专门的探索阶段，基线智能体会把探测与编码交错进行，在投入实现之前只把一小部分轮次分配给行为发现。对 gomplate 而言这尤其致命：智能体不仅要理解顶层 CLI 接口，还要理解横跨十个命名空间的函数语义，每个命名空间都有自己的参数约定和边界行为。实践中我们观察到，通用代码合成智能体（即使用 Qwen3.6-35B-A3B 的 mini-SWE-agent）把探测局限在了 README 中明确提到的函数上——主要是 env 和 data 命名空间——而 coll、math、net 和 random 的行为基本未经验证。

Specification loss over long horizon. Even when the collected specification is read correctly, its content can be lost across a long run if nothing anchors it. In gomplate, the general code synthesis agent (i.e., mini-SWE-agent using GPT-5.5-high) collected the full namespace index at turn 4, receiving function signatures for every namespace including aws, gcp, sockaddr, semver, sprig, and cidr. Yet across the remaining 25 turns, none of these six namespace names appears again in the agent's reasoning or tool calls. The information was observed once and never re-referenced: the final submission's function map registers 17 namespaces and silently omits all six, causing 126 test cases to fail before a single line of code is written for them.

长程下的规约丢失。 即便收集到的规约被正确读取，若没有任何东西为其锚定，其内容也会在长时间运行中丢失。在 gomplate 中，通用代码合成智能体（即使用 GPT-5.5-high 的 mini-SWE-agent）在第 4 轮收集到了完整的命名空间索引，拿到了包括 aws、gcp、sockaddr、semver、sprig 和 cidr 在内的所有命名空间的函数签名。然而在其余 25 轮中，这六个命名空间的名称再未在智能体的推理或工具调用中出现过。这些信息被观测了一次便再未被引用：最终提交的函数映射表注册了 17 个命名空间，静默地漏掉了这六个，导致 126 个测试用例在还没为它们写下一行代码时就已注定失败。

Error propagation without anchoring. Without a persistent specification, a single early misinterpretation can silently corrupt every subsequent implementation decision. In the gomplate instance under Qwen3.6-35B-A3B, the agent correctly reads the typed signature Seq(start, end, step int64) []int64 from documentation at turns 4–5. Yet when Seq is first implemented at turn 57, it emits a degraded form — func Seq(args ...interface) []interface — discarding both typed arguments and return value. Over the next 140 turns the math namespace is refactored five times, each time re-emitting the wrong signature without ever consulting the original documentation. The incorrect signature ships in the final submission, causing 25 of 43 Seq-related tests to fail with type errors.

缺乏锚定的错误传播。 没有一份持久化的规约，一次早期的误读就能悄然污染其后每一个实现决策。在 Qwen3.6-35B-A3B 下的 gomplate 实例中，智能体在第 4–5 轮从文档中正确读到了带类型的签名 Seq(start, end, step int64) []int64。然而当 Seq 在第 57 轮首次被实现时，它给出的是一个退化形式——func Seq(args ...interface) []interface——同时丢弃了带类型的参数和返回值。在其后的 140 轮里，math 命名空间被重构了五次，每次都重新发出这个错误签名，而从未回头查阅原始文档。这个错误签名最终随提交发布，导致 43 个 Seq 相关测试中有 25 个因类型错误而失败。

These limitations motivate SpecFirst's core design: a dedicated spec agent that systematically explores the specification before implementation begins, externalizing its findings into a persistent specification file (Spec.md) that eliminates the coverage gap from ineffective probing, prevents early misinterpretations from propagating uncorrected, and ensures that behavioral knowledge discovered during exploration is never lost across turns.

这些局限催生了 SpecFirst 的核心设计：一个专职的规约智能体，在实现开始之前系统化地探索规约，并把其发现外化为一份持久的规约文件（Spec.md），从而消除无效探测带来的覆盖缺口、阻止早期误读在未经纠正的情况下继续传播，并确保探索期间发现的行为知识不会跨轮次丢失。

III. Approach of SpecFirst

III. SpecFirst 的方法

Our approach directly addresses all three limitations through a dedicated specification elicitation phase prior to implementation. We implement an autonomous spec agent that probes \(B\) systematically through black-box interaction, uncovering behaviors that documentation \(D\) leaves implicit or omits entirely — directly countering ❶ by ensuring exploration is complete before coding begins. The elicited specification is persisted as an explicit artifact \(S\) (i.e., SPEC.md in our case), which serves as a stable behavioral contract that anchors all subsequent implementation decisions, resolving ❷ by providing an anchor that prevents early errors from compounding. Critically, because \(S\) is stored externally rather than maintained implicitly in the model's context, it remains intact regardless of context growth or compression, mitigating ❸. The overall framework of SpecFirst is presented in Figure 1. The code synthesis agent can be any existing agent (e.g., OpenHands [6] or SWE-agent [2]). If the agent encounters an ambiguity or gap in \(S\) during implementation, it may still probe binary \(B\) to resolve it. We elaborate on the design and operation of the spec agent in the following sections.

我们的方法通过在实现之前设置一个专门的规约获取阶段，直接应对上述三项局限。我们实现了一个自主的规约智能体，它通过黑盒交互系统化地探测 \(B\)，揭示文档 \(D\) 只做隐含表达或完全省略的行为——通过确保探索在编码开始前就已完成，直接针对 ❶。获取到的规约被持久化为显式制品 \(S\)（在我们的实现中即 SPEC.md），它充当稳定的行为契约，锚定其后所有实现决策，通过提供防止早期错误叠加的锚点来解决 ❷。关键在于，由于 \(S\) 存储在外部而非隐式维持在模型上下文中，无论上下文如何增长或被压缩，它都保持完整，从而缓解 ❸。SpecFirst 的整体框架见图 1。代码合成智能体可以是任何既有智能体（例如 OpenHands [6] 或 SWE-agent [2]）。若智能体在实现过程中遇到 \(S\) 中的歧义或缺口，它仍可探测二进制程序 \(B\) 来解决。我们在后续小节中详述规约智能体的设计与运作。

A. Eliciting Behavior Specification through Probing of the Executable File

A. 通过探测可执行文件获取行为规约

At each turn, the spec agent selects a probe, i.e., an invocation of \(B\) with arguments, flags, or stdin chosen from what it has inferred so far, and observes the run time results from triple channels (stdout, stderr, exit). Free-form bash was chosen over a structured probe API because it mirrors how a human engineer would interact with an unfamiliar tool, and because it allows the agent to chain commands (e.g., constructing input files, running the binary, and inspecting its output in one step). For interactive or TUI programs, pre-installed tmux/libtmux provides a virtual terminal through which the agent can send keystrokes and capture screen state.

在每一轮中，规约智能体选择一次探测，即依据它已推断出的信息，用某组参数、标志位或标准输入去调用 \(B\)，并从三条通道（stdout、stderr、exit）观察运行时结果。我们选择自由形式的 bash 而非结构化的探测 API，一是因为它更贴近人类工程师与陌生工具打交道的方式，二是因为它允许智能体串联命令（例如在一步之内构造输入文件、运行二进制程序并检查其输出）。对于交互式或 TUI 程序，预装的 tmux/libtmux 提供了一个虚拟终端，智能体可通过它发送按键并捕获屏幕状态。

The spec agent conducts an iterative probing loop in which each observation of binary \(B\) informs the next probe. Starting from the behavioral skeleton provided by \(D\), the agent progressively deepens its exploration of \(P\) by targeting the classes of behavior that documentation characteristically under-specifies. Analyzing of the \(D\) reveals four recurring probing patterns that go beyond what \(D\) already provides:

规约智能体执行一个迭代探测循环，其中对二进制程序 \(B\) 的每一次观测都会指导下一次探测。从 \(D\) 提供的行为骨架出发，智能体针对文档惯常欠规约的那几类行为，逐步深化对 \(P\) 的探索。对 \(D\) 的分析揭示出四种超出 \(D\) 已有内容的、反复出现的探测模式：

  • Boundary probing: testing inputs at the limits of accepted ranges (e.g., empty input, maximum-length strings, special characters) to determine exact boundary semantics that documentation leaves implicit.
  • Error-path elicitation: systematically triggering error conditions (malformed input, missing required arguments, conflicting flags) to record the precise stderr message and exit code each condition produces.
  • Combinatorial flag testing: exercising flags in combination to surface interaction effects absent from per-flag documentation.
  • Output-format refinement: presenting adjacent inputs and comparing their outputs to resolve ambiguities in field ordering, delimiter choice, and whitespace handling that prose descriptions inevitably leave underspecified.
  • 边界探测： 在可接受范围的极限处测试输入（例如空输入、最大长度字符串、特殊字符），以确定文档只做隐含表达的精确边界语义。
  • 错误路径获取： 系统性地触发错误条件（畸形输入、缺失必需参数、冲突标志位），以记录每种条件所产生的精确 stderr 消息和退出码。
  • 组合标志位测试： 组合使用标志位，以暴露单标志位文档中不存在的交互效应。
  • 输出格式精化： 提供相邻输入并比较其输出，以消解字段顺序、分隔符选择和空白处理上的歧义——这些正是散文式描述必然会欠规约的地方。

B. Constraints and Shortcut Prevention

B. 约束与捷径防范

We observe that LLM agents can shortcut the intended task in ways that inflate apparent performance without genuine behavioral understanding. Two shortcuts are particularly dangerous in this setting: (a) source recovery locates the original source code via package registries, GitHub, or web search, which would trivialize re-implementation; (b) binary introspection uses disassemblers, tracers, or decompilers to bypass black-box interaction entirely. Neither shortcut represents the specification-elicitation behavior we aim to study, and both would confound the results.

我们观察到，LLM 智能体可能以某些方式抄近路完成预期任务，从而在没有真正行为理解的情况下虚高其表观性能。在本设定下有两类捷径尤其危险：(a) 源码找回，即通过包registry、GitHub 或网络搜索定位原始源码，这会让重实现变得毫无意义；(b) 二进制内省，即使用反汇编器、跟踪器或反编译器完全绕开黑盒交互。这两类捷径都不代表我们想研究的规约获取行为，且都会混淆实验结果。

Therefore, to address this, when designing prompts, we explicitly prohibit LLM from doing both classes of actions. All interactions with \(B\) must go through its normal user interface (CLI flags, stdin/stdout). An automated judge inspects the agent's command history for prohibited patterns (repository clones, registry installs, source tarball downloads, and disassembler calls); any detected violation disqualifies the run and records a score of zero. Wrapping or shimming the provided binary is similarly prohibited and detected. This enforcement ensures that all behavioral knowledge encoded in the generated spec file derives from black-box observation, making the specification-elicitation loop the sole source of information beyond \(D\).

因此，为应对这一点，我们在设计提示词时显式禁止 LLM 执行这两类动作。所有与 \(B\) 的交互都必须走其正常用户界面（CLI 标志位、stdin/stdout）。一个自动化判定器会检查智能体的命令历史中是否出现被禁止的模式（仓库克隆、registry 安装、源码 tarball 下载和反汇编器调用）；任何被检出的违规都会使该次运行作废并记为零分。对所提供二进制程序的包装或垫片（shim）同样被禁止且会被检出。这一执行机制确保生成的规约文件中编码的所有行为知识都源自黑盒观测，使规约获取循环成为 \(D\) 之外唯一的信息来源。

C. Specification Deliverable and Format

C. 规约交付物与格式

Even a thorough elicitation loop is only useful if its findings are communicated in a form the downstream exec agent can act on. The format of specification is a non-trivial design variable. A free-form transcript of raw observations is hard to act on, while an over-prescribed template may suppress behavioral detail that does not fit its categories. We adopt the sections format: a light scaffold of six named headings: Overview; Flags; Input & stdin; Output format; Error patterns; Edge cases. They are chosen as the minimal structure that covers the behavioral dimensions a re-implementer needs. The headings prescribe what to document, not how to discover or phrase it, ensuring the isolation between specification elicitation and code synthesis. More comparison of different formats (i.e., freeform and OpenSpec [15]) can be found in Section VII-B.

即便获取循环再彻底，其发现也只有在以下游执行智能体能够据以行动的形式传达出来时才有用。规约的格式是一个不平凡的设计变量。原始观测的自由形式记录难以据以行动，而过度规定的模板又可能压制那些不适配其分类的行为细节。我们采用 sections（分节）格式：一套由六个具名标题构成的轻量骨架：Overview（概览）、Flags（标志位）、Input & stdin（输入与标准输入）、Output format（输出格式）、Error patterns（错误模式）、Edge cases（边界情况）。选择它们，是因为这是覆盖重实现者所需行为维度的最小结构。这些标题规定的是要记录什么，而非如何去发现或表述，从而确保规约获取与代码合成之间的隔离。不同格式（即 freeform 与 OpenSpec [15]）的更多比较见第 VII-B 节。

D. Termination

D. 终止条件

There is no semantic oracle for specification completeness: no external judge can assess whether SPEC.md captures all of \(P\)'s observable behavior. An agent that terminates too early produces an incomplete spec; one that never terminates produces no spec at all. A run terminates under one of three conditions, applied in priority order.

规约的完整性没有语义预言机：没有任何外部判定者能评估 SPEC.md 是否已捕获 \(P\) 的全部可观测行为。过早终止的智能体会产出不完整的规约；永不终止的智能体则根本产不出规约。一次运行在以下三个条件之一下终止，并按优先级顺序应用。

  • Self-declared completion (primary): if the spec agent judges the specification complete, it finalizes the process. Completeness is the agent's own judgment, which is itself a research variable we measure.
  • Step limit: if 1,000 agent–environment turns is reached, it terminated. The generous step limit (1,000 turns) is set to permit high-coverage exploration; in practice, most runs self-terminate well before this cap, confirming that the limit is a safety net rather than a binding constraint.
  • Wall-clock limit: We use 6 hours as a final safeguard. The spec agent is terminated after running 6 hours.
  • 自声明完成（主要条件）： 若规约智能体判断规约已完整，它就结束该流程。完整性由智能体自行判断，而这本身就是我们要度量的一个研究变量。
  • 步数上限： 若达到 1,000 次智能体—环境轮次，则终止。设置这一宽松的步数上限（1,000 轮）是为了允许高覆盖率探索；实践中大多数运行远在该上限之前就自行终止，这印证了该上限只是安全网而非约束性限制。
  • 墙钟上限： 我们以 6 小时作为最后一道保障。规约智能体在运行 6 小时后被终止。

Finally, a deliverable gate enforces artifact presence. If the specification file is absent at submission, the run is rejected and the agent is asked to write it (capped at 8 rejections, after which the run is recorded as a failure).

最后，交付物闸门强制要求制品存在。若提交时规约文件缺失，该次运行会被拒绝并要求智能体补写（最多拒绝 8 次，超出后该次运行记为失败）。

E. Principles of Agent Design

E. 智能体设计原则

We introduce the principles of the agent design involved in SpecFirst in this section. General agent architecture. All our agents follow the ReAct agent design by following previous work [19], [20]. Except for that, we force all agents to emit reasoning output after each tool calling, including observation, considering alternative actions, and reasoning about next actions. This reasoning output forces explicit processing rather than blind tool call chaining and creates interpretable reasoning traces for debugging. Context Management. We compress information passing through the two stages (i.e., spec agent and code synthesis agent), to prevent information overload. More specifically, we condition the code synthesis agent with the structured behavioral specification artifact (i.e., SPEC.md), while discarding verbose reasoning and tool calling outputs from the spec agent. This preserves essential findings while removing redundant content that causes attention dilution when context windows become too large. We summarize the context information between stages rather than complete conversation histories [2], [19].

本节介绍 SpecFirst 中所涉智能体的设计原则。通用智能体架构。 我们所有的智能体都遵循先前工作 [19]、[20] 的 ReAct 智能体设计。除此之外，我们强制所有智能体在每次工具调用后输出推理内容，包括观测、考量替代动作以及对下一步动作的推理。这种推理输出迫使智能体进行显式处理而非盲目串联工具调用，同时也产生了可供调试的可解释推理轨迹。上下文管理。 我们对在两个阶段（即规约智能体与代码合成智能体）之间传递的信息进行压缩，以防信息过载。具体而言，我们用结构化的行为规约制品（即 SPEC.md）来条件化代码合成智能体，同时丢弃规约智能体冗长的推理与工具调用输出。这既保留了关键发现，又移除了会在上下文窗口过大时造成注意力稀释的冗余内容。我们在阶段之间摘要上下文信息，而非传递完整对话历史 [2]、[19]。

IV. Experimental Design

IV. 实验设计

In this section, we present our research questions (RQs), studied dataset, retrievers, used prompt templates, implementation details, and our approach to RQs.

本节给出我们的研究问题（RQ）、所用数据集、检索器、所用提示词模板、实现细节，以及我们回答各 RQ 的方法。

A. Research Question

A. 研究问题

We aim to answer the following research question:

我们旨在回答以下研究问题：

  • RQ1: What is the effectiveness of SpecFirst?
  • RQ2: How effective is SpecFirst across task difficulty levels?
  • RQ3: Does the Spec Agent improve behavioral exploration coverage?
  • RQ4: How does SpecFirst affect the behavior of the code synthesis agent?
  • RQ1： SpecFirst 的有效性如何？
  • RQ2： SpecFirst 在不同任务难度层级上的有效性如何？
  • RQ3： 规约智能体是否提升了行为探索覆盖率？
  • RQ4： SpecFirst 如何影响代码合成智能体的行为？

In RQ1, we evaluate the effectiveness of SpecFirst in synthesizing programs from scratch and compare it with selected baseline. In RQ2, we evaluate the effectiveness of SpecFirst across instances with different difficulty levels. In RQ3, we evaluate the specification exploration ability of SpecFirst and compare it with the baseline. In RQ4, we investigate how the spec agent affects the behavior of the code synthesis agent by comparing pipeline configurations with and without spec elicitation.

在 RQ1 中，我们评估 SpecFirst 从零合成程序的有效性，并与选定基线比较。在 RQ2 中，我们评估 SpecFirst 在不同难度层级实例上的有效性。在 RQ3 中，我们评估 SpecFirst 的规约探索能力并与基线比较。在 RQ4 中，我们通过比较有无规约获取的流水线配置，考察规约智能体如何影响代码合成智能体的行为。

B. Benchmark

B. 基准

We evaluate on the full ProgramBench suite [5], which comprises 200 command-line program instances drawn from real-world open-source tools, covering widely used software and complex applications, such as FFmpeg, SQLite, and the PHP interpreter. Those 200 task instances in ProgramBench are built from repositories written primarily in compiled languages: Rust (107), Go (46 repositories), C/C++ (45 repositories), 1 (Java), and 1 (Haskell). Each instance provides a natural-language documentation (a README and man page) describing the program, and an execute-only binary that serves as the behavioral oracle during spec elicitation and implementation. Each instance is labelled by difficulty — easy (28), medium (143), and hard (29) — and annotated with the implementation language of the reference binary. To evaluate the correctness and coverage of the implemented program, the benchmark contains 248,853 test functions across its 200 tasks, averaging a median of 770 tests per task. These suites achieve an average of 79.7% line coverage, and are hidden from the code synthesis agent.

我们在完整的 ProgramBench 套件 [5] 上评估，该套件包含 200 个取自真实开源工具的命令行程序实例，覆盖广泛使用的软件和复杂应用，例如 FFmpeg、SQLite 和 PHP 解释器。ProgramBench 中这 200 个任务实例构建自主要以编译型语言编写的仓库：Rust（107）、Go（46 个仓库）、C/C++（45 个仓库）、Java（1）和 Haskell（1）。每个实例提供一份描述该程序的自然语言文档（README 和 man 手册页），以及一个在规约获取和实现阶段充当行为预言机的只能执行的二进制程序。每个实例都按难度标注——easy（28）、medium（143）和 hard（29）——并标注了参考二进制程序的实现语言。为评估所实现程序的正确性与覆盖率，该基准在其 200 个任务中共包含 248,853 个测试函数，每个任务的测试数中位数平均为 770。这些套件平均达到 79.7% 的行覆盖率，且对代码合成智能体不可见。

C. Evaluation Metric

C. 评估指标

Average test pass rate as the primary metric. For each instance \(p\), let \(k_p\) denote the number of hidden test cases passed by the candidate executable and \(n_p\) the total number of test cases for that instance. The instance-level pass rate is \(r_p = k_p / n_p\), and the benchmark-level score is the mean over all instances:

以平均测试通过率为主要指标。 对每个实例 \(p\)，令 \(k_p\) 表示候选可执行文件通过的隐藏测试用例数，\(n_p\) 表示该实例的测试用例总数。实例级通过率为 \(r_p = k_p / n_p\)，基准级得分为其在所有实例上的均值：

\[\bar{r} = \frac{1}{|P|}\sum_{p \in P} \frac{k_p}{n_p} \tag{2}\]
\[\bar{r} = \frac{1}{|P|}\sum_{p \in P} \frac{k_p}{n_p} \tag{2}\]

This metric awards partial credit for implementations that reproduce a subset of the target's behavior, making it sensitive to incremental improvements that a binary resolved/unresolved rate would mask. Note that even the strongest baseline, GPT-5.5-high without spec elicitation, fully resolves only 1 of 200 instances (resolved rate 0.5%) [5], yet achieves a non-trivial \(\bar{r}\) reflecting partial behavioral coverage across many instances. Average test pass rate therefore provides a meaningful signal for comparing pipeline configurations in a regime where full resolution is rare.

该指标对复现了目标部分行为的实现给予部分学分，从而对"已解决/未解决"这类二值比率会掩盖的增量改进保持敏感。注意，即便是最强的基线 GPT-5.5-high（不做规约获取），也只完全解决了 200 个实例中的 1 个（解决率 0.5%）[5]，但仍取得了不平凡的 \(\bar{r}\)，反映出它在许多实例上实现了部分行为覆盖。因此，在完全解决极为罕见的这一区间内，平均测试通过率为比较不同流水线配置提供了有意义的信号。

Probing Coverage. To quantitatively evaluate the specification exploration ability of our approach against the baseline, we introduce probing coverage as the primary metric. Given a target binary executable \(B\), let \(C = \{c_1, c_2, \ldots, c_N\}\) denote the set of all \(N\) executable lines of code in \(B\). During the probing phase, the agent interacts with \(B\) by issuing a sequence of probes; for each probe, we instrument \(B\) to record the set of lines executed. We use a language-specific instrumentation tool for each language. For instance, we use go build -cover for Go binaries, gcc --coverage for C/C++ binaries, and cargo llvm-cov for Rust binaries to capture line-level execution traces for every probe issued during the session. Upon completion of the probing phase, we aggregate the unique recorded lines across all probes to obtain the covered set \(C_{\text{probed}} \subseteq C\). Probing coverage is then defined as:

探测覆盖率。 为定量评估我们的方法相对基线的规约探索能力，我们引入探测覆盖率作为主要指标。给定目标二进制可执行文件 \(B\)，令 \(C = \{c_1, c_2, \ldots, c_N\}\) 表示 \(B\) 中全部 \(N\) 行可执行代码的集合。在探测阶段，智能体通过发出一系列探测与 \(B\) 交互；对每次探测，我们对 \(B\) 进行插桩以记录被执行的代码行集合。我们为每种语言使用对应的插桩工具。例如，我们对 Go 二进制程序使用 go build -cover，对 C/C++ 二进制程序使用 gcc --coverage，对 Rust 二进制程序使用 cargo llvm-cov，以捕获会话期间每次探测的行级执行轨迹。探测阶段结束后，我们汇总所有探测中记录到的唯一代码行，得到被覆盖集合 \(C_{\text{probed}} \subseteq C\)。探测覆盖率定义为：

\[\mathrm{Coverage} = \frac{|C_{\text{probed}}|}{|C|} \times 100\% \tag{3}\]
\[\mathrm{Coverage} = \frac{|C_{\text{probed}}|}{|C|} \times 100\% \tag{3}\]

A higher probing coverage indicates that the agent has exercised a larger portion of the program's behavior during specification, reflecting a more thorough and complete understanding of the binary's functionality.

更高的探测覆盖率表明智能体在规约阶段执行到了程序更大比例的行为，反映出对二进制程序功能更彻底、更完整的理解。

VI. Related Work

VI. 相关工作

A. LLM-based Code Generation and Program Synthesis

A. 基于 LLM 的代码生成与程序合成

The application of large language models to code synthesis has progressed from template-filling approaches [25] through neural program induction [26] to contemporary autoregressive models trained on hundreds of billions of tokens of source code [3], [27]–[30]. These models achieve impressive performance on function-level benchmarks such as HumanEval [3] and MBPP [31], where a docstring and a handful of unit-test examples provide a highly constrained, unambiguous specification. Scaling the same paradigm to repository-level or whole-program tasks reveals a pronounced degradation. SWE-bench [2] demonstrates that resolving real GitHub issues, which requires understanding repository context far harder than synthesizing isolated functions. Agentic frameworks [2], [19], [32], [33] couple LLMs with tool-use loops (shell, file editors, web search) to extend their reach, yet they still rely on a task description written by a human that is treated as a fixed, complete specification. ProgramBench [5] introduces a harder variant: the reference behavior is embodied in a black-box binary, not a text description, forcing the agent to discover the specification rather than consume it. Our work is the first to explicitly design the discovery step as a first-class, reusable pipeline component when building programs from scratch.

把大语言模型应用于代码合成，已从模板填充方法 [25] 经神经程序归纳 [26] 发展到在数千亿源码 token 上训练的当代自回归模型 [3]、[27]–[30]。这些模型在 HumanEval [3] 和 MBPP [31] 等函数级基准上取得了亮眼性能——在那里，一段 docstring 加上少量单元测试示例就提供了高度受限且无歧义的规约。把同一范式扩展到仓库级或整程序级任务时，性能会出现明显退化。SWE-bench [2] 表明，解决真实的 GitHub issue 需要理解仓库上下文，其难度远高于合成孤立函数。智能体框架 [2]、[19]、[32]、[33] 把 LLM 与工具使用循环（shell、文件编辑器、网络搜索）耦合起来以扩展其能力边界，但它们仍然依赖一份由人类撰写、并被当作固定且完整规约的任务描述。ProgramBench [5] 引入了一个更难的变体：参考行为体现在一个黑盒二进制程序中而非文本描述中，迫使智能体去发现规约而非消费规约。我们的工作是首个在从零构建程序时，把发现步骤显式设计为一等、可复用流水线组件的工作。

B. Requirements Elicitation in Software Engineering

B. 软件工程中的需求获取

Requirements engineering (RE) is among the most studied disciplines in SE [11]–[13], with a recurring finding that written artifacts systematically omit behavioral detail, contain ambiguities, and conflict with one another [17], [18], making elicitation through interaction the standard remedy [14], [34]. NLP and LLM techniques have been applied to automate parts of this process, including ambiguity detection [18], traceability recovery [35], and requirements inconsistency detection [36], but these approaches treat requirements as textual artifacts to be processed rather than behaviors to be discovered through interaction. SpecAgent takes the complementary view, instantiating an LLM as an active elicitor that probes a running system rather than analyzing static documents — closest in spirit to behavior-driven development [37], [38], but producing a requirements artifact rather than a test suite.

需求工程（RE）是 SE 中被研究得最多的学科之一 [11]–[13]，其中一个反复出现的发现是：书面制品系统性地遗漏行为细节、包含歧义、彼此冲突 [17]、[18]，因而通过交互进行获取成为标准解法 [14]、[34]。NLP 与 LLM 技术已被用于自动化该过程的部分环节，包括歧义检测 [18]、可追溯性恢复 [35] 和需求不一致检测 [36]，但这些方法把需求视为待处理的文本制品，而非待通过交互发现的行为。SpecAgent 采取互补视角，把 LLM 实例化为一个主动的获取者，去探测一个正在运行的系统而非分析静态文档——精神上最接近行为驱动开发 [37]、[38]，但产出的是需求制品而非测试套件。

C. Black-box Program Analysis and Specification Extraction

C. 黑盒程序分析与规约抽取

The closest prior work to SpecFirst's elicitation loop is the line of research on protocol reverse engineering, which probes network binaries to extract message formats and state machines [39], [40]. These approaches share our black-box observation model but produce machine-readable protocol grammars for security analysis rather than natural-language behavioral specifications for code generation. Specification mining [41] and dynamic invariant detection [42] infer formal properties from execution traces, but require either source instrumentation or passive observation of existing traces rather than active, agent-directed probing. LLM-based decompilation [43] recovers source from binaries at the instruction level and requires disassembly access that our setting explicitly prohibits. Program translation approaches [44] operate source-to-source and assume a complete, readable specification is already available. SpecFirst occupies a distinct position: it actively probes a black-box binary under maximal access restrictions and produces a natural-language behavioral specification consumable directly by a downstream LLM code synthesis agent.

与 SpecFirst 获取循环最接近的既有工作，是协议逆向工程这条研究线：它探测网络二进制程序以抽取消息格式和状态机 [39]、[40]。这些方法与我们共享黑盒观测模型，但产出的是供安全分析使用的机器可读协议文法，而非供代码生成使用的自然语言行为规约。规约挖掘 [41] 与动态不变式检测 [42] 从执行轨迹中推断形式化性质，但它们要么需要源码插桩，要么依赖对既有轨迹的被动观察，而非主动的、由智能体导向的探测。基于 LLM 的反编译 [43] 在指令层面从二进制程序中恢复源码，需要我们的设定明确禁止的反汇编访问。程序翻译方法 [44] 在源码到源码层面运作，并假定已经具备一份完整、可读的规约。SpecFirst 占据了一个独特位置：它在最大访问限制下主动探测黑盒二进制程序，并产出一份可被下游 LLM 代码合成智能体直接消费的自然语言行为规约。

VII. Discussion

VII. 讨论

A. Failure case analysis

A. 失败案例分析

To understand the failure case and identify their root causes, we randomly sample 50 test failure cases across four models and manually label each by examining three artifacts jointly: (i) the failing-test message (what behavior the test exercises and what concrete output, exit code, or error string it expects), (ii) the Spec.md (whether and how precisely the behavior is described), and (iii) the relevant source snippet (whether the implementation contains the corresponding code path and whether it matches Spec.md). We observed the following five types of failures:

为理解失败案例并识别其根因，我们跨四个模型随机抽取 50 个测试失败案例，通过联合考察三类制品来人工标注每一个：(i) 失败测试的报错信息（该测试考察什么行为，以及它期望的具体输出、退出码或错误串），(ii) Spec.md（该行为是否被描述、描述得多精确），以及 (iii) 相关源码片段（实现中是否包含对应代码路径，以及它是否与 Spec.md 一致）。我们观察到以下五类失败：

F1: Spec Omission (10%). Spec.md never documents the features that the test exercises (e.g., the CLI flag, subcommand, error path, or output channel). It means that the spec agent failed to discover and collect the behavior from the binary.

F1：规约遗漏（10%）。 Spec.md 从未记录该测试所考察的特性（例如 CLI 标志位、子命令、错误路径或输出通道）。这意味着规约智能体未能从二进制程序中发现并收集该行为。

F2: Wrong Spec Description (4%). Spec.md describes the behavior incorrectly (e.g., attributing a message to stderr when the test asserts stdout). The implementation was faithful to Spec.md, but Spec.md itself contradicted the binary's actual behavior.

F2：规约描述错误（4%）。 Spec.md 对行为的描述有误（例如把某条消息归到 stderr，而测试断言的是 stdout）。实现忠实于 Spec.md，但 Spec.md 本身与二进制程序的实际行为相矛盾。

F3: Inaccurate Spec Description (26%). Spec.md documents the feature under test, but the description is insufficiently precise, forcing the implementation agent to guess. For example, Spec.md may document that invalid input produces an error without specifying the exit code or output channel; the implementation chooses rc=1 with a stderr message, while the test expects rc=2 with a stdout message.

F3：规约描述不精确（26%）。 Spec.md 记录了被测特性，但描述不够精确，迫使实现智能体去猜。例如，Spec.md 可能记录了非法输入会产生错误，却未指明退出码或输出通道；实现选择了 rc=1 加一条 stderr 消息，而测试期望的是 rc=2 加一条 stdout 消息。

F4: Execution Fault (52%). Spec.md describes the behavior correctly and completely, yet the implementation diverges. Common shapes include a subcommand recognized in help text but rejected by the dispatcher, a flag was parsed but its effect never applied, or an error format that contradicts Spec.md's documented convention. This is the dominant failure mode, indicating that even a correct Spec.md does not guarantee a correct implementation for complex behavioral constraints.

F4：执行故障（52%）。 Spec.md 对行为的描述既正确又完整，实现却仍然偏离。常见形态包括：某个子命令在帮助文本中被识别却被分发器拒绝；某个标志位被解析了却从未施加其效果；或错误格式与 Spec.md 所记录的约定相矛盾。这是主导性失败模式，表明即便 Spec.md 正确，也不能保证在复杂行为约束下得到正确的实现。

F5: Environment-dependent Error (8%). Failures are environment-dependent (e.g., NS server strings embedded in error messages, missing test-wrapper paths, or subprocess timeouts from absent toolchains). These reflect benchmark infrastructure noise rather than agent deficiencies.

F5：环境相关错误（8%）。 失败与环境相关（例如错误消息中内嵌的 NS 服务器串、缺失的测试包装器路径，或因工具链缺失导致的子进程超时）。这些反映的是基准基础设施噪声，而非智能体缺陷。

Implications. Although SpecFirst prove the use of spec agent is a promising direction for building a program from scratch. Our failure analysis suggests the following research direction. The dominant failure mode (F4, 52%) indicates that closing the remaining gap requires stronger execution-stage reasoning (e.g., better instruction following, self-consistency checking against Spec.md, and test-driven repair loops), rather than improvements to spec elicitation alone. F1, F2, and F3 (40% combined) suggest that elicitation coverage and behavioral fidelity remains an open problem; future work could further explore targeted probing strategies that systematically exercise under-documented surfaces such as error paths, flag interactions, and output routing.

启示。 尽管 SpecFirst 证明了使用规约智能体是从零构建程序的一个有前景的方向，我们的失败分析仍指出了以下研究方向。主导性失败模式（F4，52%）表明，弥合剩余差距需要更强的执行阶段推理（例如更好的指令遵循、针对 Spec.md 的自洽性检查，以及测试驱动的修复循环），而不仅仅是改进规约获取。F1、F2 和 F3（合计 40%）表明，获取覆盖率与行为保真度仍是开放问题；未来工作可以进一步探索有针对性的探测策略，系统性地执行错误路径、标志位交互和输出路由等文档欠覆盖的接触面。

B. Does the specification's format matter?

B. 规约的格式重要吗？

To understand the impact of specification format, we compared the following formats, differing only in the deliverable-instruction paragraph of the task prompt; all other prompt text, probing rules, and limits are identical across conditions. Note that all the results reported in RQs are based on Sections.

为理解规约格式的影响，我们比较了以下几种格式，它们仅在任务提示词的交付物说明段落上有差异；其他所有提示词文本、探测规则和限制在各条件下完全相同。注意，各 RQ 中报告的全部结果均基于 Sections。

  • Sections. The format we used is introduced in Section VII-B, where the agent is asked to write SPEC.md as structured Markdown under named headings.
  • Freeform. The agent chooses its own structure and coverage criteria. This condition isolates whether imposed structure helps or hurts downstream exec quality.
  • OpenSpec. The agent writes SPEC.md in the OpenSpec format [15], structuring the document as a ## Purpose section followed by ### Requirement: blocks, each annotated with RFC 2119 keywords (MUST/SHALL, SHOULD, MAY), and concrete #### Scenario: examples in GIVEN/WHEN/THEN form. This condition tests whether a more formal, requirements-engineering vocabulary improves the precision of the elicited specification.
  • Sections。 我们所使用的格式，已在第 VII-B 节介绍，即要求智能体把 SPEC.md 写成具名标题之下的结构化 Markdown。
  • Freeform。 智能体自行选择结构与覆盖标准。该条件用于分离出"施加结构"究竟有助于还是有损下游执行质量。
  • OpenSpec。 智能体以 OpenSpec 格式 [15] 撰写 SPEC.md，把文档组织为一个 ## Purpose 小节，其后是若干 ### Requirement: 块，每块以 RFC 2119 关键字（MUST/SHALL、SHOULD、MAY）标注，并配有 GIVEN/WHEN/THEN 形式的具体 #### Scenario: 示例。该条件检验更正式的需求工程词汇是否能提升所获取规约的精确度。

We compare the average test pass rate of SpecFirst using the above different format with GPT-5.4-mini on randomly sampled 50 instances (we choose to use GPT-5.4-mini and a subset due to budget limit). Table VI compares the effectiveness of different formats. As shown, every specification format improves on the baseline, while Sections improves the most and outperforms other formats.

我们在随机抽取的 50 个实例上，用 GPT-5.4-mini 比较 SpecFirst 采用上述不同格式时的平均测试通过率（受预算限制，我们选择使用 GPT-5.4-mini 和一个子集）。表 VI 比较了不同格式的有效性。如表所示，每种规约格式都优于基线，而 Sections 提升最大，优于其他格式。

C. Cost of SpecFirst

C. SpecFirst 的成本

Table VII reports the mean per-instance cost for Direct-Synthesis and SpecFirst. The total cost of SpecFirst is higher by 48%–130% across models, which is expected: the spec agent constitutes an additional inference phase ($0.25–$3.16 per instance), and the more complete specification produced leads the code synthesis agent to generate larger, more feature-complete implementations, modestly increasing its own cost as well (+6%–+32% for most models). The exception is GPT-5.4-mini, where synthesis cost decreases by 17%, suggesting that a clearer upfront specification reduces exploratory overhead during coding. The largest overhead occurs with GPT-5.5-high (+130%), driven primarily by the cost of the spec agent itself rather than by synthesis. Overall, the cost increase is a direct reflection of SpecFirst doing more useful work — broader behavioral exploration and more complete implementation — rather than redundant computation.

表 VII 报告了 Direct-Synthesis 与 SpecFirst 的每实例平均成本。SpecFirst 的总成本在各模型上高出 48%–130%，这在预期之内：规约智能体构成了一个额外的推断阶段（每实例 $0.25–$3.16），且其产出的更完整规约会促使代码合成智能体生成更大、特性更完整的实现，从而也小幅推高其自身成本（多数模型为 +6%–+32%）。例外是 GPT-5.4-mini，其合成成本下降了 17%，这提示更清晰的前置规约减少了编码期间的探索性开销。最大的开销出现在 GPT-5.5-high（+130%），主要由规约智能体本身的成本驱动，而非合成阶段。总体而言，成本上升直接反映了 SpecFirst 做了更多有用的工作——更广的行为探索和更完整的实现——而非冗余计算。

D. Threats to Validity

D. 有效性威胁

Internal Validity. The SpecFirst uses two agents instead of one, meaning it spends more budget than the baseline (without spec agent). The risk is that the improvement is not actually from the value of having a specification, but simply because the model got a larger compute budget. To alleviate this threat, as shown in RQ4, 100% of the runs ended early by choice. Therefore, giving the baseline models more compute wouldn't have naturally increased their test pass rate.

内部有效性。 SpecFirst 使用了两个智能体而非一个，这意味着它比基线（不含规约智能体）花费了更多预算。风险在于，提升可能并非真正来自"拥有规约"的价值，而只是因为模型获得了更大的算力预算。为缓解该威胁，如 RQ4 所示，100% 的运行都是由智能体自行选择提前结束的。因此，给基线模型更多算力也不会自然提高其测试通过率。

External Validity. Our evaluation covers deterministic command-line programs in ProgramBench; results may not generalize to programs with non-deterministic behavior, graphical interfaces, or complex inter-process communication. We evaluate four models on a single scaffold (SWE-agent); while consistent gains across two model families suggest robustness, results may differ for other models and scaffolds. Although SpecFirst requires an executable binary for spec elicitation, the binary serves as a proxy for any executable oracle that exposes a probe-and-observe interface, such as a running REST API, a containerized service, a compiled SDK, or a remote CLI are all equivalent from the spec agent's perspective. The key prerequisite is not a binary specifically but any queryable reference or human, a condition met by most software maintenance, migration, and integration scenarios.

外部有效性。 我们的评估覆盖 ProgramBench 中的确定性命令行程序；结果可能无法推广到具有非确定性行为、图形界面或复杂进程间通信的程序。我们在单一脚手架（SWE-agent）上评估了四个模型；虽然跨两个模型族的一致增益提示了稳健性，但结果在其他模型和脚手架上可能不同。尽管 SpecFirst 需要一个可执行二进制程序来进行规约获取，但该二进制程序只是任何暴露"探测—观察"接口的可执行预言机的代理——从规约智能体的视角看，一个运行中的 REST API、一个容器化服务、一个已编译的 SDK 或一个远程 CLI 都是等价的。关键前提并非必须是二进制程序，而是任何可查询的参照物或人，这一条件在大多数软件维护、迁移和集成场景中都能满足。

Construct Validity. The study's main evaluation metric (a 0–100% scale average test pass rate) combines two different things: whether the agent can actually build a working program, and whether that program behaves correctly. There was a risk that failures such as compilation failures (like a missing compile.sh) would unfairly tank the average scores. However, these total technical failures were extremely rare (at most 3 out of 200 runs). This means when an agent scored a 0%, it was not because it could not build a working program; it was because the program's actual behavior was completely wrong.

构念有效性。 本研究的主要评估指标（0–100% 量纲的平均测试通过率）混合了两件不同的事：智能体是否真的能构建出一个可运行的程序，以及该程序的行为是否正确。存在这样一种风险：编译失败（例如缺失 compile.sh）之类的失败会不公平地拉低平均分。然而，这类彻底的技术性失败极为罕见（200 次运行中至多 3 次）。这意味着当某个智能体得 0% 时，并不是因为它构建不出可运行的程序，而是因为该程序的实际行为完全错误。

VIII. Conclusion

VIII. 结论

We presented SpecFirst, a two-stage agentic framework that explicitly decouples behavioral specification elicitation from code synthesis for from-scratch program re-implementation. By dedicating a separate spec agent to systematically probe the binary and produce a structured specification prior to implementation, SpecFirst addresses three fundamental limitations of single-loop baselines: insufficient behavioral exploration, specification loss over multi-turns, and uncorrected error propagation. Experiments on all 200 ProgramBench instances across four frontier models demonstrate consistent improvements in test pass rates (6.9%–21.3%) and binary exploration coverage (9.4%–18.5%). Our results suggest that treating requirements elicitation as a first-class phase is a promising paradigm for advancing LLM agents on complex, from-scratch software construction tasks.

我们提出了 SpecFirst——一个两阶段智能体框架，针对从零重实现程序的任务，显式地把行为规约获取与代码合成解耦。通过设置一个独立的规约智能体，在实现之前系统化地探测二进制程序并产出结构化规约，SpecFirst 应对了单循环基线的三项根本局限：行为探索不足、多轮次下的规约丢失，以及未经纠正的错误传播。在全部 200 个 ProgramBench 实例上跨四个前沿模型的实验，证明了测试通过率（6.9%–21.3%）与二进制探索覆盖率（9.4%–18.5%）的一致提升。我们的结果表明，把需求获取当作一等阶段，是推进 LLM 智能体完成复杂的从零软件构建任务的一种有前景的范式。
