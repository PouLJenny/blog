Abstract

摘要

Spec-Driven Development (SDD) frameworks guide Large Language Model (LLM)-powered code generation through formal specifications, yet they differ fundamentally in how they enforce traceability between requirements and generated code. This paper presents two controlled empirical studies comparing three SDD frameworks: traceSDD, which enforces mandatory per-line requirement citations using hierarchical REQ-XXX.Y.Z identifiers; Spec Kit, which uses artifact-level traceability through user stories and acceptance criteria; and OpenSpec, which relies on post-hoc external trace maps. We measure two primary outcomes across two frontier LLMs—Claude Sonnet 4.6 (N=20, 4 conditions, 240 implementations) and GLM-5-turbo (N=50, 4 conditions, 600 implementations): output determinism (lexical similarity across independent LLM sessions) and automated hallucination detection rate (TDR). Our pre-registered analysis reveals a consistent, cross-model replicated trade-off: the uncited condition produces significantly higher determinism than the cited condition (Claude: d = −0.76, p = 0.003; GLM: d = −0.72, p < 0.001), while only the cited condition enables automated hallucination detection (TDR: Claude 86.4%, GLM 88.0%, vs 0% for all alternatives, FPR=0% across both studies). traceSDD (cited) significantly outperforms Spec Kit on determinism (Claude: d = 0.47, p = 0.049; GLM: d = 0.42, p = 0.003) but not OpenSpec (Claude: d = 0.18, p = 0.44; GLM: d = 0.14, p = 0.32). These findings establish that citation annotations trade determinism for verifiability, and that this trade-off generalizes across model architectures.

规约驱动开发（Spec-Driven Development, SDD）框架通过形式化规约来引导大语言模型（LLM）驱动的代码生成，但它们在「如何强制需求与生成代码之间的可追溯性」这一点上存在根本差异。本文给出两项受控实证研究，对比三种 SDD 框架：traceSDD，使用层级化 REQ-XXX.Y.Z 标识符强制要求逐行需求引用；Spec Kit，通过用户故事与验收标准实现制品级可追溯性；OpenSpec，依赖事后生成的外部追溯映射。我们在两个前沿 LLM 上测量两项主要结果指标——Claude Sonnet 4.6（N=20，4 个条件，240 份实现）与 GLM-5-turbo（N=50，4 个条件，600 份实现）：输出确定性（跨独立 LLM 会话的词法相似度）与自动化幻觉检出率（TDR）。我们的预注册分析揭示出一个稳定且跨模型可复现的权衡：无引用条件的确定性显著高于带引用条件（Claude：d = −0.76，p = 0.003；GLM：d = −0.72，p < 0.001），而只有带引用条件才能实现自动化幻觉检测（TDR：Claude 86.4%，GLM 88.0%，其余全部为 0%；两项研究的 FPR 均为 0%）。在确定性上，traceSDD（带引用）显著优于 Spec Kit（Claude：d = 0.47，p = 0.049；GLM：d = 0.42，p = 0.003），但相对 OpenSpec 无显著优势（Claude：d = 0.18，p = 0.44；GLM：d = 0.14，p = 0.32）。这些发现确立了：引用标注是用确定性换取可验证性，并且这一权衡可跨模型架构泛化。

1 Introduction

1 引言

The emergence of agentic coding systems—AI agents that autonomously write, test, and revise software—introduces a fundamental accountability problem: how do we verify that the code an agent writes actually implements what was specified? Unlike human developers who can explain their decisions, LLM-generated code appears plausible even when it introduces subtle deviations, including out-of-scope features, prior-art bleed-in from training data, and over-engineering beyond what was specified [1, 2]. These hallucinations are particularly dangerous because they typically pass all automated tests while introducing unauthorized functionality with security, compliance, or maintenance implications [3].

智能体编码系统（agentic coding systems）——能自主编写、测试并修改软件的 AI 智能体——的出现带来了一个根本性的问责难题：我们如何验证智能体写出的代码确实实现了规约所要求的内容？与能够解释自身决策的人类开发者不同，LLM 生成的代码即便引入了微妙偏差也依然显得合情合理，这些偏差包括超出范围的功能、来自训练数据的先验知识渗入，以及超出规约要求的过度工程 [1, 2]。这类幻觉尤其危险，因为它们通常能通过全部自动化测试，却同时引入了未经授权的功能，带来安全、合规或维护上的隐患 [3]。

The challenge of verifying LLM-generated code against specifications draws on a rich history of requirements traceability research in software engineering [4–6]. The IEEE 830 standard defines requirements traceability as the association between requirements and the work products that implement them [7]. Tools such as DOORS and Jama have provided enterprise-grade traceability matrices for decades. However, these traditional tools require substantial manual effort and are not designed for the rapid iteration cycles inherent to AI-assisted coding workflows [8].

针对规约验证 LLM 生成代码这一挑战，可以追溯到软件工程中源远流长的需求可追溯性研究 [4–6]。IEEE 830 标准将需求可追溯性定义为需求与实现这些需求的工作产品之间的关联 [7]。DOORS、Jama 等工具几十年来一直提供企业级的可追溯性矩阵。然而，这些传统工具需要大量人工投入，且并非为 AI 辅助编码工作流固有的快速迭代周期而设计 [8]。

Three specification-driven development (SDD) frameworks have emerged with distinct philosophies on traceability for LLM-generated code. traceSDD enforces mandatory inline citations on every line of code, binding each line to a specific Tier-3 requirement point (REQ-XXX.Y.Z). These citations are treated as verifiable claims: any REQ ID cited in code that does not appear in the specification is an automatically detectable orphan, signaling a hallucinated requirement. GitHub Spec Kit enforces artifact-level consistency through a spec-plan-tasks chain, but once implementation begins, the citation chain ends. OpenSpec uses post-hoc external trace maps (YAML sidecar files) that link line ranges to spec IDs after the fact, without annotating source code directly.

已出现三种规约驱动开发（SDD）框架，它们对 LLM 生成代码的可追溯性持有不同的理念。traceSDD 强制要求每一行代码都带内联引用，把每一行绑定到某个具体的三级需求点（REQ-XXX.Y.Z）。这些引用被视作可验证的断言：代码中引用的任何 REQ ID 若未出现在规约中，就是一个可自动检出的孤儿项，标志着一条被幻觉出来的需求。GitHub Spec Kit 通过 spec-plan-tasks 链条强制制品级一致性，但一旦进入实现阶段，引用链条就断了。OpenSpec 使用事后生成的外部追溯映射（YAML 边车文件），在事后把行区间关联到规约 ID，并不直接在源码中做标注。

The core question this work investigates is whether forcing an agentic coding system to cite a requirement for every line of code it writes materially improves implementation correctness, output determinism, and hallucination detectability—and whether any observed effects replicate across different LLM architectures. To address this question, we conduct two independent controlled studies: Study 1 uses Claude Sonnet 4.6 with 20 benchmark tasks, and Study 2 uses GLM-5-turbo with 50 benchmark tasks spanning 8 software engineering domains, 3 difficulty levels, and 2 size classes. This cross-model design provides the strongest possible evidence for generalizability of our findings.

本工作要考察的核心问题是：强制智能体编码系统为它写下的每一行代码都引用一条需求，是否能实质性地改善实现正确性、输出确定性和幻觉可检出性——以及所观察到的任何效应能否在不同 LLM 架构间复现。为回答这一问题，我们开展了两项独立的受控研究：研究 1 使用 Claude Sonnet 4.6 与 20 个基准任务，研究 2 使用 GLM-5-turbo 与 50 个基准任务，覆盖 8 个软件工程领域、3 个难度层级和 2 个规模类别。这一跨模型设计为我们发现的可泛化性提供了尽可能强的证据。

Our contributions are fourfold. First, we provide the first cross-model controlled comparison of SDD framework citation disciplines (70 total tasks, 4 conditions, 840 implementations). Second, we replicate the citation isolation finding across two fundamentally different LLM architectures, confirming that inline citations significantly reduce output determinism (Claude d = −0.76, GLM d = −0.72). Third, we provide the first comprehensive subgroup analysis across domains, difficulty levels, and size classes, revealing that the determinism penalty of citations is most pronounced for easy and small tasks. Fourth, we demonstrate that hallucination detection via the orphan-REQ check achieves 86–88% TDR with 0% FPR across both models, a unique capability unmatched by any alternative framework.

我们的贡献有四点。第一，我们提供了首个针对 SDD 框架引用纪律的跨模型受控对比（共 70 个任务、4 个条件、840 份实现）。第二，我们在两种根本不同的 LLM 架构上复现了引用隔离效应，确认内联引用会显著降低输出确定性（Claude d = −0.76，GLM d = −0.72）。第三，我们提供了首个跨领域、跨难度层级、跨规模类别的全面亚组分析，揭示出引用带来的确定性代价在简单任务和小型任务上最为显著。第四，我们证明基于孤儿 REQ 检查的幻觉检测在两个模型上都达到 86–88% 的 TDR 且 FPR 为 0%，这是任何替代框架都无法企及的独特能力。

2 Background and Related Work

2 背景与相关工作

2.1 Requirements Traceability in Software Engineering

2.1 软件工程中的需求可追溯性

Requirements traceability—the ability to describe and follow the life of a requirement in both a forwards and backwards direction—has long been recognized as critical for safety-critical and regulated systems [4]. Cleland-Huang et al. [5] identified the gap between theoretical traceability frameworks and practical tooling, arguing that traceability must be embedded in the development workflow rather than treated as a post-hoc documentation exercise. Jalali and Wohlin [6] conducted a systematic literature review finding moderate evidence that traceability improves software quality, though the effect size depends heavily on tool support and process maturity. Pinto et al. [8] surveyed traceability tools and found that most operate at the artifact level (requirement-to-test, requirement-to-module) rather than at the line-of-code level that traceSDD targets. The work presented here extends this line of inquiry into the novel context of LLM-generated code, where the "developer" is an AI agent that cannot be asked to explain its decisions post-hoc.

需求可追溯性——即在正向和反向两个方向上描述并追踪一条需求全生命周期的能力——长期以来被公认为安全关键系统和受监管系统的关键要素 [4]。Cleland-Huang 等人 [5] 指出了理论可追溯性框架与实用工具之间的落差，主张可追溯性必须嵌入开发工作流本身，而非被当作事后的文档工作。Jalali 与 Wohlin [6] 开展了一项系统性文献综述，发现有中等强度的证据表明可追溯性能提升软件质量，但效应量高度依赖于工具支持与流程成熟度。Pinto 等人 [8] 调研了可追溯性工具，发现大多数工具工作在制品级（需求到测试、需求到模块），而非 traceSDD 所瞄准的代码行级。本文的工作把这条研究脉络延伸到 LLM 生成代码这一全新场景中——在这里，「开发者」是一个无法在事后被要求解释其决策的 AI 智能体。

2.2 LLM Code Generation and Hallucination

2.2 LLM 代码生成与幻觉

Large language models have demonstrated remarkable code generation capabilities [9–11]. Codex [9] demonstrated that LLMs can solve competitive programming problems, while GPT-4 [10] showed further improvements in complex reasoning tasks. Recent models including StarCoder [12] and DeepSeek-Coder [13] have pushed code generation quality further. Claude [14] and GLM [15] represent two distinct architectures: Claude uses a transformer with constitutional AI training [16], while GLM uses an autoregressive model with bidirectional attention for pre-training.

大语言模型已展现出令人瞩目的代码生成能力 [9–11]。Codex [9] 证明了 LLM 能解决竞赛编程题目，GPT-4 [10] 则在复杂推理任务上带来了进一步提升。近期模型如 StarCoder [12] 与 DeepSeek-Coder [13] 又把代码生成质量推进了一步。Claude [14] 与 GLM [15] 代表两种不同的架构：Claude 使用带宪法式 AI 训练的 transformer [16]，而 GLM 使用带双向注意力预训练的自回归模型。

However, LLMs are known to hallucinate: generating plausible-looking but factually incorrect or ungrounded content [1, 2]. In the code generation domain, hallucinations manifest as out-of-scope functions, unauthorized imports from prior training data, and over-engineering through unnecessary decorators or optimizations. Ji et al. [1] provided a comprehensive survey of hallucination types in natural language generation, while Huang et al. [2] extended this taxonomy to cover multimodal and code generation contexts. Approaches to detecting code hallucinations include test-based validation [17], static analysis heuristics, and specification comparison. The orphan-REQ check employed by traceSDD represents a novel approach: by requiring the code to cite specific requirement IDs, the system creates a set-difference operation that is both fully automated and language-agnostic.

然而，LLM 众所周知会产生幻觉：生成看似合理但事实上错误或缺乏依据的内容 [1, 2]。在代码生成领域，幻觉表现为超出范围的函数、来自既往训练数据的未授权导入，以及通过不必要的装饰器或优化造成的过度工程。Ji 等人 [1] 对自然语言生成中的幻觉类型做了全面综述，Huang 等人 [2] 则把这一分类法扩展到多模态与代码生成场景。检测代码幻觉的方法包括基于测试的验证 [17]、静态分析启发式规则和规约比对。traceSDD 采用的孤儿 REQ 检查代表了一种新思路：通过要求代码引用具体的需求 ID，系统构造出一个既完全自动化又与语言无关的集合差运算。

2.3 Output Determinism and Consistency in LLMs

2.3 LLM 的输出确定性与一致性

Output determinism in LLMs—the degree to which identical prompts produce identical or highly similar outputs—has received increasing attention. Wang et al. [18] demonstrated that self-consistency, where multiple sampled outputs are used to improve reasoning, can be leveraged for better performance. However, the lexical similarity between independently generated code outputs as a metric of determinism has been less explored. The Levenshtein Set Similarity (LSS) metric, adapted from software clone detection [19], provides a practical measure of inter-run consistency. The hypothesis that specification structure can anchor LLM output toward deterministic solutions is intuitive but, prior to this work, empirically underexplored in the context of SDD frameworks. Our study provides the most comprehensive test of this hypothesis across two distinct LLM architectures.

LLM 的输出确定性——相同提示词产生相同或高度相似输出的程度——正受到越来越多关注。Wang 等人 [18] 证明了自洽性（self-consistency，即用多次采样输出来改进推理）可以被用来提升性能。然而，把独立生成的代码输出之间的词法相似度作为确定性度量，此前研究较少。Levenshtein 集合相似度（LSS）指标改编自软件克隆检测 [19]，提供了一种可操作的跨运行一致性度量。「规约结构能把 LLM 输出锚定到确定性解」这一假设直觉上成立，但在本工作之前，尚未在 SDD 框架语境下得到充分的实证检验。我们的研究在两种不同的 LLM 架构上给出了对这一假设最全面的检验。

2.4 Agentic Coding and Specification-Driven Development

2.4 智能体编码与规约驱动开发

The rise of agentic coding frameworks—where LLMs autonomously plan, implement, test, and revise code—has created a new urgency around structured prompt methodologies. Yao et al. [20] introduced ReAct, combining reasoning and acting for LLM agents. Shinn et al. [21] proposed Reflexion, where agents learn from verbal feedback. These approaches focus on agent architecture rather than the specification format that grounds the agent's behavior. Spec Kit and OpenSpec represent two commercially available specification tools, while traceSDD introduces the novel concept of mandatory per-line citations as a verifiable constraint on LLM-generated code.

智能体编码框架的兴起——LLM 自主规划、实现、测试并修改代码——使得结构化提示词方法论变得空前紧迫。Yao 等人 [20] 提出了 ReAct，把推理与行动结合用于 LLM 智能体。Shinn 等人 [21] 提出了 Reflexion，让智能体从口头反馈中学习。这些方法关注的是智能体架构，而非用来锚定智能体行为的规约格式。Spec Kit 与 OpenSpec 代表两款已商用的规约工具，而 traceSDD 引入了一个全新概念：把强制性的逐行引用作为对 LLM 生成代码的可验证约束。

3 Research Questions and Hypotheses

3 研究问题与假设

This work is guided by two primary research questions, each investigated across two independent LLMs:

本工作由两个主要研究问题引导，每个问题都在两个独立的 LLM 上分别考察：

RQ1 (Output Determinism): Does mandatory per-line REQ citation (traceSDD) produce more lexically consistent code across independent LLM sessions than specification approaches that do not require inline citations (Spec Kit, OpenSpec)?

RQ1（输出确定性）：相比不要求内联引用的规约方案（Spec Kit、OpenSpec），强制逐行 REQ 引用（traceSDD）是否能在独立 LLM 会话之间产生词法上更一致的代码？

RQ2 (Hallucination Detection): Does traceSDD's orphan-REQ check automatically detect scope creep, prior-art injection, and over-engineering that are not explicitly required by the specification, while Spec Kit and OpenSpec provide no automated mechanism?

RQ2（幻觉检测）：traceSDD 的孤儿 REQ 检查是否能自动检出规约并未明确要求的范围蔓延、先验知识注入和过度工程，而 Spec Kit 与 OpenSpec 则完全不提供自动化机制？

We pre-register the following hypotheses, with significance criteria locked before data collection:

我们预注册了以下假设，显著性判据在数据采集之前即已锁定：

H1: traceSDD (cited) mean LSS will be greater than Spec Kit mean LSS (p < 0.05, |d| > 0.5).

H1：traceSDD（带引用）的平均 LSS 将高于 Spec Kit 的平均 LSS（p < 0.05，|d| > 0.5）。

H2: traceSDD (cited) TDR will be substantially greater than 0%, while Spec Kit and OpenSpec TDR will be 0% (automated detection).

H2：traceSDD（带引用）的 TDR 将显著大于 0%，而 Spec Kit 与 OpenSpec 的 TDR 将为 0%（自动化检测）。

H3: All conditions will achieve 100% TPR, confirming that citation discipline does not affect functional correctness.

H3：所有条件都将达到 100% TPR，证实引用纪律不影响功能正确性。

H4 (exploratory): The uncited condition will have higher LSS than the cited condition, revealing that citations introduce rather than reduce lexical variability.

H4（探索性）：无引用条件的 LSS 将高于带引用条件，从而揭示引用是引入而非降低了词法变异性。

4 Experimental Design

4 实验设计

4.1 Task Suites

4.1 任务集

Study 1 (Claude Sonnet 4.6, N=20) used 20 benchmark Python tasks: 10 pre-existing utility tasks (user registry, email validator, retry runner, token service, config resolver, CLI parser, form validator, structured logger, schema migrator, HTTP client) and 10 diverse algorithmic tasks (finite state machine, rate limiter, trie, directed graph, expression parser, plus 5 large multi-file tasks: REST API router, cache store, event bus, plugin registry, CSV pipeline). Tasks span 5 software engineering domains with 15 single-file tasks (∼50–100 lines) and 5 multi-file tasks (∼600–800 lines).

研究 1（Claude Sonnet 4.6，N=20）使用了 20 个基准 Python 任务：10 个既有的工具类任务（用户注册表、邮箱校验器、重试执行器、令牌服务、配置解析器、CLI 解析器、表单校验器、结构化日志器、schema 迁移器、HTTP 客户端）和 10 个多样化的算法类任务（有限状态机、限流器、字典树、有向图、表达式解析器，外加 5 个大型多文件任务：REST API 路由、缓存存储、事件总线、插件注册表、CSV 流水线）。任务覆盖 5 个软件工程领域，其中 15 个单文件任务（约 ∼50–100 行）和 5 个多文件任务（约 ∼600–800 行）。

Study 2 (GLM-5-turbo, N=50) designed 50 novel benchmark tasks spanning 8 software engineering domains: Data Structures and Algorithms (8 tasks), Web/API Utilities (7 tasks), Data Validation and Transformation (7 tasks), Security and Authentication (6 tasks), File I/O and Processing (6 tasks), Concurrency and Async (5 tasks), Configuration and Infrastructure (5 tasks), and Testing, Monitoring and Observability (6 tasks). Tasks are distributed across three difficulty levels (9 easy, 28 medium, 13 hard) and two size classes (37 small single-file, 13 large multi-file). This diversity ensures findings are not domain-specific artifacts but reflect generalizable properties of the SDD frameworks.

研究 2（GLM-5-turbo，N=50）设计了 50 个全新的基准任务，覆盖 8 个软件工程领域：数据结构与算法（8 个任务）、Web/API 工具（7 个任务）、数据校验与转换（7 个任务）、安全与认证（6 个任务）、文件 I/O 与处理（6 个任务）、并发与异步（5 个任务）、配置与基础设施（5 个任务）、测试与监控可观测性（6 个任务）。任务分布在三个难度层级（9 个简单、28 个中等、13 个困难）和两个规模类别（37 个小型单文件、13 个大型多文件）。这种多样性确保研究发现不是特定领域的产物，而是反映了 SDD 框架的可泛化属性。

4.2 Conditions

4.2 实验条件

Four conditions are compared in both studies:

两项研究中都对比以下四个条件：

(A) traceSDD (cited): Uses a hierarchical REQ-XXX.Y.Z specification format with mandatory inline citation annotations (# [REQ-XXX.Y.Z]) on every non-trivial line of generated code.

（A）traceSDD（带引用）：使用层级化 REQ-XXX.Y.Z 规约格式，并强制在生成代码的每一行非平凡代码上加内联引用标注（# [REQ-XXX.Y.Z]）。

(B) traceSDD uncited: Uses the identical REQ-format specification but generates code without any inline citations. This isolates the causal effect of the annotation mechanism itself, since both conditions share identical spec content.

（B）traceSDD 无引用：使用完全相同的 REQ 格式规约，但生成的代码不带任何内联引用。由于两个条件共享完全相同的规约内容，这就把标注机制本身的因果效应隔离了出来。

(C) Spec Kit: Uses Spec Kit's native prose specification format (user stories, FR-XXX requirements, acceptance scenarios) with no citation mechanism.

（C）Spec Kit：使用 Spec Kit 原生的散文式规约格式（用户故事、FR-XXX 需求、验收场景），不含任何引用机制。

(D) OpenSpec: Uses OpenSpec's native capability/scenario specification format with C-NNN section markers and external trace YAML files.

（D）OpenSpec：使用 OpenSpec 原生的能力/场景规约格式，带 C-NNN 章节标记和外部追溯 YAML 文件。

For each condition, three independent cold-start LLM sessions are executed, with no session having knowledge of what other sessions produced.

每个条件下都执行三次独立的冷启动 LLM 会话，任何会话都不知道其他会话产出了什么。

4.3 Metrics

4.3 指标

LSS (Lexical Similarity Score): Computed via difflib.SequenceMatcher.ratio() on comment-stripped, whitespace-normalized source code. For each task-condition pair, the mean LSS is computed over anchor comparisons (run 1 vs run 2, run 1 vs run 3). Higher LSS indicates more deterministic output. For multi-file tasks, files are concatenated alphabetically before comparison.

LSS（词法相似度分数）：在剥除注释、归一化空白后的源码上，通过 difflib.SequenceMatcher.ratio() 计算。对每一个「任务-条件」组合，取锚点比较（run 1 对 run 2、run 1 对 run 3）的平均 LSS。LSS 越高表示输出越确定。对多文件任务，先按字母序拼接文件再比较。

TDR (Traceability Detection Rate): Measures the percentage of injected hallucinations automatically detected. Three hallucination types are injected: H-SCOPE (out-of-scope functions not in any specification requirement), H-PRIOR (prior-art bleed-in via unauthorized imports such as logging or os), and H-OVER (over-engineering via unauthorized decorators such as @lru_cache).

TDR（可追溯性检出率）：衡量被注入的幻觉中被自动检出的百分比。注入三类幻觉：H-SCOPE（任何规约需求中都不存在的越界函数）、H-PRIOR（通过 logging、os 等未授权导入造成的先验知识渗入）、H-OVER（通过 @lru_cache 等未授权装饰器造成的过度工程）。

TPR (True Positive Rate): Measures functional correctness as the proportion of ground-truth tests passed by each implementation.

TPR（真阳性率）：以每份实现通过基准真值测试的比例来衡量功能正确性。

FPR (False Positive Rate): Measures how often the orphan-REQ check fires on correct implementations without any hallucination.

FPR（假阳性率）：衡量孤儿 REQ 检查在不含任何幻觉的正确实现上误触发的频率。

4.4 Hallucination Injection Protocol

4.4 幻觉注入协议

Each task in Study 1 had hallucinations deliberately injected into a hallucinated variant of run 1. Study 2 follows the same protocol. Hallucinated lines cite fake REQ IDs (e.g., REQ-099.1.1 for H-SCOPE, REQ-098.1.1 for H-PRIOR, REQ-097.1.1 for H-OVER). None of these fake IDs appear in any legitimate specification. Crucially, all injected hallucinations pass functional test suites—they add code that never breaks existing behavior—confirming that test-based validation alone cannot substitute for citation-based traceability checks.

研究 1 中每个任务都在 run 1 的一个「含幻觉变体」上被刻意注入了幻觉。研究 2 遵循同样的协议。幻觉行引用伪造的 REQ ID（例如 H-SCOPE 用 REQ-099.1.1，H-PRIOR 用 REQ-098.1.1，H-OVER 用 REQ-097.1.1）。这些伪造 ID 都不出现在任何合法规约中。关键在于，所有注入的幻觉都能通过功能测试套件——它们添加的代码从不破坏既有行为——这印证了单靠基于测试的验证无法替代基于引用的可追溯性检查。

4.5 Statistical Methodology

4.5 统计方法

All statistical tests are pre-registered with locked significance criteria. We employ both parametric (paired t-test, two-tailed, α = 0.05) and non-parametric (Wilcoxon signed-rank test) tests, paired on task ID. Effect sizes are reported as Cohen's d [22] (parametric) and Cliff's delta [23] (non-parametric). Confidence intervals are computed via both analytical methods (t-interval) and bootstrap (5,000 resamples). Multiple comparison correction uses the Bonferroni-Holm procedure across all pairwise comparisons. Normality of LSS distributions is assessed via the Shapiro-Wilk test.

所有统计检验均预注册且显著性判据已锁定。我们同时采用参数方法（配对 t 检验，双尾，α = 0.05）与非参数方法（Wilcoxon 符号秩检验），按任务 ID 配对。效应量以 Cohen's d [22]（参数）和 Cliff's delta [23]（非参数）报告。置信区间同时用解析方法（t 区间）和自助法（bootstrap，5,000 次重采样）计算。多重比较校正在所有成对比较上使用 Bonferroni-Holm 程序。LSS 分布的正态性通过 Shapiro-Wilk 检验评估。

The uncited condition is particularly instructive: it uses the identical REQ-format specification as the cited condition, but since no citations appear in the generated code, the orphan-REQ check has nothing to scan. A REQ-format spec without mandatory inline citations gives the same TDR = 0% as any unstructured spec.

无引用条件尤其具有启发性：它使用与带引用条件完全相同的 REQ 格式规约，但由于生成代码中不出现任何引用，孤儿 REQ 检查根本无从扫描。这直接证明了幻觉检测所需要的是生成代码中的标注机制，而不仅仅是规约中存在 REQ ID。一份不强制内联引用的 REQ 格式规约，其 TDR 与任何非结构化规约一样都是 0%。

6.3 False Positive Rate

6.3 假阳性率

The false positive rate is 0.0% across all checks in both studies (Claude: 60 checks across 20 tasks × 3 runs; GLM: 150 checks across 50 tasks × 3 runs). No correct implementation generated a fake or phantom REQ ID. This is critical: a detection mechanism with high TDR but high FPR would generate excessive false alarms that erode developer trust. The combination of 86–88% TDR with 0% FPR makes traceSDD's orphan-REQ check a practical and trustworthy verification tool.

两项研究的所有检查中假阳性率均为 0.0%（Claude：20 个任务 × 3 次运行共 60 次检查；GLM：50 个任务 × 3 次运行共 150 次检查）。没有任何一份正确实现生成了伪造或幻影 REQ ID。这一点至关重要：一个 TDR 高但 FPR 也高的检测机制会产生大量误报，侵蚀开发者的信任。86–88% 的 TDR 配合 0% 的 FPR，使 traceSDD 的孤儿 REQ 检查成为一个实用且可信赖的验证工具。

6.4 Functional Correctness (H3)

6.4 功能正确性（H3）

All conditions achieve 100% TPR across both studies, confirming that citation discipline does not affect functional correctness. The specification methodology alone is not the correctness bottleneck; the bottleneck is the completeness and precision of the specification itself. Any tool that forces the author to be more precise indirectly improves correctness, but the citation requirement itself neither helps nor hurts test-pass rates.

两项研究中所有条件都达到 100% TPR，证实引用纪律不影响功能正确性。规约方法论本身并不是正确性的瓶颈；瓶颈在于规约自身的完备性与精确度。任何迫使作者写得更精确的工具都会间接改善正确性，但引用要求本身对测试通过率既无助益也无损害。

6.5 Per-Task Detection Breakdown (Claude Study)

6.5 逐任务检出细分（Claude 研究）

In the Claude study, 15 of 20 tasks achieved 100% TDR (all hallucinations detected). Tasks T17–T20 showed reduced detection rates (66.7%, 25.0%, 66.7%, 20.0%) because some hallucinations were implemented as uncited nontrivial lines rather than citing fake REQ IDs—the LLM occasionally omitted the citation entirely rather than citing a fake one. This represents a detection gap: the orphan-REQ check catches cited hallucinations but not uncited ones. The GLM study's per-task analysis shows a similar pattern, with the overall TDR slightly higher (88.0%) due to the model's more consistent citation behavior across the larger task suite.

在 Claude 研究中，20 个任务里有 15 个达到 100% TDR（所有幻觉均被检出）。任务 T17–T20 的检出率偏低（66.7%、25.0%、66.7%、20.0%），原因是部分幻觉是以「不带引用的非平凡代码行」形式实现的，而非引用伪造的 REQ ID——LLM 偶尔会干脆省略引用，而不是引用一个假的。这构成一个检测缺口：孤儿 REQ 检查能抓住带引用的幻觉，却抓不住不带引用的。GLM 研究的逐任务分析呈现类似模式，只是总体 TDR 略高（88.0%），得益于该模型在更大任务集上更稳定的引用行为。

7 Discussion

7 讨论

7.1 The Determinism-Detection Trade-off

7.1 确定性与可检测性的权衡

The most important finding of this work is the identification and cross-model replication of a fundamental trade-off in specification-driven LLM code generation. Mandatory inline citations significantly reduce output determinism (mean d = −0.72, p < 0.001 across both models) while simultaneously enabling the only automated hallucination detection mechanism (TDR = 86–88% vs 0% for all alternatives). This trade-off is not a limitation of a specific model or task set—it is a structural property of the citation annotation mechanism itself.

本工作最重要的发现，是识别出规约驱动 LLM 代码生成中的一个根本性权衡，并在跨模型上复现了它。强制内联引用显著降低输出确定性（两个模型上平均 d = −0.72，p < 0.001），却同时使唯一可用的自动化幻觉检测机制成为可能（TDR = 86–88%，其余方案全部为 0%）。这一权衡并非某个特定模型或任务集的局限——它是引用标注机制自身的结构性属性。

The mechanism underlying the determinism reduction is citation placement variability. In each independent LLM session, the model must decide not only what code to write but where to place each citation. Should a function signature cite all REQs it implements, or just the primary one? Should a multi-line conditional cite the REQ once or on each line? These decisions, which have no correct answer, introduce systematic lexical divergence across runs. The uncited condition avoids this entirely: without citations, the LLM focuses solely on code generation, producing more consistent output. The REQ-format specification still provides structural anchoring (explaining why uncited LSS is higher than both baselines), but the citation annotation layer adds noise.

确定性下降背后的机制是引用位置的变异性。在每一次独立的 LLM 会话中，模型不仅要决定写什么代码，还要决定把每个引用放在哪里。函数签名应当引用它实现的全部 REQ，还是只引用主要那一条？跨多行的条件语句应当只引用一次 REQ，还是每行都引用？这些没有标准答案的决策，在多次运行之间引入了系统性的词法分歧。无引用条件完全规避了这一点：没有引用，LLM 就只专注于生成代码，从而产出更一致的结果。REQ 格式规约依然提供结构性锚定（这解释了为什么无引用条件的 LSS 高于两个基线），但引用标注这一层增加了噪声。

Practically, this trade-off is worth accepting in production environments where specification correctness is more critical than lexical consistency. The approximately 0.13–0.21 point LSS reduction is a moderate cost, while the 86–88% automated hallucination detection capability is a unique benefit that no alternative framework can match.

从实践角度看，在规约正确性比词法一致性更关键的生产环境中，这一权衡是值得接受的。约 0.13–0.21 个点的 LSS 下降是中等代价，而 86–88% 的自动化幻觉检测能力则是任何替代框架都无法匹敌的独特收益。

7.2 Cross-Model Consistency

7.2 跨模型一致性

The remarkable consistency of results across Claude Sonnet 4.6 and GLM-5-turbo strengthens our confidence in the findings. These models differ substantially in architecture, training data, and parameter count. Claude is trained with constitutional AI methods emphasizing safety and helpfulness [14, 16], while GLM uses autoregressive bidirectional pre-training [15]. Despite these differences, the citation isolation effect size is nearly identical (d = −0.76 vs d = −0.72), the TDR values are closely matched (86.4% vs 88.0%), and the pattern of significant vs non-significant comparisons is identical across all six pairwise tests. This consistency suggests that the observed effects are driven by the specification framework properties rather than model-specific behaviors.

Claude Sonnet 4.6 与 GLM-5-turbo 之间结果的高度一致性增强了我们对这些发现的信心。这两个模型在架构、训练数据和参数量上都有显著差异。Claude 采用强调安全性与有用性的宪法式 AI 方法训练 [14, 16]，而 GLM 使用自回归双向预训练 [15]。尽管存在这些差异，引用隔离效应量几乎相同（d = −0.76 对比 d = −0.72），TDR 数值高度接近（86.4% 对比 88.0%），且六组成对检验中「显著/不显著」的模式完全一致。这种一致性表明，所观察到的效应是由规约框架属性驱动的，而非模型特有的行为。

7.3 Practical Implications and Recommendations

7.3 实践启示与建议

The findings suggest a three-tier recommendation framework for practitioners. First, for production systems in regulated or high-stakes domains (healthcare, finance, safety-critical), use traceSDD with mandatory citations: the 86–88% automated hallucination detection with 0% false positive rate is a unique capability that justifies the moderate determinism cost. Second, for rapid prototyping where speed matters more than verification, use the uncited approach with a REQ-format specification: you get the structural anchoring benefit (LSS greater than both baselines) without the citation overhead. Third, for teams considering Spec Kit or OpenSpec, our data suggests that Spec Kit's lower determinism (Claude mean 0.460 vs OpenSpec 0.487; GLM mean 0.434 vs 0.480) and complete lack of automated detection make it the weakest choice on the measured dimensions, though its developer experience and natural workflow may compensate in practice.

这些发现给实践者提供了一个三层建议框架。第一，对于受监管或高风险领域（医疗、金融、安全关键）的生产系统，使用带强制引用的 traceSDD：86–88% 的自动化幻觉检测配合 0% 的假阳性率是一项独特能力，足以证明那点中等的确定性代价是值得的。第二，对于速度比验证更重要的快速原型场景，使用配合 REQ 格式规约的无引用方案：你能拿到结构性锚定的收益（LSS 高于两个基线），却无需承担引用开销。第三，对于正在考虑 Spec Kit 或 OpenSpec 的团队，我们的数据表明 Spec Kit 在确定性上更低（Claude 均值 0.460 对比 OpenSpec 0.487；GLM 均值 0.434 对比 0.480）且完全没有自动化检测能力，因而在所测量的维度上是最弱的选择——尽管它的开发者体验和自然的工作流在实践中可能有所弥补。

7.4 Maintenance Posture

7.4 维护姿态

Beyond the metrics measured in this study, traceSDD's inline citations create a live, always-current traceability map. Operations such as grep REQ-003.1.2 src/ find all code touching a specific requirement instantly. This advantage compounds with codebase scale and becomes the dominant maintenance differentiator in production systems with hundreds of requirements. While our study measures this advantage only indirectly (through TDR and FPR), the long-term maintenance implications are substantial.

除了本研究测量的指标之外，traceSDD 的内联引用还构建出一张实时、永远最新的可追溯性映射。像 grep REQ-003.1.2 src/ 这样的操作可以瞬间找出触及某条具体需求的所有代码。这一优势随代码库规模而复利增长，并在拥有数百条需求的生产系统中成为决定性的维护差异点。虽然我们的研究只是间接测量了这一优势（通过 TDR 与 FPR），但其长期维护意义相当可观。

8 Threats to Validity

8 效度威胁

Task scope and language. All implementations use Python and span moderate complexity (50–1,000 lines). Production-scale tasks (5,000+ lines) may show different dynamics, particularly for the citation overhead and hallucination detection scalability. The task suite, while diverse across 8 domains, may not represent all software engineering patterns equally.

任务范围与语言。所有实现都使用 Python，复杂度处于中等区间（50–1,000 行）。生产规模的任务（5,000 行以上）可能呈现不同的动态特性，尤其是在引用开销和幻觉检测的可扩展性方面。任务集虽覆盖 8 个领域，但未必对所有软件工程模式都有同等代表性。

Model scope. While two models provide stronger evidence than single-model studies, they represent only a subset of the LLM landscape. Different models (GPT-4, Gemini, Llama, Mistral) may exhibit different determinism distributions and hallucination rates. The consistency of our findings across two architecturally distinct models is encouraging but not conclusive evidence of universality.

模型范围。虽然两个模型比单模型研究提供了更强的证据，但它们只代表 LLM 版图的一个子集。不同模型（GPT-4、Gemini、Llama、Mistral）可能呈现不同的确定性分布和幻觉率。我们的发现在两个架构迥异的模型上保持一致，这令人鼓舞，但并不构成普适性的确凿证据。

Hallucination injection methodology. Hallucinations are injected with known-fake REQ-099 IDs. Organic hallucinations may be subtler and harder to detect with a simple set-difference check. In particular, a model that omits citations entirely for hallucinated code (rather than citing fake REQ IDs) would bypass the orphan-REQ check. Our Claude data shows this occurs in approximately 12% of hallucination instances (T17–T20), suggesting that the orphan-REQ check should be supplemented with an uncited-line check for maximum coverage.

幻觉注入方法。幻觉是以已知伪造的 REQ-099 类 ID 注入的。自然产生的幻觉可能更隐蔽，用简单的集合差检查更难发现。特别是，若模型对幻觉代码干脆完全省略引用（而非引用伪造 REQ ID），就能绕过孤儿 REQ 检查。我们的 Claude 数据显示这种情况约占幻觉实例的 12%（T17–T20），这表明孤儿 REQ 检查应当辅以「未引用行检查」以获得最大覆盖率。

Metric limitations. LSS measures lexical similarity, which conflates content similarity with formatting and style similarity. We mitigate this by normalizing source code (stripping all comments, blank lines, and whitespace) before comparison, but structural differences (e.g., different algorithmic approaches) still reduce LSS even when the functional output is identical. A complementary metric such as behavioral equivalence testing or abstract syntax tree (AST) similarity would strengthen the determinism analysis in future work.

指标局限。LSS 测量的是词法相似度，它把内容相似性与格式、风格相似性混杂在了一起。我们通过在比较前归一化源码（剥除全部注释、空行和空白）来缓解这一点，但结构性差异（例如采用不同的算法思路）仍会拉低 LSS，即便功能输出完全相同。诸如行为等价性测试或抽象语法树（AST）相似度这类互补指标，将在未来工作中强化确定性分析。

Study 2 sample size for Claude comparison. The Claude study (N=20) was underpowered for some comparisons (e.g., traceSDD vs OpenSpec: d = 0.18, p = 0.44). The GLM study (N=50) provides adequate power for all comparisons. A replication of the Claude study at N=50 would further strengthen cross-model comparisons.

Claude 对比中研究 2 的样本量。Claude 研究（N=20）对某些比较而言功效不足（例如 traceSDD 对比 OpenSpec：d = 0.18，p = 0.44）。GLM 研究（N=50）则为所有比较提供了足够功效。若把 Claude 研究复现到 N=50，将进一步强化跨模型对比。

Cold-start session independence. All three runs per task are independent cold-start LLM sessions with no shared context. However, the underlying model weights are fixed, and models may have implicit biases from training data that create correlated outputs even across independent sessions. This is an inherent limitation of studying a fixed model.

冷启动会话独立性。每个任务的三次运行都是无共享上下文的独立冷启动 LLM 会话。然而底层模型权重是固定的，模型可能带有来自训练数据的隐含偏好，从而即便在独立会话之间也产生相关的输出。这是研究固定模型时固有的局限。

9 Conclusion and Future Work

9 结论与未来工作

This paper presents the first cross-model controlled comparison of specification-driven development framework citation disciplines, conducted across Claude Sonnet 4.6 (20 tasks, 240 implementations) and GLM-5-turbo (50 tasks, 600 implementations). Our four key findings are:

本文给出了首个针对规约驱动开发框架引用纪律的跨模型受控对比，覆盖 Claude Sonnet 4.6（20 个任务、240 份实现）与 GLM-5-turbo（50 个任务、600 份实现）。我们的四项关键发现是：

  1. Citations reduce determinism. Mandatory inline citations significantly reduce output determinism compared to an identical uncited condition (mean d = −0.72, p < 0.001 across both models), establishing that citation annotations introduce rather than absorb lexical variability.
  2. traceSDD outperforms Spec Kit but not OpenSpec on determinism. traceSDD (cited) significantly outperforms Spec Kit (mean d = 0.44, p < 0.01) but not OpenSpec (mean d = 0.16, p = 0.36) across both models.
  3. Cited condition uniquely enables automated hallucination detection. The cited condition achieves 86–88% TDR with 0% FPR across both models, while all three alternatives achieve 0%. The uncited condition—using the identical REQ-format specification—also achieves 0%, proving that detection requires annotations in code, not just structured specifications.
  4. Uncited REQ-format specs provide the best determinism anchor. The uncited condition significantly outperforms both external baselines (mean d = 1.02 vs Spec Kit, mean d = 0.91 vs OpenSpec), confirming that structured REQ-format specifications provide a determinism anchor independent of citation annotations.
  1. 引用会降低确定性。相比完全相同的无引用条件，强制内联引用显著降低输出确定性（两个模型上平均 d = −0.72，p < 0.001），确立了引用标注是引入而非吸收词法变异性。
  2. 在确定性上 traceSDD 胜过 Spec Kit，但不胜过 OpenSpec。两个模型上，traceSDD（带引用）显著优于 Spec Kit（平均 d = 0.44，p < 0.01），但不优于 OpenSpec（平均 d = 0.16，p = 0.36）。
  3. 只有带引用条件能实现自动化幻觉检测。带引用条件在两个模型上都达到 86–88% 的 TDR 与 0% 的 FPR，而其余三个方案全部为 0%。无引用条件——使用完全相同的 REQ 格式规约——同样是 0%，这证明检测所依赖的是代码中的标注，而不仅仅是结构化的规约。
  4. 无引用的 REQ 格式规约提供了最好的确定性锚点。无引用条件显著优于两个外部基线（对 Spec Kit 平均 d = 1.02，对 OpenSpec 平均 d = 0.91），证实结构化的 REQ 格式规约提供了一个独立于引用标注的确定性锚点。

These findings establish that traceSDD makes a principled trade-off: reduced determinism in exchange for automated hallucination detection. The trade-off is worthwhile in production environments where specification correctness is critical, but teams that prioritize determinism should consider the uncited approach with a REQ-format specification.

这些发现确立了 traceSDD 做出的是一个有原则的权衡：以降低确定性换取自动化幻觉检测。在规约正确性至关重要的生产环境中，这一权衡是划算的；但优先考虑确定性的团队，应当考虑配合 REQ 格式规约的无引用方案。

Future work should address several promising directions. First, replication with additional models (GPT-4, Gemini, Llama, Mistral) would further test cross-model generalizability. Second, extending the task suite to production-scale projects (5,000+ lines, multi-module systems) would reveal whether the determinism-detection trade-off scales. Third, hybrid approaches that combine uncited generation for determinism with post-hoc citation analysis for verification could potentially achieve both benefits. Fourth, investigating the interaction between temperature, few-shot prompting, and citation behavior would deepen our understanding of the mechanisms driving these effects. Fifth, longitudinal studies measuring the maintenance cost impact of citation traceability over time would provide the economic justification for adopting citation-disciplined workflows in production environments. Finally, integrating the orphan-REQ check into CI/CD pipelines as an automated quality gate would translate our academic findings into immediate practical impact.

未来工作应从几个有前景的方向展开。第一，用更多模型（GPT-4、Gemini、Llama、Mistral）做复现，将进一步检验跨模型泛化性。第二，把任务集扩展到生产规模项目（5,000 行以上、多模块系统），将揭示确定性-检测权衡是否可扩展。第三，把「用无引用生成保确定性」与「用事后引用分析做验证」结合起来的混合方案，有可能同时拿到两方面收益。第四，考察温度参数、少样本提示与引用行为之间的交互作用，将加深我们对驱动这些效应的机制的理解。第五，纵向研究以测量引用可追溯性随时间推移对维护成本的影响，将为在生产环境中采纳引用纪律工作流提供经济性论证。最后，把孤儿 REQ 检查集成进 CI/CD 流水线作为自动化质量门禁，将把我们的学术发现转化为即时的实践影响。
