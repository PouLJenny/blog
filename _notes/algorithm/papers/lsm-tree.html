Abstract

摘要

High-performance transaction system applications typically insert rows in a History table to provide an activity trace; at the same time the transaction system generates log records for purposes of system recovery. Both types of generated information can benefit from efficient indexing. An example in a well-known setting is the TPC-A benchmark application, modified to support efficient queries on the History for account activity for specific accounts. This requires an index by account-id on the fast-growing History table. Unfortunately, standard disk-based index structures such as the B-tree will effectively double the I/O cost of the transaction to maintain an index such as this in real time, increasing the total system cost up to fifty percent. Clearly a method for maintaining a real-time index at low cost is desirable.

高性能事务处理系统通常需要向 History 表中插入行以提供活动追踪记录；与此同时，事务系统还会生成日志记录用于系统恢复。这两类信息都可以从高效索引中获益。一个典型的例子是经过修改的 TPC-A 基准测试应用，需要支持按特定账户查询 History 表中的账户活动。这要求在快速增长的 History 表上建立按 account-id 的索引。不幸的是，标准的基于磁盘的索引结构（如 B-tree）在实时维护此类索引时实际上会使事务的 I/O 成本翻倍，使总系统成本增加高达 50%。显然，我们需要一种低成本维护实时索引的方法。

The Log-Structured Merge-tree (LSM-tree) is a disk-based data structure designed to provide low-cost indexing for a file experiencing a high rate of record inserts (and deletes) over an extended period. The LSM-tree uses an algorithm that defers and batches index changes, cascading the changes from a memory-based component through one or more disk components in an efficient manner reminiscent of merge sort. During this process all index values are continuously accessible to retrievals (aside from very short locking periods), either through the memory component or one of the disk components. The algorithm has greatly reduced disk arm movements compared to traditional access methods such as B-trees, and will improve cost-performance in domains where disk arm costs for inserts with traditional access methods overwhelm storage media costs.

日志结构合并树（LSM-tree）是一种基于磁盘的数据结构，旨在为长期经历高频记录插入（及删除）的文件提供低成本索引。LSM-tree 使用一种延迟并批量处理索引变更的算法，以类似归并排序的高效方式将变更从内存组件级联传播到一个或多个磁盘组件。在此过程中，所有索引值始终可被检索访问（除了极短的锁定时间段），无论是通过内存组件还是某个磁盘组件。与 B-tree 等传统访问方法相比，该算法大幅减少了磁盘臂移动，在传统访问方法的插入磁盘臂开销超过存储介质成本的应用领域中，能显著改善性价比。

The LSM-tree approach also generalizes to operations other than insert and delete. However, indexed finds requiring immediate response will lose I/O efficiency in some cases, so the LSM-tree is most useful in applications where index inserts are more common than finds that retrieve the entries. This seems to be a common property for History tables and log files. The conclusions of Section 6 compare the hybrid use of memory and disk components in the LSM-tree access method with the commonly understood advantage of the hybrid method to buffer disk pages in memory.

LSM-tree 方法也可推广到插入和删除之外的其他操作。然而，需要立即响应的索引查找在某些情况下会损失 I/O 效率，因此 LSM-tree 最适用于索引插入远多于索引查找的应用场景。这似乎是 History 表和日志文件的普遍特性。第 6 节的结论将 LSM-tree 访问方法中内存和磁盘组件的混合使用，与广为人知的用内存缓冲磁盘页的混合方法优势进行了比较。

1. Introduction

1. 引言

As long-lived transactions in activity flow management systems become commercially available ([10], [11], [12], [20], [24], [27]), there will be increased need to provide indexed access to transactional log records. Traditionally, transactional logging has focused on aborts and recovery, and has required the system to refer back to a relatively short-term history in normal processing with occasional transaction rollback, while recovery was performed using batched sequential reads. However, as systems take on responsibility for more complex activities, the duration and number of events that make up a single long-lived activity will increase to a point where there is sometimes a need to review past transactional steps in real time to remind users of what has been accomplished. At the same time, the total number of active events known to a system will increase to the point where memory-resident data structures now used to keep track of active logs are no longer feasible, notwithstanding the continuing decrease in memory cost to be expected. The need to answer queries about a vast number of past activity logs implies that indexed log access will become more and more important.

随着活动流管理系统中的长寿命事务逐步实现商业化（[10]、[11]、[12]、[20]、[24]、[27]），对事务日志记录进行索引访问的需求将日益增长。传统上，事务日志主要关注中止和恢复，要求系统在正常处理和偶发事务回滚时仅回溯相对短期的历史，而恢复则通过批量顺序读取完成。然而，随着系统承担越来越复杂的活动，构成单个长寿命活动的事件持续时间和数量将增长到一定程度——有时需要实时回顾过去的事务步骤以提醒用户已完成的工作。同时，系统所知的活跃事件总数也将增长到一个程度，使得当前用于跟踪活跃日志的内存驻留数据结构不再可行，尽管内存成本预计将持续下降。需要对海量历史活动日志进行查询这一事实意味着，索引化的日志访问将变得越来越重要。

Even with current transactional systems there is clear value in providing indexing to support queries on history tables with high insert volume. Networking, electronic mail, and other nearly-transactional systems produce huge logs often to the detriment of their host systems. To start from a concrete and well-known example, we explore a modified TPC-A benchmark in the following Examples 1.1 and 1.2. Note that examples presented in this paper deal with specific numeric parametric values for ease of presentation; it is a simple task to generalize these results. Note too that although both history tables and logs involve time-series data, the index entries of the LSM-Tree are not assumed to have identical temporal key order. The only assumption for improved efficiency is high update rates compared to retrieval rates.

即便在当前的事务系统中，为高插入量的 History 表提供索引以支持查询也具有明确的价值。网络、电子邮件及其他准事务系统会产生大量日志，往往对宿主系统造成负担。为了从一个具体且广为人知的例子出发，我们在下面的例 1.1 和例 1.2 中探讨了一个修改过的 TPC-A 基准测试。注意，本文中的示例使用了特定的数值参数以便于表述；将这些结果一般化是很简单的。另需注意，虽然 History 表和日志都涉及时间序列数据，但 LSM-Tree 的索引条目并不假定具有相同的时间键序。改进效率的唯一假设是更新速率远高于检索速率。

The Five Minute Rule

五分钟法则

The following two examples both depend on the Five Minute Rule [13]. This basic result states that we can reduce system costs by purchasing memory buffer space to keep pages in memory, thus avoiding disk I/O, when page reference frequency exceeds about once every 60 seconds. The time period of 60 seconds is approximate, a ratio between the amortized cost for a disk arm providing one I/O per second and memory cost to buffer a disk page of 4 KBytes amortized over one second. In terms of the notation of section 3, the ratio is COSTP/COSTm divided by the page size in Mbytes. Here we are simply trading off disk accesses for memory buffers while the tradeoff gives economic gain. Note that the 60 second time period is expected to grow over the years as memory prices come down faster than disk arms. The reason it is smaller now in 1995 than when defined in 1987 when it was five minutes, is partly technical (different buffering assumptions) and partly due to the intervening introduction of extremely inexpensive mass-produced disks.

以下两个例子都依赖于五分钟法则 [13]。这一基本结论指出：当页面引用频率超过大约每 60 秒一次时，我们可以通过购买内存缓冲空间将页面保留在内存中来降低系统成本，从而避免磁盘 I/O。60 秒这一时间段是近似值，是提供每秒一次 I/O 的磁盘臂摊销成本与缓冲一个 4 KB 磁盘页面的内存摊销成本之比。用第 3 节的符号表示，该比值为 COSTP/COSTm 除以页面大小（MB）。这里我们只是在磁盘访问与内存缓冲之间进行权衡，只要权衡能带来经济收益。注意，60 秒这一时间段预计会随着内存价格比磁盘臂下降更快而逐年增长。它在 1995 年比 1987 年定义时的五分钟要短，部分原因是技术性的（不同的缓冲假设），部分原因是其间引入了极其廉价的量产磁盘。

Example 1.1. Consider the multi-user application envisioned by the TPC-A benchmark [26] running 1000 transactions per second (this rate can be scaled, but we will consider only 1000 TPS in what follows). Each transaction updates a column value, withdrawing an amount Delta from a Balance column, in a randomly chosen row containing 100 bytes, from each of three tables: the Branch table, with 1000 rows, the Teller table with 10,000 rows, and the Account table, with 100,000,000 rows; the transaction then writes a 50 byte row to a History table before committing, with columns: Account-ID, Branch-ID, Teller-ID, Delta, and Timestamp. Accepted calculations projecting disk and memory costs shows that Account table pages will not be memory resident for a number of years to come (see reference [6]), while the Branch and Teller tables should be entirely memory resident now.

例 1.1. 考虑 TPC-A 基准测试 [26] 设想的多用户应用，以每秒 1000 个事务运行（此速率可伸缩，但下文仅考虑 1000 TPS）。每个事务在三张表中各随机选择一行（100 字节），更新其列值，从 Balance 列中扣减金额 Delta：Branch 表有 1000 行，Teller 表有 10,000 行，Account 表有 100,000,000 行；然后在提交前向 History 表写入一行 50 字节的记录，包含列：Account-ID、Branch-ID、Teller-ID、Delta 和 Timestamp。磁盘和内存成本的预测计算表明，Account 表的页面在未来数年内不会常驻内存（见参考文献 [6]），而 Branch 和 Teller 表现在应该完全常驻内存。

Under the assumptions given, repeated references to the same disk page of the Accounts table will be about 2,500 seconds apart, well below the frequency needed to justify buffer residence by the Five Minute rule. Now each transaction requires about two disk I/Os, one to read in the desired Account record (we treat the rare case where the page accessed is already in buffer as insignificant), and one to write out a prior dirty Account page to make space in buffers for a read (necessary for steady-state behavior). Thus 1000 TPS will correspond to about 2000 I/Os per second. This requires 80 disk arms (actuators) at the nominal rate of 25 I/Os per disk-arm-second assumed in [13]. In the 8 years since then (1987 to 1995) the rate has climbed by less than 10%/year so that the nominal rate is now about 40 I/Os per second, or 50 disk arms for 2000 I/Os per second. The cost of disk for the TPC application was calculated to be about half the total cost of the system in [6], although it is somewhat less on IBM mainframe systems. However, the cost for supporting I/O is clearly a growing component of the total system cost as the cost of both memory and CPU drop faster than disk.

在给定假设下，对 Account 表同一磁盘页面的重复引用间隔约为 2500 秒，远低于五分钟法则证明缓冲驻留合理性所需的频率。现在每个事务大约需要两次磁盘 I/O，一次读入所需的 Account 记录（我们将页面已在缓冲中的罕见情况视为可忽略），一次写出先前的脏 Account 页面以腾出缓冲空间（稳态行为所必需）。因此 1000 TPS 对应约 2000 I/O/秒。按 [13] 中假定的每磁盘臂每秒 25 次 I/O 的名义速率，这需要 80 个磁盘臂（执行器）。此后 8 年间（1987 至 1995），该速率以低于每年 10% 的幅度提升，名义速率现约为每秒 40 次 I/O，即 2000 I/O/秒需要 50 个磁盘臂。[6] 中计算出 TPC 应用的磁盘成本约为系统总成本的一半，在 IBM 大型机系统上略低。然而，随着内存和 CPU 成本比磁盘下降更快，支持 I/O 的成本显然是系统总成本中一个不断增长的组成部分。

Example 1.2. Now we consider an index on the high insert volume History table, and demonstrate that such an index essentially doubles the disk cost for the TPC application. An index on "Account-ID concatenated with Timestamp" (Acct-ID||Timestamp) for the History table is crucial to support efficient queries on recent account activity such as: (1.1) Select * from History where History.Acct-ID = %custacctid and History.Timestamp > %custdatetime;

例 1.2. 现在我们考虑对高插入量的 History 表建立索引，并证明这样的索引实质上会使 TPC 应用的磁盘成本翻倍。History 表上"Account-ID 与 Timestamp 连接"（Acct-ID||Timestamp）的索引对于支持高效查询近期账户活动至关重要，例如：(1.1) Select * from History where History.Acct-ID = %custacctid and History.Timestamp > %custdatetime;

If an Acct-ID||Timestamp index is not present, such a query requires a direct search of all rows of the History table, and thus becomes impractical. An index on Acct-ID alone provides most of the benefit, but cost considerations that follow don't change if the Timestamp is left out, so we assume here the more useful concatenated index. What resources are required to maintain such a secondary B-tree index in real time? We see that the entries in the B-tree are generated 1000 per second, and assuming a 20 day period of accumulation, with eight hour days and 16 byte index entries, this implies 576,000,000 entries on 9.2 GBytes of disk, or about 2.3 million pages needed on the index leaf level, even if there is no wasted space. Since transactional Acct-ID values are randomly chosen, each transaction will require at least one page read from this index, and in the steady state a page write as well. By the Five Minute Rule these index pages will not be buffer resident (disk page reads about 2300 seconds apart), so all I/Os are to disk. This addition of 2000 I/Os per second to the 2000 I/Os already needed for updating the Account table, requires a purchase of an additional 50 disk arms, doubling our disk requirements. The figure optimistically assumes that deletes needed to keep the log file index only 20 days in length can be performed as a batch job during slack use times.

如果不存在 Acct-ID||Timestamp 索引，这样的查询就需要直接搜索 History 表的所有行，因而变得不切实际。仅按 Acct-ID 建立索引能提供大部分收益，但后续的成本分析在省略 Timestamp 时不会改变，因此我们假定使用更实用的连接索引。实时维护这样一个二级 B-tree 索引需要什么资源？我们看到 B-tree 中的条目以每秒 1000 条的速率生成，假设累积 20 天（每天 8 小时工作时间），索引条目为 16 字节，则意味着 576,000,000 条条目占用 9.2 GB 磁盘空间，即使没有空间浪费也需要约 230 万个页面用于索引叶级。由于事务的 Acct-ID 值是随机选择的，每个事务至少需要从索引中读取一个页面，在稳态下还需要写出一个页面。根据五分钟法则，这些索引页面不会常驻缓冲（磁盘页面读取间隔约 2300 秒），所以所有 I/O 都指向磁盘。在更新 Account 表已需要的 2000 I/O/秒基础上再增加 2000 I/O/秒，需要额外购买 50 个磁盘臂，使磁盘需求翻倍。该数字乐观地假设保持日志文件索引仅 20 天长度所需的删除操作可以在空闲时段作为批处理作业执行。

We have considered a B-tree for the Acct-ID||Timestamp index on the History file because it is the most common disk-based access method used in commercial systems, and in fact no classical disk indexing structure consistently gives superior I/O cost/performance. We will discuss the considerations that lead us to this conclusion in Section 5.

我们为 History 文件上的 Acct-ID||Timestamp 索引考虑了 B-tree，因为它是商业系统中最常用的基于磁盘的访问方法，而且实际上没有经典的磁盘索引结构能始终提供更优的 I/O 性价比。我们将在第 5 节讨论导致这一结论的考量。

The LSM-tree access method presented in this paper enables us to perform the frequent index inserts for the Account-ID||Timestamp index with much less disk arm use, therefore at an order of magnitude lower cost. The LSM-tree uses an algorithm that defers and batches index changes, migrating the changes out to disk in a particularly efficient way reminiscent of merge sort. As we shall see in Section 5, the function of deferring index entry placement to an ultimate disk position is of fundamental importance, and in the general LSM-tree case there is a cascaded series of such deferred placements. The LSM-tree structure also supports other operations of indexing such as deletes, updates, and even long latency find operations with the same deferred efficiency. Only finds that require immediate response remain relatively costly.

本文提出的 LSM-tree 访问方法使我们能够以远少的磁盘臂使用量完成 Account-ID||Timestamp 索引的频繁插入，因此成本降低了一个数量级。LSM-tree 使用一种延迟并批量处理索引变更的算法，以类似归并排序的特别高效方式将变更迁移到磁盘。正如我们在第 5 节将看到的，将索引条目放置延迟到最终磁盘位置的功能具有根本重要性，在一般的 LSM-tree 情况下存在一系列级联的延迟放置。LSM-tree 结构还支持其他索引操作，如删除、更新甚至长延迟查找操作，均具有相同的延迟效率。只有需要立即响应的查找仍然相对昂贵。

A major area of effective use for the LSM-tree is in applications such as Example 1.2 where retrieval is much less frequent than insert (most people don't ask for recent account activity nearly as often as they write a check or make a deposit). In such a situation, reducing the cost of index inserts is of paramount importance; at the same time, find access is frequent enough that an index of some kind must be maintained, because a sequential search through all the records is out of the question.

LSM-tree 的主要高效应用领域是如例 1.2 这样检索远少于插入的应用（大多数人查询近期账户活动的频率远低于开支票或存款的频率）。在这种情况下，降低索引插入成本至关重要；同时，查找访问又足够频繁，必须维护某种索引，因为对所有记录的顺序搜索是不可接受的。

2. The Two Component LSM-Tree Algorithm

2. 两组件 LSM-Tree 算法

An LSM-tree is composed of two or more tree-like component data structures. We deal in this Section with the simple two component case and assume in what follows that LSM-tree is indexing rows in a History table as in Example 1.2. See Figure 2.1, below.

LSM-tree 由两个或更多树状组件数据结构组成。本节处理简单的两组件情况，并假设 LSM-tree 正在为如例 1.2 中的 History 表行建立索引。参见下面的图 2.1。

A two component LSM-tree has a smaller component which is entirely memory resident, known as the C0 tree (or C0 component), and a larger component which is resident on disk, known as the C1 tree (or C1 component). Although the C1 component is disk resident, frequently referenced page nodes in C1 will remain in memory buffers as usual (buffers not shown), so that popular high level directory nodes of C1 can be counted on to be memory resident.

两组件 LSM-tree 包含一个完全常驻内存的较小组件，称为 C0 树（或 C0 组件），以及一个驻留在磁盘上的较大组件，称为 C1 树（或 C1 组件）。尽管 C1 组件驻留在磁盘上，但 C1 中经常被引用的页面节点将照常留在内存缓冲区中（缓冲区未在图中显示），因此 C1 的高层目录节点可以被认为常驻内存。

Figure 2.1. Schematic picture of an LSM-tree of two components.
图 2.1. 两组件 LSM-tree 的示意图。

As each new History row is generated, a log record to recover this insert is first written to the sequential log file in the usual way. The index entry for the History row is then inserted into the memory resident C0 tree, after which it will in time migrate out to the C1 tree on disk; any search for an index entry will look first in C0 and then in C1. There is a certain amount of latency (delay) before entries in the C0 tree migrate out to the disk resident C1 tree, implying a need for recovery of index entries that don't get out to disk prior to a crash. Recovery is discussed in Section 4, but for now we simply note that the log records that allow us to recover new inserts of History rows can be treated as logical logs; during recovery we can reconstruct the History rows that have been inserted and simultaneously recreate any needed entries to index these rows to recapture the lost content of C0.

每当生成新的 History 行时，首先按通常方式将用于恢复此插入的日志记录写入顺序日志文件。然后将该 History 行的索引条目插入到内存常驻的 C0 树中，之后它将逐渐迁移到磁盘上的 C1 树；对索引条目的任何搜索都会先查找 C0，再查找 C1。C0 树中的条目迁移到磁盘常驻的 C1 树之前存在一定的延迟，这意味着需要恢复在崩溃前未能写入磁盘的索引条目。恢复将在第 4 节讨论，但现在我们只需注意，允许我们恢复 History 行新插入的日志记录可以被当作逻辑日志处理；在恢复过程中，我们可以重建已插入的 History 行，同时重建为这些行建立索引所需的条目，以恢复 C0 丢失的内容。

The operation of inserting an index entry into the memory resident C0 tree has no I/O cost. However, the cost of memory capacity to house the C0 component is high compared to disk, and this imposes a limit on its size. We need an efficient way to migrate entries out to the C1 tree that resides on the lower cost disk medium. To achieve this, whenever the C0 tree as a result of an insert reaches a threshold size near the maximum allotted, an ongoing rolling merge process serves to delete some contiguous segment of entries from the C0 tree and merge it into the C1 tree on disk. Figure 2.2 depicts a conceptual picture of the rolling merge process.

向内存常驻的 C0 树插入索引条目没有 I/O 开销。然而，容纳 C0 组件的内存容量成本相对于磁盘很高，这对其大小施加了限制。我们需要一种高效的方式将条目迁移到位于低成本磁盘介质上的 C1 树。为此，每当 C0 树因插入而达到接近最大分配量的阈值大小时，一个持续进行的滚动合并过程会从 C0 树中删除某段连续的条目并将其合并到磁盘上的 C1 树中。图 2.2 描绘了滚动合并过程的概念图。

The C1 tree has a comparable directory structure to a B-tree, but is optimized for sequential disk access, with nodes 100% full, and sequences of single-page nodes on each level below the root packed together in contiguous multi-page disk blocks for efficient arm use; this optimization was also used in the SB-tree [21]. Multi-page block I/O is used during the rolling merge and for long range retrievals, while single-page nodes are used for matching indexed finds to minimize buffering requirements. Multi-page block sizes of 256 KBytes are envisioned to contain nodes below the root; the root node is always a single page by definition.

C1 树具有与 B-tree 类似的目录结构，但针对顺序磁盘访问进行了优化：节点 100% 填满，根节点以下每层的单页节点序列被打包在连续的多页磁盘块中以高效利用磁盘臂；这种优化也在 SB-tree [21] 中使用。滚动合并和长范围检索使用多页块 I/O，而匹配索引查找使用单页节点以最小化缓冲需求。多页块大小设定为 256 KB 以容纳根节点以下的节点；根节点按定义始终为单页。

The rolling merge acts in a series of merge steps. A read of a multi-page block containing leaf nodes of the C1 tree makes a range of entries in C1 buffer resident. Each merge step then reads a disk page sized leaf node of the C1 tree buffered in this block, merges entries from the leaf node with entries taken from the leaf level of the C0 tree, thus decreasing the size of C0, and creates a newly merged leaf node of the C1 tree.

滚动合并以一系列合并步骤进行。读取包含 C1 树叶节点的多页块使 C1 中一个范围的条目常驻缓冲。每个合并步骤读取缓冲在此块中的一个磁盘页大小的 C1 树叶节点，将叶节点中的条目与取自 C0 树叶级的条目合并，从而减小 C0 的大小，并创建新合并的 C1 树叶节点。

The buffered multi-page block containing old C1 tree nodes prior to merge is called the emptying block, and new leaf nodes are written to a different buffered multi-page block called the filling block. When this filling block has been packed full with newly merged leaf nodes of C1, the block is written to a new free area on disk. The new multi-page block containing merged results is pictured in Figure 2.2 as lying on the right of the former nodes. Subsequent merge steps bring together increasing index value segments of the C0 and C1 components until the maximum values are reached and the rolling merge starts again from the smallest values.

包含合并前旧 C1 树节点的缓冲多页块称为排空块，新叶节点写入另一个称为填充块的缓冲多页块。当填充块被新合并的 C1 叶节点装满时，该块被写入磁盘上的新空闲区域。包含合并结果的新多页块在图 2.2 中显示为位于先前节点的右侧。后续合并步骤汇合 C0 和 C1 组件中索引值递增的段，直到达到最大值，然后滚动合并从最小值重新开始。

Newly merged blocks are written to new disk positions, so that the old blocks will not be overwritten and will be available for recovery in case of a crash. The parent directory nodes in C1, also buffered in memory, are updated to reflect this new leaf structure, but usually remain in buffer for longer periods to minimize I/O; the old leaf nodes from the C1 component are invalidated after the merge step is complete and are then deleted from the C1 directory. In general, there will be leftover leaf-level entries for the merged C1 component following each merge step, since a merge step is unlikely to result in a new node just as the old leaf node empties. The same consideration holds for multi-page blocks, since in general when the filling block has filled with newly merged nodes, there will be numerous nodes containing entries still in the shrinking block. These leftover entries, as well as updated directory node information, remain in block memory buffers for a time without being written to disk. Techniques to provide concurrency during the merge step and recovery from lost memory during a crash are covered in detail in Section 4. To reduce reconstruction time in recovery, checkpoints of the merge process are taken periodically, forcing all buffered information to disk.

新合并的块被写入新的磁盘位置，使得旧块不会被覆盖，在崩溃时可用于恢复。C1 中的父目录节点也缓冲在内存中，被更新以反映新的叶结构，但通常在缓冲中保留更长时间以最小化 I/O；C1 组件中的旧叶节点在合并步骤完成后被无效化，然后从 C1 目录中删除。一般来说，每个合并步骤后合并的 C1 组件会有遗留的叶级条目，因为合并步骤不太可能恰好在旧叶节点清空时产生一个新节点。多页块也有同样的考虑，因为通常当填充块装满新合并的节点时，收缩块中仍有大量包含条目的节点。这些遗留条目以及更新的目录节点信息暂时保留在块内存缓冲中，不写入磁盘。在合并步骤期间提供并发性以及从崩溃期间丢失的内存中恢复的技术在第 4 节详细介绍。为减少恢复时的重建时间，定期对合并过程进行检查点，将所有缓冲信息强制写入磁盘。

2.1 How a Two Component LSM-tree Grows

2.1 两组件 LSM-tree 的成长过程

To trace the metamorphosis of an LSM-tree from the beginning of its growth, let us begin with a first insertion to the C0 tree component in memory. Unlike the C1 tree, the C0 tree is not expected to have a B-tree-like structure. For one thing, the nodes could be any size: there is no need to insist on disk page size nodes since the C0 tree never sits on disk, and so we need not sacrifice CPU efficiency to minimize depth. Thus a (2-3) tree or AVL-tree (as explained, for example, in [1]) are possible alternative structures for a C0 tree. When the growing C0 tree first reaches its threshold size, a leftmost sequence of entries is deleted from the C0 tree (this should be done in an efficient batch manner rather than one entry at a time) and reorganized into a C1 tree leaf node packed 100% full. Successive leaf nodes are placed left-to-right in the initial pages of a buffer resident multi-page block until the block is full; then this block is written out to disk to become the first part of the C1 tree disk-resident leaf level. A directory node structure for the C1 tree is created in memory buffers as successive leaf nodes are added, with details explained below.

为了追踪 LSM-tree 从初始生长开始的演变过程，我们从第一次向内存中的 C0 树组件插入开始。与 C1 树不同，C0 树不必具有类似 B-tree 的结构。一方面，节点可以是任意大小：由于 C0 树永远不会位于磁盘上，因此没有必要坚持使用磁盘页大小的节点，也就不必为最小化深度而牺牲 CPU 效率。因此 (2-3) 树或 AVL 树（如 [1] 中所述）都是 C0 树的可选结构。当成长中的 C0 树首次达到其阈值大小时，从 C0 树中删除最左侧的一段连续条目（应以高效的批量方式而非逐条进行），并重组为 100% 填满的 C1 树叶节点。连续的叶节点从左到右放置在缓冲常驻多页块的初始页面中，直到该块被填满；然后将此块写出到磁盘，成为 C1 树磁盘常驻叶级的第一部分。随着连续叶节点的添加，在内存缓冲中创建 C1 树的目录节点结构，细节如下所述。

Successive multi-page blocks of the C1 tree leaf level in ever increasing key-sequence order are written out to disk to keep the C0 tree threshold size from exceeding its threshold. Upper level C1 tree directory nodes are maintained in separate multi-page block buffers, or else in single page buffers, whichever makes more sense from a standpoint of total memory and disk arm cost; entries in these directory nodes contain separators that channel access to individual single-page nodes below, as in a B-tree. The intention is to provide efficient exact-match access along a path of single page index nodes down to the leaf level, avoiding multi-page block reads in such a case to minimize memory buffer requirements. Thus we read and write multi-page blocks for the rolling merge or for long range retrievals, and single-page nodes for indexed find (exact-match) access. C1 directory nodes are forced to new positions on disk when: (a) A multi-page block buffer containing directory nodes becomes full; (b) The root node splits, increasing the depth of the C1 tree (to a depth greater than two); (c) A checkpoint is performed. In the first case, the single multi-page block which has filled is written out to disk. In the latter two cases, all multi-page block buffers and directory node buffers are flushed to disk.

C1 树叶级的连续多页块以不断递增的键序写出到磁盘，以防止 C0 树超过其阈值大小。上层 C1 树目录节点维护在单独的多页块缓冲中，或者维护在单页缓冲中，取决于从总内存和磁盘臂成本的角度哪种更合理；这些目录节点中的条目包含分隔符，将访问引导到下层的各个单页节点，就像 B-tree 一样。目的是提供沿单页索引节点路径到叶级的高效精确匹配访问，在这种情况下避免多页块读取以最小化内存缓冲需求。因此我们为滚动合并或长范围检索读写多页块，为索引查找（精确匹配）访问读写单页节点。C1 目录节点在以下情况被强制写入磁盘新位置：(a) 包含目录节点的多页块缓冲满了；(b) 根节点分裂，增加 C1 树深度（大于二）；(c) 执行检查点。在情况 (a) 中，已满的单个多页块被写出到磁盘。在后两种情况中，所有多页块缓冲和目录节点缓冲都被刷新到磁盘。

After the rightmost leaf entry of the C0 tree is written out to the C1 tree for the first time, the process starts over on the left end of the two trees, except that now and with successive passes multi-page leaf-level blocks of the C1 tree must be read into buffer and merged with the entries in the C0 tree, thus creating new multi-page leaf blocks of C1 to be written to disk.

在 C0 树的最右侧叶条目首次写出到 C1 树之后，过程从两棵树的左端重新开始，不同的是现在以及在后续的遍历中，C1 树的多页叶级块必须被读入缓冲并与 C0 树中的条目合并，从而创建新的 C1 多页叶块写入磁盘。

Once the merge starts, the situation is more complex. We picture the rolling merge process in a two component LSM-tree as having a conceptual cursor which slowly circulates in quantized steps through equal key values of the C0 tree and C1 tree components, drawing indexing data out from the C0 tree to the C1 tree on disk. The rolling merge cursor has a position at the leaf level of the C1 tree and within each higher directory level as well. At each level, all currently merging multi-page blocks of the C1 tree will in general be split into two blocks: the "emptying" block whose entries have been depleted but which retains information not yet reached by the merge cursor, and the "filling" block which reflects the result of the merge up to this moment. There will be an analogous "filling node" and "emptying node" defining the cursor which will certainly be buffer resident. For concurrent access purposes, both the emptying block and the filling block on each level contain an integral number of page-sized nodes of the C1 tree, which simply happen to be buffer resident. (During the merge step that restructures individual nodes, other types of concurrent access to the entries on those nodes are blocked.)

一旦合并开始，情况就更加复杂。我们将两组件 LSM-tree 中的滚动合并过程想象为拥有一个概念性游标，它以量化步骤缓慢地在 C0 树和 C1 树组件的相同键值之间循环，将索引数据从 C0 树抽取到磁盘上的 C1 树。滚动合并游标在 C1 树的叶级以及每个更高的目录级别都有一个位置。在每个层级上，C1 树中所有当前正在合并的多页块通常会被分为两个块："排空"块——其条目已被消耗但保留着合并游标尚未到达的信息，以及"填充"块——反映到目前为止的合并结果。还会有类似的"填充节点"和"排空节点"定义游标位置，它们必然常驻缓冲。为并发访问目的，每层上的排空块和填充块都包含整数个页面大小的 C1 树节点，只是碰巧常驻缓冲。（在重构单个节点的合并步骤期间，对这些节点上条目的其他类型并发访问会被阻塞。）

Whenever a complete flush of all buffered nodes to disk is required, all buffered information at each level must be written to new positions on disk (with positions reflected in superior directory information, and a sequential log entry for recovery purposes). At a later point, when the filling block in buffer on some level of the C1 tree fills and must be flushed again, it goes to a new position. Old information that might still be needed during recovery is never overwritten on disk, only invalidated as new writes succeed with more up-to-date information.

每当需要将所有缓冲节点完全刷新到磁盘时，每个层级的所有缓冲信息必须写入磁盘上的新位置（位置反映在上级目录信息中，并有顺序日志条目用于恢复目的）。稍后，当 C1 树某层级缓冲中的填充块被填满并需要再次刷新时，它会写入新位置。在恢复期间可能仍需要的旧信息永远不会在磁盘上被覆盖，仅在更新的写入成功后被无效化。

It is an important efficiency consideration of the LSM-tree that when the rolling merge process on a particular level of the C1 tree passes through nodes at a relatively high rate, all reads and writes are in multi-page blocks. By eliminating seek time and rotational latency, we expect to gain a large advantage over random page I/O involved in normal B-tree entry insertion. (This advantage is analyzed below, in Section 3.2.) The idea of always writing multi-page blocks to new locations was inspired by the Log-Structured File System devised by Rosenblum and Ousterhout [23], from which the Log-Structured Merge-tree takes its name. Note that the continuous use of new disk space for fresh multi-page block writes implies that the area of disk being written will wrap, and old discarded blocks must be reused. This bookkeeping can be done in a memory table; old multi-page blocks are invalidated and reused as single units, and recovery is guaranteed by the checkpoint. In the Log-Structured File System, the reuse of old blocks involves significant I/O because blocks are typically only partially freed up, so reuse requires a block read and block write. In the LSM-Tree, blocks are totally freed up on the trailing edge of the rolling merge, so no extra I/O is involved.

LSM-tree 的一个重要效率考量是：当滚动合并过程以相对较高的速率通过 C1 树某层级的节点时，所有读写都以多页块进行。通过消除寻道时间和旋转延迟，我们预期相对于正常 B-tree 条目插入所涉及的随机页面 I/O 获得巨大优势。（此优势在下面的第 3.2 节中分析。）始终将多页块写入新位置的思想受到 Rosenblum 和 Ousterhout [23] 设计的日志结构文件系统的启发，日志结构合并树也因此得名。注意，持续使用新磁盘空间进行多页块写入意味着磁盘上被写入的区域会环绕，旧的已废弃块必须被重用。这种簿记可以在内存表中完成；旧的多页块作为整体单元被无效化和重用，恢复由检查点保证。在日志结构文件系统中，旧块的重用涉及大量 I/O，因为块通常只被部分释放，重用需要一次块读和一次块写。在 LSM-Tree 中，块在滚动合并的尾端被完全释放，因此不涉及额外的 I/O。

2.2 Finds in the LSM-tree Index

2.2 LSM-tree 索引中的查找

When an exact-match find or range find requiring immediate response is performed through the LSM-tree index, first the C0 tree and then the C1 tree is searched for the value or values desired. This may imply a slight CPU overhead compared to the B-tree case, since two directories may need to be searched. In LSM-trees with more than two components, there may also be an I/O overhead. To anticipate Chapter 3 somewhat, we define a multi component LSM-tree as having components C0, C1, C2, ..., CK-1 and CK, indexed tree structures of increasing size, where C0 is memory resident and all other components are disk resident. There are asynchronous rolling merge processes in train between all component pairs (Ci-1, Ci) that move entries out from the smaller to the larger component each time the smaller component, Ci-1, exceeds its threshold size. As a rule, in order to guarantee that all entries in the LSM-tree have been examined, it is necessary for an exact-match find or range find to access each component Ci through its index structure. However, there are a number of possible optimizations where this search can be limited to an initial subset of the components.

当通过 LSM-tree 索引执行需要立即响应的精确匹配查找或范围查找时，首先搜索 C0 树，然后搜索 C1 树以查找所需的值。与 B-tree 情况相比，这可能意味着轻微的 CPU 开销，因为可能需要搜索两个目录。在多于两个组件的 LSM-tree 中，还可能有 I/O 开销。为了稍稍预告第 3 章，我们定义多组件 LSM-tree 具有组件 C0、C1、C2、...、CK-1 和 CK，它们是大小递增的索引树结构，其中 C0 常驻内存，所有其他组件驻留在磁盘上。在所有组件对 (Ci-1, Ci) 之间存在异步的滚动合并过程，每当较小的组件 Ci-1 超过其阈值大小时，就将条目从较小组件移出到较大组件。通常，为保证 LSM-tree 中的所有条目都被检查，精确匹配查找或范围查找需要通过其索引结构访问每个组件 Ci。然而，存在若干可能的优化，可以将搜索限制在组件的初始子集中。

First, where unique index values are guaranteed by the logic of generation, as when timestamps are guaranteed to be distinct, a matching indexed find is complete if it locates the desired value in an early Ci component. As another example, we could limit our search when the find criterion uses recent timestamp values so that the entries sought could not yet have migrated out to the largest components. As the merge cursor circulates through the (Ci, Ci+1) pairs, we will often have reason to retain entries in Ci that have been inserted in the recent past (in the last τi seconds), allowing only the older entries to go out to Ci+1. In cases where the most frequent find references are to recently inserted values, many finds can be completed in the C0 tree, and so the C0 tree fulfills a valuable memory buffering function. This point was made also in [23], and represents an important efficiency consideration. For example, indexes to short-term transaction UNDO logs accessed in the event of an abort will have a large proportion of accesses in a relatively short time-span after creation, and we can expect most of these indexes to remain memory resident. By keeping track of the start-time for each transaction we can guarantee that all logs for a transaction started in the last τ0 seconds, for example, will be found in component C0, without recourse to disk components.

首先，当索引值的唯一性由生成逻辑保证时（如时间戳保证不重复），匹配的索引查找只要在较早的 Ci 组件中找到所需值即可完成。另一个例子是，当查找条件使用近期时间戳值时，我们可以限制搜索范围，因为所查找的条目尚不可能迁移到最大的组件中。当合并游标在 (Ci, Ci+1) 对之间循环时，我们通常有理由在 Ci 中保留最近插入的条目（在最近 τi 秒内），只让较旧的条目迁移到 Ci+1。当最频繁的查找引用指向最近插入的值时，许多查找可以在 C0 树中完成，因此 C0 树发挥了宝贵的内存缓冲功能。[23] 中也提出了这一点，它代表了一个重要的效率考量。例如，在中止事件中访问的短期事务 UNDO 日志的索引，大部分访问将集中在创建后相对较短的时间段内，我们可以预期大多数这类索引保持在内存中。通过跟踪每个事务的开始时间，我们可以保证在最近 τ0 秒内开始的事务的所有日志都将在组件 C0 中找到，无需访问磁盘组件。

2.3 Deletes, Updates and Long-Latency Finds in the LSM-tree

2.3 LSM-tree 中的删除、更新与长延迟查找

We note that deletes can share with inserts the valuable properties of deferral and batching. When an indexed row is deleted, if a key value entry is not found in the appropriate position in the C0 tree, a delete node entry can be placed in that position, also indexed by the key value, but noting an entry Row ID (RID) to delete. The actual delete can be done at a later time during the rolling merge process, when the actual index entry is encountered: we say the delete node entry migrates out to larger components during merge and annihilates the associated entry when it is encountered. In the meantime, find requests must be filtered through delete node entries so as to avoid returning references to deleted records. This filtering is easily performed during the search for the relevant keyvalue, since the delete node entry will be located in the appropriate keyvalue position of an earlier component than the entry itself, and in many cases this filter will reduce the overhead of determining an entry is deleted. Updates of records that cause changes to indexed values are unusual in any kind of applications, but such updates can be handled by LSM-trees in a deferred manner if we view an update as a delete followed by an insert.

我们注意到删除可以与插入共享延迟和批处理的宝贵特性。当删除一个已索引的行时，如果在 C0 树的适当位置未找到键值条目，可以在该位置放置一个删除节点条目，同样按键值索引，但标注要删除的行 ID（RID）。实际删除可以在稍后的滚动合并过程中完成，当遇到实际的索引条目时：我们说删除节点条目在合并期间迁移到更大的组件，并在遇到关联条目时将其湮灭。在此期间，查找请求必须通过删除节点条目进行过滤，以避免返回对已删除记录的引用。这种过滤在搜索相关键值期间很容易执行，因为删除节点条目将位于比条目本身更早的组件的适当键值位置中，在许多情况下，这种过滤将减少确定条目是否已删除的开销。导致索引值变更的记录更新在任何应用中都很少见，但如果我们将更新视为删除后跟插入，LSM-tree 可以以延迟方式处理此类更新。

We sketch another type of operation for efficient index modification. A process known as predicate deletion provides a means of performing batch deletes by simply asserting a predicate, for example the predicate that all index values with timestamps more than 20 days old are to be deleted. When the affected entries in the oldest (largest) component become resident during the normal course of the rolling merge, this assertion causes them simply to be dropped during the merge process. Yet another type of operation, a long-latency find, provides an efficient means of responding to a query where the results can wait for the circulation period of the slowest cursor. A find note entry is inserted in component C0, and the find is actually performed over an extended period of time as it migrates out to later components. Once the find note entry has circulated out to the appropriate region of the largest relevant component of the LSM-tree, the accumulated list of RIDs for the long-latency find is complete.

我们概述另一类用于高效索引修改的操作。一种称为谓词删除的过程提供了通过简单断言谓词来执行批量删除的方法，例如断言所有时间戳超过 20 天的索引值都应被删除。当受影响的条目在最老的（最大的）组件中在滚动合并的正常过程中变为常驻时，此断言使它们在合并过程中被直接丢弃。另一种操作——长延迟查找——提供了一种高效方式来响应结果可以等待最慢游标循环周期的查询。一个查找标注条目被插入组件 C0 中，查找实际上在延长的时间段内执行，随着它迁移到后续组件。一旦查找标注条目循环到 LSM-tree 最大相关组件的适当区域，长延迟查找的累积 RID 列表即告完成。

3. Cost-Performance and the Multi-Component LSM-Tree

3. 性价比与多组件 LSM-Tree

In this section we analyze the cost-performance of an LSM-tree, starting with an LSM-tree of two components. We analyze the LSM-tree by analogy with a B-tree providing the same indexing capabilities, comparing the I/O resources utilized for a high volume of new insertions. As we will argue in Section 5, other disk-based access methods are comparable to the B-tree in I/O cost for inserts of new index entries. The most important reason for the comparison of the LSM-tree and B-tree that we perform here is that these two structures are easily comparable, both containing an entry for each row indexed in collation sequence at a leaf level, with upper level directory information that channels access along a path of page-sized nodes. The analysis of I/O advantage for new entry inserts to the LSM-tree is effectively illustrated by analogy to the less efficient but well understood behavior of the B-tree.

本节分析 LSM-tree 的性价比，从两组件 LSM-tree 开始。我们通过与提供相同索引能力的 B-tree 进行类比来分析 LSM-tree，比较高频新插入所使用的 I/O 资源。正如我们在第 5 节将论证的，其他基于磁盘的访问方法在新索引条目的插入 I/O 成本方面与 B-tree 相当。我们在此进行 LSM-tree 与 B-tree 比较的最重要原因是这两种结构容易比较，两者都在叶级按排序序列为每个被索引的行包含一个条目，上层目录信息沿页面大小节点的路径引导访问。LSM-tree 新条目插入的 I/O 优势通过与效率较低但广为人知的 B-tree 行为的类比得到有效说明。

In Section 3.2 following, we compare the I/O insert costs and demonstrate that the small ratio of cost for an LSM-tree of two components to that of a B-tree is a product of two factors. The first factor, COSTπ/COSTP, corresponds to the advantage gained in the LSM-tree by performing all I/O in multi-page blocks, thus utilizing disk arms much more efficiently by saving a great deal of seek and rotational latency time. The COSTπ term represents the disk arm cost of reading or writing a page on disk as part of a multi-page block, and COSTP represents the cost of reading or writing a page at random. The second factor that determines I/O cost ratio between the LSM-tree and the B-tree is given as 1/M, representing the batching efficiency to be gained during a merge step. M is the average number of entries merged from C0 into a page-sized leaf node of C1. Inserting multiple entries per leaf is an advantage over a (large) B-tree where each entry inserted normally requires two I/Os to read and write the leaf node on which it resides. Because of the Five minute rule, it is unlikely in Example 1.2 that a leaf page read in from a B-tree will be re-referenced for a second insert during the short time it remains in buffer. Thus there is no batching effect in a B-tree index. In an LSM-tree however, there will be an important batching effect as long as the C0 component is sufficiently large in comparison to the C1 component.

在随后的第 3.2 节中，我们比较 I/O 插入成本，并证明两组件 LSM-tree 相对于 B-tree 的成本小比值是两个因子的乘积。第一个因子 COSTπ/COSTP 对应于 LSM-tree 通过以多页块执行所有 I/O 而获得的优势，通过节省大量寻道时间和旋转延迟来更高效地利用磁盘臂。COSTπ 项代表作为多页块一部分读写磁盘上一个页面的磁盘臂成本，COSTP 代表随机读写一个页面的成本。决定 LSM-tree 与 B-tree 之间 I/O 成本比的第二个因子为 1/M，代表合并步骤中获得的批处理效率。M 是从 C0 合并到 C1 页大小叶节点的平均条目数。每个叶中插入多条目比每次插入通常需要两次 I/O 来读写叶节点的（大型）B-tree 具有优势。由于五分钟法则，在例 1.2 中，从 B-tree 读入的叶页面在其保留在缓冲的短暂时间内不太可能被第二次插入重新引用。因此 B-tree 索引中没有批处理效应。然而在 LSM-tree 中，只要 C0 组件相对于 C1 组件足够大，就会有重要的批处理效应。

The factor COSTπ/COSTP corresponding to the ratio of efficiency of multi-page block over single page I/O is a constant, and we can do nothing with the LSM-tree structure to have any effect on it. However the batching efficiency 1/M of a merge step is proportional to the ratio in size between the C0 and the C1 components; the larger the C0 component in comparison to the C1 component, the more efficiency is gained in the merge. Up to a certain point, this means that we can save additional money on disk arm cost by using a larger C0 component, but this entails a larger memory cost to contain the C0 component. There is an optimal mix of sizes to minimize the total cost of disk arms and memory capacity, but the solution can be quite expensive in terms of memory for a large C0. It is this consideration that motivates the need for a multi-component LSM-tree, which is investigated in Section 3.3.

对应于多页块与单页 I/O 效率比的因子 COSTπ/COSTP 是常数，我们无法通过 LSM-tree 结构对其施加任何影响。然而合并步骤的批处理效率 1/M 与 C0 和 C1 组件之间的大小比成正比；C0 组件相对于 C1 组件越大，合并获得的效率越高。在一定程度上，这意味着我们可以通过使用更大的 C0 组件来节省额外的磁盘臂成本，但这需要更大的内存成本来容纳 C0 组件。存在最小化磁盘臂和内存容量总成本的最优大小组合，但对于较大的 C0 来说，内存方面的解决方案可能相当昂贵。正是这一考虑引出了多组件 LSM-tree 的需要，将在第 3.3 节研究。

3.1 The Disk Model

3.1 磁盘模型

The advantage of the LSM-tree over the B-tree lies mainly in the area of reduced cost for I/O (although disk components that are 100% full offer a capacity cost advantage as well over other known flexible disk structures). Part of this I/O cost advantage for the LSM-tree is the fact that a page I/O can be amortized along with many other pages of a multi-page block.

LSM-tree 相对于 B-tree 的优势主要在于降低的 I/O 成本（尽管 100% 填满的磁盘组件在容量成本方面也比其他已知的灵活磁盘结构具有优势）。LSM-tree I/O 成本优势的一部分在于页面 I/O 可以与多页块中的许多其他页面一起摊销。

Definition 3.1.1. I/O Costs and Data Temperature. As we store data of a particular kind on disk, rows in a table or entries in an index, we find that as we increase the amount of data stored, the disk arms see more and more utilization under normal use in a given application environment. We are paying for two things when we buy a disk: first, disk capacity, and second, disk I/O rate. Usually one of these two will be a limiting factor in any kind of use. If capacity is the limiting factor, we will fill up the disks and find that the disk arms are only fractionally utilized; on the other hand we may find that as we add data the disk arms reach their full utilization rate when the disk is only fractionally full, and this means that the I/O rate is the limiting factor.

定义 3.1.1. I/O 成本与数据温度。 当我们在磁盘上存储特定类型的数据（表中的行或索引中的条目）时，我们发现随着存储数据量的增加，在给定应用环境的正常使用下，磁盘臂的利用率越来越高。购买磁盘时我们为两样东西付费：第一，磁盘容量；第二，磁盘 I/O 速率。在任何使用方式中，这两者之一通常是限制因素。如果容量是限制因素，我们会填满磁盘并发现磁盘臂仅被部分利用；另一方面，我们可能发现随着添加数据，当磁盘仅被部分填满时磁盘臂就达到了满负荷利用率，这意味着 I/O 速率是限制因素。

A random page I/O during peak use has a cost, COSTP, which is based on a fair rent for the disk arm, whereas the cost of a disk page I/O as part of a large multi-page block I/O will be represented as COSTπ, and this quantity is a good deal smaller because it amortizes seek time and rotational latency over multiple pages. We adopt the following nomenclature for storage costs: COSTd = cost of 1 MByte of disk storage; COSTm = cost of 1 MByte of memory storage; COSTP = disk arm cost to provide 1 page/second I/O rate, for random pages; COSTπ = disk arm cost to provide 1 page/second I/O rate, as part of multi-page block I/O.

峰值使用时的随机页面 I/O 有一个成本 COSTP，基于磁盘臂的公平租金，而作为大型多页块 I/O 一部分的磁盘页面 I/O 成本表示为 COSTπ，这个量要小得多，因为它将寻道时间和旋转延迟分摊到多个页面上。我们采用以下存储成本术语：COSTd = 1 MB 磁盘存储成本；COSTm = 1 MB 内存存储成本；COSTP = 为随机页面提供每秒 1 页 I/O 速率的磁盘臂成本；COSTπ = 作为多页块 I/O 一部分提供每秒 1 页 I/O 速率的磁盘臂成本。

Given an application referencing a body of data with S MBytes of storage and H random pages per second of I/O transfer (we assume no data is buffered), the rent for disk arms is given by H·COSTP and the rent for disk media is given by S·COSTd. The calculated cost for accessing this disk resident data, COST-D, is given by: COST-D = max(S·COSTd, H·COSTP). If we assume that memory buffers can be populated in advance to support the random I/O requests, the cost of accessing this buffer resident data, COST-B, is simply: COST-B = S·COSTm + S·COSTd. Now the total cost is: COST-TOT = min(max(S·COSTd, H·COSTP), S·COSTm + S·COSTd).

给定一个引用 S MB 存储和每秒 H 次随机页面 I/O 传输的应用（假设没有数据被缓冲），磁盘臂的租金为 H·COSTP，磁盘介质的租金为 S·COSTd。访问此磁盘驻留数据的计算成本 COST-D 为：COST-D = max(S·COSTd, H·COSTP)。如果我们假设可以预先填充内存缓冲以支持随机 I/O 请求，则访问此缓冲驻留数据的成本 COST-B 简单为：COST-B = S·COSTm + S·COSTd。总成本为：COST-TOT = min(max(S·COSTd, H·COSTP), S·COSTm + S·COSTd)。

There are three cost regimes in the graph of COST-TOT as the page access rate H increases for a given volume of data S. See Figure 3.1. Following Copeland et al. [6], we define the temperature of a body of data as H/S, and we name these three cost regimes cold, warm, and hot. Hot data has a high enough access rate H, and thus temperature H/S, to justify memory buffer residence. At the other extreme, cold data is disk capacity limited. In between is warm data, whose access requirements must be met by limiting the data capacity used under each disk arm. These ranges are divided as follows: Tf = COSTd/COSTP = temperature division point between cold and warm data ("freezing"); Tb = COSTm/COSTP = temperature division point between warm and hot data ("boiling").

在给定数据量 S 下，随着页面访问速率 H 的增加，COST-TOT 的图形有三个成本区间。见图 3.1。遵循 Copeland 等人 [6] 的方法，我们将数据体的温度定义为 H/S，并将这三个成本区间命名为冷、温和热。热数据具有足够高的访问速率 H（因而温度 H/S 足够高），足以证明内存缓冲驻留的合理性。在另一个极端，冷数据受磁盘容量限制。介于两者之间的是温数据，其访问需求必须通过限制每个磁盘臂下使用的数据容量来满足。这些范围划分如下：Tf = COSTd/COSTP = 冷数据与温数据之间的温度分界点（"冰点"）；Tb = COSTm/COSTP = 温数据与热数据之间的温度分界点（"沸点"）。

Figure 3.1. Cost per MByte vs. data temperature, showing cold/warm/hot regions.
图 3.1. 每 MB 成本与数据温度关系，显示冷/温/热区域。

As stressed in [6], it is straightforward to calculate the temperature of a database table when it is accessed uniformly. However, the relevance of this temperature depends on the access method: the temperature that is relevant involves the actual disk access rate, not the logical insert rate (including batched buffered inserts). One way to express what an LSM-tree achieves is to say that it reduces the actual disk accesses and thus lowers the effective temperature of the indexed data. This idea is revisited in the conclusions of Section 6.

正如 [6] 中所强调的，当数据库表被均匀访问时，计算其温度是很简单的。然而，该温度的相关性取决于访问方法：相关的温度涉及实际磁盘访问速率，而非逻辑插入速率（包括批量缓冲的插入）。表达 LSM-tree 所实现目标的一种方式是：它减少了实际磁盘访问，从而降低了被索引数据的有效温度。这一思想在第 6 节的结论中重新讨论。

Multi-page block I/O Advantage

多页块 I/O 优势

The advantage to be gained by multi-page block I/O is central to several earlier access methods, such as Bounded Disorder files [16], SB-trees [21], and Log Structured files [23]. A 1989 IBM publication analyzing DB2 utility performance on IBM 3380 disk [29] gave the following analysis: the time to complete a read of a single page could be estimated to be about 20 ms (assumes 10ms seek, 8.3ms rotational delay, 1.7ms read); the time to perform a sequential prefetch read of 64 contiguous pages could be estimated to be about 125ms (assumes 10ms seek, 8.3ms rotational delay, 106.9ms read of 64 pages), or about 2 ms per page. Thus the ratio of 2 ms per page for multi-page block I/O to 20 ms for random I/O implies a ratio of rental costs for the disk arm, COSTπ/COSTP, equal to about 1/10. An analysis of a more recent SCSI-2 disk read of a 4 KByte page gives us a 9 ms seek, 5.5 ms rotational delay, and 1.2 ms read, totalling 16 ms. Reading 64 contiguous 4 KByte pages requires a 9 ms seek, 5.5 ms rotational delay, and 80 ms read for 64 pages, or a total of 95 ms, about 1.5 ms/page. Once again COSTπ/COSTP is equal to about 1/10.

多页块 I/O 所获得的优势对于若干早期访问方法是核心的，如有界无序文件 [16]、SB-tree [21] 和日志结构文件 [23]。1989 年 IBM 发表的分析 IBM 3380 磁盘上 DB2 工具性能的文献 [29] 给出了以下分析：完成单页读取的时间估计约 20 ms（假设 10ms 寻道、8.3ms 旋转延迟、1.7ms 读取）；执行 64 个连续页面顺序预读的时间估计约 125ms（假设 10ms 寻道、8.3ms 旋转延迟、106.9ms 读取 64 页），即每页约 2 ms。因此多页块 I/O 的每页 2 ms 与随机 I/O 的 20 ms 之比意味着磁盘臂租赁成本比 COSTπ/COSTP 约等于 1/10。对较新的 SCSI-2 磁盘读取 4 KB 页面的分析给出 9 ms 寻道、5.5 ms 旋转延迟和 1.2 ms 读取，总计 16 ms。读取 64 个连续 4 KB 页面需要 9 ms 寻道、5.5 ms 旋转延迟和 80 ms 读取 64 页，总计 95 ms，约 1.5 ms/页。COSTπ/COSTP 同样约等于 1/10。

We analyze a workstation server system with SCSI-2 disks holding one GByte and costing about $1000, and a peak rate of approximately 60-70 I/Os per second. The nominal usable I/O rate to avoid long I/O queues is lower, about 40 I/Os per second. The multi-block I/O advantage is significant. Typical Workstation Costs, 1995: COSTm = $100/MByte; COSTd = $1/MByte; COSTP = $25/(IOs/sec); COSTπ = $2.5/(IOs/sec); Tf = COSTd/COSTP = .04 IOs/(sec·MByte) ("freezing point"); Tb = COSTm/COSTP = 4 IOs/(sec·MByte) ("boiling point").

我们分析一个配备 SCSI-2 磁盘的工作站服务器系统，每个磁盘容纳 1 GB，成本约 $1000，峰值速率约为每秒 60-70 次 I/O。为避免长 I/O 队列，可用的名义 I/O 速率更低，约每秒 40 次。多块 I/O 优势显著。1995 年典型工作站成本：COSTm = $100/MB；COSTd = $1/MB；COSTP = $25/(IO/秒)；COSTπ = $2.5/(IO/秒)；Tf = COSTd/COSTP = 0.04 IO/(秒·MB)（"冰点"）；Tb = COSTm/COSTP = 4 IO/(秒·MB)（"沸点"）。

We use the Tb value to derive the reference interval τ for the Five Minute Rule, which asserts that data sustaining an I/O rate of one page every τ seconds is incurring the same cost as the memory needed to hold it. That common cost is: (1/τ)·COSTP = pagesize·COSTm. Solving for τ, we see τ = (1/pagesize)·(COSTP/COSTm) = 1/(pagesize·Tb), and for the values given above, with a page of .004 MBytes, we have τ = 1/(.004·4) ≈ 62.5 seconds/IO.

我们使用 Tb 值推导五分钟法则的参考间隔 τ，该法则断言维持每 τ 秒一次页面 I/O 速率的数据所产生的成本等于容纳它所需的内存成本。该公共成本为：(1/τ)·COSTP = pagesize·COSTm。求解 τ，我们得到 τ = (1/pagesize)·(COSTP/COSTm) = 1/(pagesize·Tb)，对于上述给定值，页面为 0.004 MB，我们有 τ = 1/(0.004·4) ≈ 62.5 秒/IO。

Example 3.1. To achieve a rate of 1000 TPS in the TPC-A application of Example 1.1, there will be H = 2000 I/Os per second to the Account table, itself consisting of 100,000,000 rows of 100 bytes, a total of S = 10 GBytes. The disk storage cost here is S·COSTd = $10,000 whereas the disk I/O cost is H·COSTP = $50,000. The temperature T = H/S = 2000/10,000 = 0.2, well above freezing (a factor of 5), but also well below the boiling point. This warm data uses only 1/5 of its disk capacity for data storage. We are paying for the disk arms and not for the capacity. The situation is similar when we consider the 20 day Acct-ID||Timestamp index to the History table of Example 1.2. Such a B-tree index requires about 9.2 GBytes of leaf-level entries. Given that a growing tree is only about 70% full, the entire tree will require 13.8 GBytes, but it has the same I/O rate (for inserts alone) as the Account table, which implies a comparable temperature.

例 3.1. 为在例 1.1 的 TPC-A 应用中实现 1000 TPS 的速率，Account 表将有 H = 2000 I/O/秒，该表包含 100,000,000 行（每行 100 字节），总计 S = 10 GB。此处磁盘存储成本为 S·COSTd = $10,000，而磁盘 I/O 成本为 H·COSTP = $50,000。温度 T = H/S = 2000/10,000 = 0.2，远高于冰点（5 倍），但也远低于沸点。这些温数据仅使用其磁盘容量的 1/5 来存储数据。我们是在为磁盘臂而非容量付费。当考虑例 1.2 中 History 表的 20 天 Acct-ID||Timestamp 索引时，情况类似。这样的 B-tree 索引需要约 9.2 GB 的叶级条目。鉴于成长中的树仅约 70% 填满，整棵树将需要 13.8 GB，但它的 I/O 速率（仅计算插入）与 Account 表相同，这意味着可比的温度。

3.2 Comparison of LSM-tree and B-tree I/O costs

3.2 LSM-tree 与 B-tree I/O 成本比较

We will be considering I/O costs of index operations which we call mergeable: inserts, deletes, updates, and long-latency finds. The following discussion presents an analysis to compare an LSM-tree to a B-tree.

我们将考虑我们称为可合并操作的索引操作的 I/O 成本：插入、删除、更新和长延迟查找。以下讨论给出比较 LSM-tree 与 B-tree 的分析。

B-tree Insert Cost Formula. Consider the disk arm rental cost of performing a B-tree insert. We must first access the position in the tree where the entry should be placed, and this entails a search down nodes of the tree. We assume that successive inserts to the tree are to random positions at the leaf level, so that node pages in the path of access will not be consistently buffer resident because of past inserts. In [21], the effective depth of a B-tree, symbolized by De, was defined to be the average number of pages not found in buffer during a random key-value search down the directory levels of a B-tree. For B-trees of the size used to index Account-ID||Timestamp in Example 1.2, the value for De is typically about 2.

B-tree 插入成本公式。 考虑执行 B-tree 插入的磁盘臂租赁成本。我们必须首先访问树中应放置条目的位置，这需要沿树的节点向下搜索。我们假设对树的连续插入位于叶级的随机位置，因此访问路径上的节点页面不会因为过去的插入而始终常驻缓冲。在 [21] 中，B-tree 的有效深度（符号 De）被定义为在沿 B-tree 目录级别进行随机键值搜索期间未在缓冲中找到的平均页面数。对于用于索引例 1.2 中 Account-ID||Timestamp 大小的 B-tree，De 的值通常约为 2。

To perform an insert to a B-tree, we perform a key-value search to a leaf level page (De I/Os), update it, and (in the steady state) write out a corresponding dirty leaf page (1 I/O). The relatively infrequent node splits have an insignificant effect on our analysis. The total I/O cost for a B-tree insert, COSTB-ins is given by: (3.1) COSTB-ins = COSTP·(De + 1).

在 B-tree 中执行插入时，我们进行键值搜索到叶级页面（De 次 I/O），更新该页面，然后（在稳态下）写出相应的脏叶页面（1 次 I/O）。相对不频繁的节点分裂对我们的分析影响可以忽略。B-tree 插入的总 I/O 成本 COSTB-ins 由下式给出：(3.1) COSTB-ins = COSTP·(De + 1)。

LSM-tree Insert Cost Formula. To evaluate the cost of an insert into the LSM-tree, we need to think in terms of amortization of multiple inserts, since a single insert to the memory component C0 only occasionally has any I/O effect.

LSM-tree 插入成本公式。 为评估 LSM-tree 插入的成本，我们需要从多次插入摊销的角度思考，因为向内存组件 C0 的单次插入仅偶尔产生 I/O 效果。

Definition 3.2.1. The Batch-Merge Parameter M. To quantify this multiple-entries-per-leaf batching effect, define the parameter M for a given LSM-tree as the average number of entries in the C0 tree inserted into each single page leaf node of the C1 tree during the rolling merge. We assert that the parameter M is a relatively stable value characterizing an LSM-tree. In fact, the value for M is determined by index entry size and the ratio in size between the leaf level of the C1 tree and that of the C0 tree. We define: Se = entry (index entry) size in bytes; Sp = page size in bytes; S0 = size in MBytes of C0 component leaf level; S1 = size in MBytes of C1 component leaf level. Then the number of entries to a page is approximately Sp/Se, and the fraction of entries of the LSM-tree sitting in component C0 is S0/(S0 + S1), so the parameter M is given by: (3.2) M = (Sp/Se)·(S0/(S0 + S1)).

定义 3.2.1. 批量合并参数 M。 为量化每叶多条目的批处理效应，定义给定 LSM-tree 的参数 M 为滚动合并期间从 C0 树插入 C1 树每个单页叶节点的平均条目数。我们断言参数 M 是表征 LSM-tree 的相对稳定值。事实上，M 的值由索引条目大小以及 C1 树叶级与 C0 树叶级之间的大小比决定。我们定义：Se = 条目（索引条目）大小（字节）；Sp = 页面大小（字节）；S0 = C0 组件叶级大小（MB）；S1 = C1 组件叶级大小（MB）。那么每页的条目数约为 Sp/Se，LSM-tree 中位于组件 C0 的条目比例为 S0/(S0 + S1)，因此参数 M 由下式给出：(3.2) M = (Sp/Se)·(S0/(S0 + S1))。

Note that the larger the component C0 in comparison to C1, the larger will be the parameter M. Typical implementations might have S1 = 40·S0 and the number of entries per disk page, Sp/Se, of 200, so that M = 5. Given the parameter M, we can now give a rough formula for the cost COSTLSM-ins of an entry insert into the LSM-tree. We simply amortize the per-page cost of bringing the C1 tree leaf node into memory and writing it out again, 2·COSTπ, over the M inserts that are merged into a C1 tree leaf node during this time: (3.3) COSTLSM-ins = 2·COSTπ/M.

注意 C0 组件相对于 C1 越大，参数 M 就越大。典型实现可能有 S1 = 40·S0，每磁盘页条目数 Sp/Se 为 200，因此 M = 5。给定参数 M，我们现在可以给出 LSM-tree 条目插入成本 COSTLSM-ins 的粗略公式。我们只需将 C1 树叶节点读入内存并写回的每页成本 2·COSTπ 在此期间合并到 C1 树叶节点中的 M 次插入上摊销：(3.3) COSTLSM-ins = 2·COSTπ/M。

A Comparison of LSM-tree and B-tree Insert Costs

LSM-tree 与 B-tree 插入成本比较

If we compare the cost formulas (3.1) and (3.3) for inserts to the two data structures, we see the ratio: (3.4) COSTLSM-ins/COSTB-ins = K1·(COSTπ/COSTP)·(1/M), where K1 is a (near) constant, 2/(De + 1), with a value of approximately 0.67 for index sizes we have been considering. This formula shows that the cost ratio of an insert into the LSM-tree to one in the B-tree is directly proportional to each of two batching effects we have discussed: COSTπ/COSTP, a small fraction corresponding to the ratio of cost for a page I/O in a multi-page block to a random page I/O, and 1/M, where M is the number of entries batched per page during the rolling merge. Typically the product of the two ratios will give a cost ratio improvement of nearly two orders of magnitude.

如果我们比较两种数据结构的插入成本公式 (3.1) 和 (3.3)，我们得到比值：(3.4) COSTLSM-ins/COSTB-ins = K1·(COSTπ/COSTP)·(1/M)，其中 K1 是（近似）常数，2/(De + 1)，对于我们一直考虑的索引大小其值约为 0.67。此公式表明 LSM-tree 插入与 B-tree 插入的成本比与我们讨论的两个批处理效应中的每一个成正比：COSTπ/COSTP——对应于多页块中页面 I/O 与随机页面 I/O 成本比的小分数，以及 1/M——其中 M 是滚动合并期间每页批处理的条目数。通常两个比值的乘积将带来近两个数量级的成本比改进。

Example 3.2. If we assume that an index of the kind in Example 1.2 takes up 1 GByte of disk space but is required to sit on 10 GBytes to achieve necessary disk arm access rates, then there is certainly room for improvement in saving money on disk arm costs. If the ratio of insert costs given in Equation (3.4) is 0.02 = 1/50, then we can shrink the index and disk cost: the LSM-tree will need to take up only 0.7 GBytes on disk because of closely packed entries and reduced disk arm utilization. However, we see that the more efficient LSM-tree can only reduce cost down to what is needed for disk capacity.

例 3.2. 如果我们假设例 1.2 中的索引占用 1 GB 磁盘空间，但为达到必要的磁盘臂访问速率需要位于 10 GB 上，那么在节省磁盘臂成本方面当然有改进空间。如果公式 (3.4) 给出的插入成本比为 0.02 = 1/50，那么我们可以缩减索引和磁盘成本：由于紧密打包的条目和降低的磁盘臂利用率，LSM-tree 仅需占用 0.7 GB 磁盘空间。然而，我们看到更高效的 LSM-tree 只能将成本降低到磁盘容量所需的水平。

3.3 Multi-Component LSM-trees

3.3 多组件 LSM-tree

The parameter M for a given LSM-tree was defined as the average number of entries in the C0 tree inserted into each single page leaf node of the C1 tree during the rolling merge. However, it should be clear from equation (3.2) that if the C1 tree were extremely large in comparison to the C0 tree, or entries were extremely large and fit only a small number to a page, the quantity M might be less than 1. Such a value for M means that on the average more than one C1 tree page must be brought in and out of memory for each entry which is merged in from the C0 tree. In the case where M is extremely small in terms of formula (3.4), specifically if M < K1·COSTπ/COSTP, this could even cancel the batching effect of multi-page disk reads, so we would do better to use a normal B-tree for inserts in place of an LSM-tree.

给定 LSM-tree 的参数 M 被定义为滚动合并期间从 C0 树插入 C1 树每个单页叶节点的平均条目数。然而，从公式 (3.2) 可以清楚看出，如果 C1 树相对于 C0 树极其庞大，或者条目极大且每页只能放少量条目，M 值可能小于 1。M 小于 1 意味着平均每合并一条来自 C0 树的条目需要将多于一个 C1 树页面调入和调出内存。在 M 按公式 (3.4) 极小的情况下，具体地说如果 M < K1·COSTπ/COSTP，这甚至可能抵消多页磁盘读取的批处理效应，此时使用普通 B-tree 进行插入比 LSM-tree 更好。

To avoid a small value for M the only course with a two-component LSM-tree is to increase the size of the C0 component relative to that of C1. Consider a two-component LSM-tree of given total leaf entry size S, and assume we have a constant rate R in bytes per second of new entry inserts into C0. As we vary the size of C0, we affect the circulation speed of the merge cursor. A constant migration rate out to C1 in bytes per second requires that the rolling merge cursor move through entries of C0 at a constant rate in bytes per second, and therefore as the size of C0 decreases the circulation rate from smallest to largest index values in C0 will increase; as a result, the I/O rate for multi-page blocks in C1 to perform the rolling merge must also increase. If a C0 size of a single entry were possible, at this conceptual extreme point we would require a circulation through all multi-page blocks of C1 for each newly inserted entry, an immense demand on I/O.

为避免 M 值过小，在两组件 LSM-tree 中唯一的途径是增大 C0 组件相对于 C1 的大小。考虑一个给定叶条目总大小 S 的两组件 LSM-tree，假设有恒定速率 R（字节/秒）的新条目插入到 C0 中。当我们改变 C0 的大小时，会影响合并游标的循环速度。以恒定的字节/秒迁出速率向 C1 迁移要求滚动合并游标以恒定的字节/秒速率通过 C0 的条目，因此随着 C0 大小的减小，从最小到最大索引值的循环速率会增加；结果，执行滚动合并所需的 C1 中多页块的 I/O 速率也必须增加。如果 C0 大小可以是单个条目，在这个概念极端点上，每个新插入的条目都需要循环通过 C1 的所有多页块，这是对 I/O 的巨大需求。

Now there is a canonical size for C0 determined by the point at which the total cost of the LSM-tree, memory cost for C0 plus media/disk arm cost for the C1 component, is minimized. Now it is common in the two component LSM-tree that the canonical size we determine for C0 will still be quite expensive in terms of memory use. An alternative is to consider adopting an LSM-tree of three or more components.

C0 存在一个典型大小，由 LSM-tree 总成本（C0 的内存成本加 C1 组件的介质/磁盘臂成本）最小化的点决定。在两组件 LSM-tree 中，我们确定的 C0 典型大小通常在内存使用方面仍然相当昂贵。另一种选择是考虑采用三个或更多组件的 LSM-tree。

Figure 3.1b. An LSM-tree of K+1 components.
图 3.1b. K+1 组件的 LSM-tree。

In general, an LSM-tree of K+1 components has components C0, C1, C2, ..., CK-1 and CK, which are indexed tree structures of increasing size; the C0 component tree is memory resident and all other components are disk resident (but with popular pages buffered in memory as with any disk resident access tree). Under pressure from inserts, there are asynchronous rolling merge processes in train between all component pairs (Ci-1, Ci), that move entries out from the smaller to the larger component each time the smaller component, Ci-1, exceeds its threshold size. During the life of a long-lived entry inserted in an LSM-tree, it starts in the C0 tree and eventually migrates out to the CK, through a series of K asynchronous rolling merge steps.

一般而言，K+1 组件的 LSM-tree 具有组件 C0、C1、C2、...、CK-1 和 CK，它们是大小递增的索引树结构；C0 组件树常驻内存，所有其他组件驻留磁盘（但如同任何磁盘驻留访问树一样，热门页面缓冲在内存中）。在插入压力下，在所有组件对 (Ci-1, Ci) 之间存在异步的滚动合并过程，每当较小的组件 Ci-1 超过其阈值大小时，就将条目从较小组件移出到较大组件。在 LSM-tree 中插入的长寿命条目的生命周期中，它从 C0 树开始，最终通过一系列 K 个异步滚动合并步骤迁移到 CK。

The spotlight here is on performance under insert traffic because we are assuming that the LSM-Tree exists in an insert-mostly environment. LSM-tree finds of three or more components suffer somewhat in performance, typically by one extra page I/O per disk component.

这里关注的焦点是插入流量下的性能，因为我们假设 LSM-Tree 存在于以插入为主的环境中。三个或更多组件的 LSM-tree 在查找性能上有所损失，通常每个磁盘组件多一次页面 I/O。

3.4 LSM-trees: Component Sizes

3.4 LSM-tree：组件大小

In the current Section, we derive a formula for the I/O cost for inserts into an LSM-tree of several components and demonstrate mathematically how to choose optimal threshold sizes for the various components. We define the size of an LSM-tree component, S(Ci), as the number of bytes of entries it contains at the leaf level; S(Ci) = Si, and S is the total size of all leaf level entries in all components, S = Σi Si. We assume there is some relatively steady rate R of insertion, in bytes per second, to component C0 of the LSM-tree, and for simplicity that all newly inserted entries live to circulate out to component CK by a succession of rolling merge steps.

在本节中，我们推导多组件 LSM-tree 插入的 I/O 成本公式，并从数学上演示如何选择各组件的最优阈值大小。我们将 LSM-tree 组件的大小 S(Ci) 定义为其叶级包含的条目字节数；S(Ci) = Si，S 是所有组件中所有叶级条目的总大小，S = Σi Si。我们假设以相对稳定的速率 R（字节/秒）向 LSM-tree 的组件 C0 插入，并为简单起见假设所有新插入的条目都通过一系列滚动合并步骤存活并循环到组件 CK。

Given an LSM-tree of K components with a fixed total size S and memory component size S0, the tree is totally described by the variables ri = Si/Si-1, representing size ratios between adjacent pairs of components. The total page I/O rate to perform all ongoing merge operations can be expressed as a function of R and the ratios ri.

给定 K 个组件的 LSM-tree，总大小 S 和内存组件大小 S0 固定，该树完全由变量 ri = Si/Si-1 描述，代表相邻组件对之间的大小比。执行所有正在进行的合并操作的总页面 I/O 速率可以表示为 R 和比值 ri 的函数。

Theorem 3.1. Given an LSM-tree of K+1 components, with a fixed largest-component size SK, insert rate R, and memory component size S0, the total page I/O rate H to perform all merges is minimized when the ratios ri = Si/Si-1 are all equal to a common value r. The total size S is given by: (3.5) S = S0 + r·S0 + r²·S0 + ... + rK·S0, and the total page I/O rate H is given by: (3.6) H = (2R/Sp)·(K·(1 + r) - 1/2).

定理 3.1. 给定 K+1 组件的 LSM-tree，最大组件大小 SK 固定，插入速率为 R，内存组件大小为 S0，当比值 ri = Si/Si-1 全部等于公共值 r 时，执行所有合并的总页面 I/O 速率 H 最小化。总大小 S 由下式给出：(3.5) S = S0 + r·S0 + r²·S0 + ... + rK·S0，总页面 I/O 速率 H 由下式给出：(3.6) H = (2R/Sp)·(K·(1 + r) - 1/2)。

Proof. Since we have assumed that entries are never deleted until they arrive at component CK, the rate R in bytes per second of inserts to C0 is the same as the rate with which entries migrate by rolling merge out from component Ci-1 to component Ci, for all i. Consider the case where Ci-1 is disk resident. The merge from Ci-1 to Ci entails multi-page block reads from Ci-1 at rate R/Sp pages per second. The merge also entails multi-page reads from Ci at rate ri·R/Sp pages per second. Finally, the merge entails writes at rate (ri+1)·R/Sp pages per second. Summing over all disk resident components, the total I/O rate H is: (3.7) H = (R/Sp)·((2·r1+2) + (2·r2+2) + ... + (2·rK+1)), which can be rewritten as: (3.8) H = (2R/Sp)·(Σ(1..K) ri + K - 1/2). We minimize Σ ri under the condition Π ri = SK/S0 = C, and the solution is clearly when all ri are equal to C^(1/K). ∎

证明。 由于我们假设条目在到达组件 CK 之前不会被删除，向 C0 插入的速率 R（字节/秒）等于条目通过滚动合并从组件 Ci-1 迁出到组件 Ci 的速率（对所有 i 成立）。考虑 Ci-1 驻留磁盘的情况。从 Ci-1 到 Ci 的合并需要以 R/Sp 页/秒的速率从 Ci-1 进行多页块读取。合并还需要以 ri·R/Sp 页/秒的速率从 Ci 进行多页读取。最后，合并需要以 (ri+1)·R/Sp 页/秒的速率写入。对所有磁盘驻留组件求和，总 I/O 速率 H 为：(3.7) H = (R/Sp)·((2·r1+2) + (2·r2+2) + ... + (2·rK+1))，可改写为：(3.8) H = (2R/Sp)·(Σ(1..K) ri + K - 1/2)。我们在条件 Π ri = SK/S0 = C 下最小化 Σ ri，当所有 ri 等于 C^(1/K) 时解显然成立。∎

Theorem 3.2. We vary the assumptions of Theorem 3.1 to fix the total size S rather than the size SK of the largest component. This minimization problem is much more difficult, but can be done using Lagrange multipliers. The results are a sequence of formulas for each ri in terms of higher-indexed ri: rK-1 = rK + 1; rK-2 = rK-1 + 1/rK-1; rK-3 = rK-2 + 1/(rK-1·rK-2); and so on. We omit the proof. As we will see, useful values of ri are fairly large, say 20 or more, so the size of the largest component, SK, dominates the total size S. Note that in Theorem 3.2 therefore, each ri normally differs by only a small fraction from its higher neighbor ri+1. In what follows, we base our examples on the approximation of Theorem 3.1.

定理 3.2. 我们改变定理 3.1 的假设，固定总大小 S 而非最大组件大小 SK。这个最小化问题困难得多，但可以使用拉格朗日乘子法求解。结果是一系列以更高下标 ri 表示每个 ri 的公式：rK-1 = rK + 1；rK-2 = rK-1 + 1/rK-1；rK-3 = rK-2 + 1/(rK-1·rK-2)；依此类推。我们省略证明。我们将看到，ri 的实用值相当大，比如 20 或更多，因此最大组件 SK 的大小主导总大小 S。因此在定理 3.2 中，每个 ri 通常仅与其较高邻居 ri+1 相差很小的比例。在下文中，我们基于定理 3.1 的近似进行示例计算。

Minimizing Total Cost

最小化总成本

From Theorem 3.1, if we allow S0 to vary while R and SK remain constant, since r increases with decreasing S0, and H is proportional to r, clearly H increases with decreasing S0. We can minimize the total cost by trading off expensive memory for inexpensive disk. The total cost is: COSTtot = COSTm·S0 + max[COSTd·S1, COSTπ·H]. We introduce normalized variables: s = (COSTm·S0)/(COSTd·S1); t = 2·((R/Sp)/S1)·(COSTπ/COSTd)·(COSTm/COSTd); C = COSTtot/(COSTd·S1). Substituting equation (3.6) and simplifying, assuming S0/S1 small: C ≈ s + max(1, t/s). The optimal solution for t >= 1 is s = t^(1/2), giving: (3.8) COSTmin = 2·[(COSTm·S1)·(2·COSTπ·R/Sp)]^(1/2).

由定理 3.1，如果我们让 S0 变化而 R 和 SK 保持不变，由于 r 随 S0 减小而增大，且 H 与 r 成正比，显然 H 随 S0 减小而增大。我们可以通过用昂贵的内存换取廉价的磁盘来最小化总成本。总成本为：COSTtot = COSTm·S0 + max[COSTd·S1, COSTπ·H]。我们引入归一化变量：s = (COSTm·S0)/(COSTd·S1)；t = 2·((R/Sp)/S1)·(COSTπ/COSTd)·(COSTm/COSTd)；C = COSTtot/(COSTd·S1)。代入公式 (3.6) 并简化，假设 S0/S1 很小：C ≈ s + max(1, t/s)。对于 t >= 1 的最优解为 s = t^(1/2)，得到：(3.8) COSTmin = 2·[(COSTm·S1)·(2·COSTπ·R/Sp)]^(1/2)。

Thus the total cost of the LSM-tree (for t ≥ 1) is twice the geometric mean of the cost of enough memory to hold all the data and the cost of disk required to support the multi-page block I/O needed to write its inserts to disk in the cheapest way. Half of this total cost is used for memory for S0, the other half for disk for I/O access to S1. Note that asymptotically, the cost goes as R^(1/2) compared to R for the B-tree. In the case that t <= 1, the cooler case, the minimum cost occurs along s = t, where C = t + 1 < 2, meaning the total cost is always less than twice the basic cost of storing S1 on disk.

因此 LSM-tree 的总成本（对于 t ≥ 1）是容纳所有数据所需的内存成本与以最廉价方式将插入写入磁盘所需的多页块 I/O 磁盘成本的几何平均值的两倍。总成本的一半用于 S0 的内存，另一半用于对 S1 的 I/O 访问磁盘。注意渐近地，成本按 R^(1/2) 增长，而 B-tree 为 R。在 t <= 1 的情况下（较冷的情况），最小成本沿 s = t 出现，其中 C = t + 1 < 2，意味着总成本始终小于在磁盘上存储 S1 基本成本的两倍。

Example 3.3. We consider the Account-ID||Timestamp index detailed in Example 3.1. The insertion rate is R = 16,000 bytes per second (1000 sixteen-byte entries), resulting in 576 million entries (9.2 GBytes) over 20 days. Using a B-tree to support the index, the disk I/O will be the limiting factor. We are required to use enough disk space to provide H = 2,000 random I/Os per second to update random pages at the leaf level. Using COSTP = $25, the cost for I/O is H·COSTP = $50,000. The cost to buffer upper-level nodes: assume leaf nodes 70% full, 180 entries per leaf, therefore the level above contains about 3.2 million entries, about 16,000 pages or 64 MBytes, at COSTm = $100/MByte = $6,400. Total B-tree cost: $50,000 + $6,400 = $56,400.

例 3.3. 我们考虑例 3.1 中详述的 Account-ID||Timestamp 索引。插入速率为 R = 16,000 字节/秒（1000 条 16 字节条目），20 天产生 5.76 亿条条目（9.2 GB）。使用 B-tree 支持该索引，磁盘 I/O 将是限制因素。我们需要使用足够的磁盘空间来提供 H = 2000 随机 I/O/秒以更新叶级的随机页面。使用 COSTP = $25，I/O 成本为 H·COSTP = $50,000。缓冲上层节点的成本：假设叶节点 70% 填满，每叶 180 条条目，因此上一级包含约 320 万条条目，约 16,000 页即 64 MB，按 COSTm = $100/MB = $6,400。B-tree 总成本：$50,000 + $6,400 = $56,400。

With an LSM-tree of two components, C0 and C1, we need S1 = 9.2 GBytes on disk, costing COSTd·S1 = $9,200. We calculate the total I/O rate supported by an equal cost in disk arms using multi-page block I/O as H = 9200/COSTπ = 3700 pages per second. From Equation (3.6) we solve for r with H = 3700, R = 16,000, Sp = 4K: r = S1/S0 = 460, so S0 = 20 MBytes costing $2,000. This is the s = t solution with t = 0.22, which since t < 1 is the optimal solution. Adding $200 for 2 MBytes of merging block buffers, the total two-component cost is $11,400 — a significant improvement over the B-tree.

使用两组件 LSM-tree（C0 和 C1），我们需要 S1 = 9.2 GB 磁盘，成本 COSTd·S1 = $9,200。我们计算等成本磁盘臂使用多页块 I/O 支持的总 I/O 速率为 H = 9200/COSTπ = 3700 页/秒。从公式 (3.6) 求解 r，H = 3700，R = 16,000，Sp = 4K：r = S1/S0 = 460，因此 S0 = 20 MB，成本 $2,000。这是 s = t 解，t = 0.22，由于 t < 1 是最优解。加上 $200 的 2 MB 合并块缓冲，两组件总成本为 $11,400——相比 B-tree 有显著改善。

Here is a full explanation of the solution. The insert rate of R = 16,000 bytes/second is turned into 4 pages/second that need to be merged from C0 to C1. Since C1 is 460 times larger than C0, the new entries from C0 are on the average merged into positions 460 entries apart in C1. Thus merging a page from C0 requires reading and writing 460 pages of C1, a total of 3680 pages per second. But this is exactly what 9.2 disks provide in multiblock I/O capacity, with each providing 400 pages/sec, 10 times the nominal random I/O rate of 40 pages/second.

以下是该解的完整解释。插入速率 R = 16,000 字节/秒转化为每秒 4 页需要从 C0 合并到 C1。由于 C1 是 C0 的 460 倍大，来自 C0 的新条目平均合并到 C1 中间隔 460 个条目的位置。因此从 C0 合并一页需要读写 460 页 C1，总计每秒 3680 页。这恰好是 9.2 块磁盘在多块 I/O 容量下提供的，每块提供 400 页/秒，是名义随机 I/O 速率 40 页/秒的 10 倍。

Example 3.4. Consider Example 3.3, with R increased by a factor of 10 (to 160,000 bytes/sec). The B-tree solution now costs $506,400 ($500,000 for 500 GB of disk to support H = 20,000 I/Os/sec, plus $6,400 for directory memory). In the LSM-tree analysis, t increases to 2.2 (greater than 1), so the best 2-component solution uses equation (3.8): minimum cost $27,000, half for 13.5 GB disk, half for 135 MB memory. With 2 MB buffer, total $27,200.

例 3.4. 考虑例 3.3，R 增大 10 倍（至 160,000 字节/秒）。B-tree 方案现在成本 $506,400（$500,000 用于 500 GB 磁盘以支持 H = 20,000 IO/秒，加 $6,400 目录内存）。在 LSM-tree 分析中，t 增加到 2.2（大于 1），因此最佳 2 组件解使用公式 (3.8)：最小成本 $27,000，一半用于 13.5 GB 磁盘，一半用于 135 MB 内存。加上 2 MB 缓冲，总计 $27,200。

With an LSM-tree of three components for the R = 160,000 bytes/second case, by Theorem 3.1 we calculate r = 23 and S0 = 17 MBytes (memory cost $1,700) for fully occupied disk arms. The smaller disk component costs 1/23 of the larger. Allowing 4 MBytes of memory ($400) for buffering the two rolling merge operations, the total cost for a 3-component LSM-tree is $9,200 for disk plus $2,100 for memory, or a total cost of $11,300 — a further significant improvement over the 2-component case.

对于 R = 160,000 字节/秒的三组件 LSM-tree，根据定理 3.1 我们计算出 r = 23，S0 = 17 MB（内存成本 $1,700），磁盘臂满负荷运行。较小的磁盘组件成本为较大组件的 1/23。允许 4 MB 内存（$400）用于两个滚动合并操作的缓冲，3 组件 LSM-tree 的总成本为 $9,200 磁盘加 $2,100 内存，总计 $11,300——比 2 组件情况进一步显著改善。

Here is a full explanation of the three-component solution. The in-memory component C0 has 17 Mbytes, the smaller disk component C1 is 23 times larger, at 400 Mbytes, and C2 is 23 times larger than C1, at 9.2 Gbytes. Each page of the 40 pages/second of data that must be merged from C0 to C1 entails 23 pages of reading and 23 of writing, or 1840 pages per second. Similarly, 40 pages/second are being merged from C1 to C2, each of which requires 23 pages of reads and writes of C2. The total of the two I/O rates is 3680, exactly the multiblock I/O capacity of the 9.2 G of disk.

以下是三组件解的完整解释。内存组件 C0 为 17 MB，较小的磁盘组件 C1 大 23 倍为 400 MB，C2 大于 C1 的 23 倍为 9.2 GB。每秒 40 页需要从 C0 合并到 C1 的数据，每页需要 23 页的读取和 23 页的写入，即每秒 1840 页。类似地，每秒 40 页从 C1 合并到 C2，每页需要 23 页的 C2 读写。两个 I/O 速率的总和为 3680，恰好等于 9.2 GB 磁盘的多块 I/O 容量。

It turns out that as we increase the number of components the size of S0 continues to decrease until the point is reached where the ratio r between component sizes reaches the value e = 2.71..., or until we reach the cold-data regime. However, we can see from Example 3.4 that successively smaller S0 components make less and less difference to total cost. Furthermore, there are costs associated with increasing the number of components: a CPU cost to perform additional rolling merges, a memory cost to buffer the nodes of those merges, and indexed finds requiring immediate response will sometimes have to perform retrieval from all component trees. These considerations put a strong constraint on the appropriate number of components, and three components are probably the most that will be seen in practice.

结果是随着组件数量的增加，S0 的大小持续减小，直到组件间大小比 r 达到 e = 2.71... 的值，或者直到我们达到冷数据区间。然而，从例 3.4 可以看出，连续减小的 S0 组件对总成本的差异越来越小。此外，增加组件数量有相关成本：执行额外滚动合并的 CPU 成本、缓冲这些合并节点的内存成本，以及需要立即响应的索引查找有时必须从所有组件树中检索。这些考虑对适当的组件数量施加了强约束，三个组件可能是实践中能看到的最多数量。

4. Concurrency and Recovery in the LSM-tree

4. LSM-tree 的并发与恢复

In the current Section we investigate the approaches to be used to provide concurrency and recovery for the LSM-tree. To accomplish this, we need to sketch a more detailed level of design for the rolling merge process. We leave a formal demonstration of correctness of the concurrency and recovery algorithms for a later work, and try here simply to motivate the design proposed.

在本节中，我们研究为 LSM-tree 提供并发和恢复所使用的方法。为此，我们需要为滚动合并过程概述更详细的设计层面。我们将并发和恢复算法正确性的正式证明留给后续工作，这里只是尝试阐释所提出设计的动机。

4.1 Concurrency in the LSM-tree

4.1 LSM-tree 的并发

In general, we are given an LSM-tree of K+1 components, C0, C1, C2, ..., CK, of increasing size. Each disk resident component is constructed of page-sized nodes in a B-tree type structure, except that multiple nodes in key sequence order at all levels below the root sit on multi-page blocks. Directory information in upper levels channels access down through single page nodes and also indicates which sequence of nodes sits on a multi-page block, so that a read or write of such a block can be performed all at once. Under most circumstances, each multi-page block is packed full with single page nodes, but there are a few situations where a smaller number of nodes exist in such a block.

一般而言，我们有 K+1 个组件的 LSM-tree：C0、C1、C2、...、CK，大小递增。每个磁盘驻留组件由类似 B-tree 结构的页面大小节点构成，但在根以下所有层级上，按键序排列的多个节点位于多页块上。上层的目录信息引导访问通过单页节点向下，并指示哪些节点序列位于一个多页块上，以便可以一次性读写这样的块。在大多数情况下，每个多页块被单页节点装满，但也有少数情况下块中存在较少数量的节点。

A concurrency approach for the LSM-tree must mediate three distinct types of physical conflict: (i) A find operation should not access a node of a disk-based component at the same time that a different process performing a rolling merge is modifying the contents of the node. (ii) A find or insert into the C0 component should not access the same part of the tree that a different process is simultaneously altering to perform a rolling merge out to C1. (iii) The cursor for the rolling merge from Ci-1 out to Ci will sometimes need to move past the cursor for the rolling merge from Ci out to Ci+1, since the rate of migration out from Ci-1 is always at least as great as the rate from Ci, and this implies a faster rate of circulation of the cursor attached to the smaller component Ci-1. Whatever concurrency method is adopted must permit this passage to take place without one process being blocked behind the other.

LSM-tree 的并发方法必须调解三种不同类型的物理冲突：(i) 查找操作不应在另一个执行滚动合并的进程正在修改节点内容时同时访问该磁盘组件的节点。(ii) 对 C0 组件的查找或插入不应访问另一个进程正在同时修改以执行到 C1 的滚动合并的同一树区域。(iii) 从 Ci-1 到 Ci 的滚动合并游标有时需要越过从 Ci 到 Ci+1 的滚动合并游标，因为从 Ci-1 迁出的速率总是至少等于从 Ci 迁出的速率，这意味着附着在较小组件 Ci-1 上的游标有更快的循环速率。无论采用什么并发方法，都必须允许这种越过发生而不会使一个进程被阻塞在另一个后面。

Nodes are the unit of locking used in the LSM-tree to avoid physical conflict during concurrent access to disk based components. Nodes being updated because of rolling merge are locked in write mode and nodes being read during a find are locked in read mode; methods of directory locking to avoid deadlocks are well understood (see, for example, [3]). The locking approach taken in C0 is dependent on the data structure used. In the case of a (2-3)-tree, for example, we could write lock a subtree falling below a single (2-3)-directory node that contains all entries in the range affected during a merge to a node of C1; simultaneously, find operations would lock all (2-3)-nodes on their access path in read mode. Note that we are only considering concurrency at the lowest physical level of multi-level locking, in the sense of [28].

节点是 LSM-tree 中用于避免磁盘组件并发访问期间物理冲突的锁单元。因滚动合并而更新的节点被加写锁，在查找期间读取的节点被加读锁；避免死锁的目录锁定方法已被充分理解（例如见 [3]）。C0 中采用的锁定方法取决于所使用的数据结构。例如在 (2-3) 树的情况下，我们可以对位于单个 (2-3) 目录节点之下的子树加写锁，该目录节点包含合并到 C1 节点期间受影响范围内的所有条目；同时，查找操作会对其访问路径上的所有 (2-3) 节点加读锁。注意我们仅考虑 [28] 意义上的多级锁定的最低物理层面的并发。

Write locks for (all) nodes under the cursor are released following each node merged from the larger component. This gives an opportunity for a long range find or for a faster cursor to pass a relatively slower cursor position, and thus addresses point (iii) above.

游标下（所有）节点的写锁在从较大组件合并每个节点后释放。这为长范围查找或较快游标越过相对较慢游标位置提供了机会，从而解决了上述第 (iii) 点。

Now assume we are performing a rolling merge between two disk based components, migrating entries from Ci-1 (the inner component) out to Ci (the outer component). The cursor always has a well-defined inner component position within a leaf-level node of Ci-1, and simultaneously a position in Ci at the leaf level and at upper levels along the path of access. As the merge cursor progresses, new leaf nodes of Ci created by the merge are immediately placed left-to-right in a new buffer resident multi-page block. The nodes of Ci surrounding the current cursor position will in general be split into two partially full multi-page block buffers: the "emptying" block and the "filling" block.

现在假设我们在两个磁盘组件之间执行滚动合并，将条目从 Ci-1（内部组件）迁出到 Ci（外部组件）。游标在 Ci-1 的叶级节点中始终有一个明确定义的内部组件位置，同时在 Ci 的叶级和沿访问路径的上层也有位置。随着合并游标的推进，合并创建的 Ci 新叶节点立即从左到右放入新的缓冲常驻多页块中。围绕当前游标位置的 Ci 节点通常会被分成两个部分填满的多页块缓冲："排空"块和"填充"块。

In the most general approach, we may wish to retain certain entries in Ci-1 rather than migrating all entries out to Ci. In this case, the nodes in Ci-1 surrounding the merge cursor will also be split into an emptying block and a filling block. In this most general case, the merge cursor position is affecting four different nodes at any one time: the inner and outer component nodes in the emptying blocks where the merge is about to occur and the inner and outer component nodes in the filling blocks where new information is being written. We take write locks on all four nodes during the time the merge is actually modifying the node structures and release these locks at quantized instants; we choose to release locks each time a node in the emptying block in the outer component has been completely depleted.

在最通用的方法中，我们可能希望在 Ci-1 中保留某些条目而非将所有条目迁出到 Ci。在这种情况下，围绕合并游标的 Ci-1 节点也会被分成排空块和填充块。在这种最通用的情况下，合并游标位置在任一时刻影响四个不同的节点：排空块中即将发生合并的内外组件节点，以及填充块中正在写入新信息的内外组件节点。在合并实际修改节点结构期间，我们对所有四个节点加写锁，并在量化的时刻释放这些锁；我们选择在外部组件排空块中的一个节点被完全清空时释放锁。

As with all such merge steps from the C0 to C1 components, one CPU should be totally dedicated to this task so that other accesses are excluded by write locks for as short a time as possible. The range of C0 entries to be merged should be pre-calculated and a write lock taken on this entry range in advance. Following this, CPU time is saved by deleting entries from the C0 component in a batch fashion, without attempts to rebalance after each individual entry delete; the C0 tree can be fully rebalanced after the merge step is complete.

与所有从 C0 到 C1 组件的合并步骤一样，应该有一个 CPU 完全专注于此任务，以便写锁排除其他访问的时间尽可能短。要合并的 C0 条目范围应预先计算，并提前对此条目范围加写锁。此后，通过以批量方式从 C0 组件删除条目来节省 CPU 时间，不在每次单独条目删除后尝试重平衡；C0 树可以在合并步骤完成后完全重平衡。

4.2 Recovery in the LSM-tree

4.2 LSM-tree 的恢复

As new entries are inserted into the C0 component and the rolling merge processes migrate entry information out to successively larger components, this work takes place in memory buffered multi-page blocks. As with any such memory buffered changes, the work is not resistant to system failure until it has been written to disk. We are faced with a classical recovery problem: to reconstruct work that has taken place in memory after a crash occurs and memory is lost.

当新条目插入 C0 组件且滚动合并过程将条目信息迁移到逐渐增大的组件时，这些工作在内存缓冲的多页块中进行。与任何此类内存缓冲变更一样，这些工作在写入磁盘之前不能抵抗系统故障。我们面临一个经典的恢复问题：在崩溃发生并丢失内存后重建已在内存中发生的工作。

As we mentioned at the beginning of Chapter 2, we don't need to create special logs to recover index entries on newly created records: transactional insert logs for these new records are written out to a sequential log file in the normal course of events, and it is a simple matter to treat these insert logs as a logical base for reconstructing the index entries. This new approach to recover an index must be built into the system recovery algorithm, and may have the effect of extending the time before storage reclamation for such transactional History insert logs can take place, but this is a minor consideration.

正如我们在第 2 章开头提到的，我们不需要创建特殊日志来恢复新创建记录的索引条目：这些新记录的事务插入日志在正常事件过程中被写入顺序日志文件，将这些插入日志作为重建索引条目的逻辑基础是很简单的。这种恢复索引的新方法必须内置到系统恢复算法中，可能会延长事务 History 插入日志的存储回收时间，但这是一个次要考虑。

When a checkpoint is requested at time T0, we complete all merge steps in operation so that node locks are released, then postpone all new entry inserts to the LSM-tree until the checkpoint completes; at this point we create an LSM-tree checkpoint with the following actions: (a) We write the contents of component C0 to a known disk location; following this, entry inserts to C0 can begin again, but merge steps continue to be deferred. (b) We flush to disk all dirty memory buffered nodes of disk based components. (c) We create a special checkpoint log with the following information: the Log Sequence Number, LSN0, of the last inserted indexed row at time T0; the disk addresses of the roots of all components; the location of all merge cursors in the various components; the current information for dynamic allocation of new multi-page blocks.

当在时间 T0 请求检查点时，我们完成所有正在进行的合并步骤以便释放节点锁，然后推迟所有新条目对 LSM-tree 的插入，直到检查点完成；此时我们通过以下操作创建 LSM-tree 检查点：(a) 将 C0 组件的内容写入已知的磁盘位置；此后，可以重新开始向 C0 插入条目，但合并步骤继续被推迟。(b) 将磁盘组件的所有脏内存缓冲节点刷新到磁盘。(c) 创建特殊的检查点日志，记录以下信息：时间 T0 最后插入的索引行的日志序列号 LSN0；所有组件根节点的磁盘地址；各组件中所有合并游标的位置；新多页块动态分配的当前信息。

In the event of a crash and subsequent restart, this checkpoint can be located and the saved component C0 loaded back into memory, together with the buffered blocks of other components needed to continue rolling merges. Then logs starting with the first LSN after LSN0 are read into memory and have their associated index entries entered into the LSM-tree. None of this information has been wiped out by later writes of multi-page disk blocks since these writes are always to new locations on disk until subsequent checkpoints make outmoded multi-page blocks unnecessary. As we recover logs of inserts for indexed rows, we place new entries into the C0 component; now the rolling merge starts again, overwriting any multi-page blocks written since the checkpoint, but recovering all new index entries, until the most recently inserted row has been indexed and recovery is complete.

在崩溃和随后重启的情况下，可以定位此检查点并将保存的 C0 组件加载回内存，连同继续滚动合并所需的其他组件的缓冲块。然后从 LSN0 之后的第一个 LSN 开始读取日志到内存，并将关联的索引条目输入 LSM-tree。这些信息不会被后续的多页磁盘块写入覆盖，因为这些写入总是写到磁盘上的新位置，直到后续检查点使过时的多页块不再需要。当我们恢复索引行插入的日志时，将新条目放入 C0 组件；现在滚动合并重新开始，覆盖检查点以来写入的任何多页块，但恢复所有新索引条目，直到最近插入的行已被索引，恢复完成。

Another detail of recovery has to do with directory information. As the rolling merge progresses, each time a multi-page block or a higher level directory node is brought in from disk to be emptied it must immediately be assigned a new disk position in case a checkpoint occurs before the emptying is completed. This means that the directory entries pointing down to the emptying nodes must be immediately corrected to point to the new node locations. Similarly we must immediately assign a disk position for newly created nodes. At every point we need to take care that directory nodes containing pointers to lower-level nodes buffered by a rolling merge are also buffered. If this sounds like a great deal of work the reader should recall that there is no additional I/O necessary and the number of pointers involved is probably only about 64 for each block buffered.

恢复的另一个细节与目录信息有关。随着滚动合并的推进，每次从磁盘调入多页块或高层目录节点进行排空时，必须立即为其分配新的磁盘位置，以防在排空完成前发生检查点。这意味着指向排空节点的目录条目必须立即更正为指向新的节点位置。类似地，我们必须立即为新创建的节点分配磁盘位置。在每个点上，我们需要确保包含指向滚动合并缓冲的低层节点指针的目录节点也被缓冲。如果这听起来工作量很大，读者应该记住不需要额外的 I/O，每个被缓冲的块涉及的指针数量大概只有约 64 个。

5. Cost-Performance Comparisons with Other Access Methods

5. 与其他访问方法的性价比比较

In our introductory Example 1.2, we considered a B-tree for the Acct-ID||Timestamp index on the History file because it is the most common disk-based access method used in commercial systems. What we wish to show now is that no other disk indexing structure consistently gives superior I/O performance.

在引言的例 1.2 中，我们为 History 文件上的 Acct-ID||Timestamp 索引考虑了 B-tree，因为它是商业系统中最常用的基于磁盘的访问方法。我们现在要证明的是，没有其他磁盘索引结构能始终提供更优的 I/O 性能。

Assume we are dealing with an arbitrary indexing structure. Recall that we calculated the number of entries in the Acct-ID||Timestamp index by assuming they were generating 1000 entries per second over a 20 day period of accumulation with eight hour days. Given index entries 16 bytes in length this implies 9.2 GBytes of entries or about 2.3 million 4 KByte pages of index, even if there is no wasted space. None of these conclusions are subject to change because of the specific choice of index method.

假设我们处理的是任意索引结构。回顾我们通过假设每秒生成 1000 条条目、累积 20 天（每天 8 小时）来计算 Acct-ID||Timestamp 索引中的条目数。给定 16 字节的索引条目，这意味着 9.2 GB 的条目或约 230 万个 4 KB 索引页面，即使没有空间浪费。这些结论不会因具体的索引方法选择而改变。

Now to perform an insert of a new index entry into an index structure, we need to calculate the page on which the entry is to be inserted and make sure that page is memory resident. The question naturally arises: Are newly inserted entries generally placed in an arbitrary position among all 9.2 GBytes of index entries that are already present? The answer, for most classical access method structures, is Yes.

现在要将新索引条目插入索引结构，我们需要计算该条目应插入的页面并确保该页面常驻内存。自然产生一个问题：新插入的条目通常是否被放置在已存在的全部 9.2 GB 索引条目中的任意位置？对于大多数经典访问方法结构，答案是肯定的。

Definition 5.1. We say that the index structure of a disk based access method has the property of being a Continuum Structure if the indexing scheme provides for immediate placement of a newly inserted index entry in its ultimate collation order, based on key-value, with all other entries already present.

定义 5.1. 如果索引方案规定将新插入的索引条目基于键值立即放置在其最终的排序位置，与所有已存在的条目一起，我们就说该基于磁盘的访问方法的索引结构具有连续体结构的性质。

Since transactional Acct-ID values are randomly chosen from 100,000,000 possible values, each new insert will be on a random one of the 2.3 million pages of existing entries. Now 2.3 million pages is the minimum on which 9.2 GBytes of entries can sit, and given 1000 inserts per second, each page is accessed about once every 2,300 seconds; by the Five Minute Rule it is uneconomical to keep all these pages buffered. In general, a page is read into buffer for an entry insert and must later be dropped. In transactional systems that update disk pages in place, this requires a second I/O. Thus a Continuum Structure that does not defer updates will require at least two I/Os for each index insert, approximately the same as a B-tree.

由于事务的 Acct-ID 值从 100,000,000 个可能值中随机选择，每次新插入将在现有条目的 230 万个页面中的随机一个上。230 万页是 9.2 GB 条目可以容纳的最小页数，给定每秒 1000 次插入，每页约每 2300 秒被访问一次；根据五分钟法则，将所有这些页面保持缓冲是不经济的。通常，一个页面被读入缓冲用于条目插入，之后必须被丢弃。在原地更新磁盘页面的事务系统中，这需要第二次 I/O。因此不延迟更新的连续体结构每次索引插入至少需要两次 I/O，与 B-tree 大致相同。

Most existing disk-based access methods are Continuum Structures, including B-trees [5] and its large number of variants such as SB-trees [21], Bounded Disorder Files [16], various types of hashing schemes such as extendible hashing [9], and a myriad others. However, there are a few access methods which migrate their entries from one segment to another.

大多数现有的基于磁盘的访问方法都是连续体结构，包括 B-tree [5] 及其大量变体如 SB-tree [21]、有界无序文件 [16]、各种哈希方案如可扩展哈希 [9] 等。然而，有少数访问方法会将条目从一个段迁移到另一个段。

First of all we should analyze exactly why the LSM-tree beats the Continuum Structure in terms of I/O performance. In its most general formulation the advantage the LSM-tree enjoys results from two factors: (1) the ability to keep component C0 memory resident, and (2) careful deferred placement. It is crucial that the original insert be made to a memory based component. Without a guaranteed memory resident component to which new inserts are performed, we return to the situation of two I/Os for each entry insert.

首先我们应该准确分析 LSM-tree 为什么在 I/O 性能方面击败连续体结构。在最一般的表述中，LSM-tree 享有的优势来自两个因素：(1) 能够将 C0 组件保持在内存中，以及 (2) 精心的延迟放置。原始插入必须在基于内存的组件中进行，这一点至关重要。没有保证新插入在其中执行的内存常驻组件，我们就回到了每次条目插入两次 I/O 的情况。

Time-Split B-tree

时间分裂 B-tree

The TSB-tree is a two-dimensional search structure to locate records by dimensions of timestamp and keyvalue. It is assumed that each time a record with a given key value is inserted, the old one becomes outmoded; however, a permanent history of all records is kept indexed. When a new entry is inserted in a node that has no room, the node can be split either by key-value or by time. The object is to eventually migrate outmoded records to a history component on inexpensive write-once storage. There is no attempt to keep the current tree in memory as with the C0 component of the LSM-tree. Without a guaranteed memory resident component, we are back to two I/Os per insert.

TSB-tree 是一种二维搜索结构，按时间戳和键值两个维度定位记录。假设每次插入具有给定键值的记录时，旧记录变为过时的；然而，所有记录的永久历史都被保持索引。当新条目插入到没有空间的节点时，节点可以按键值或按时间分裂。目标是最终将过时的记录迁移到廉价的只写存储上的历史组件中。它不像 LSM-tree 的 C0 组件那样试图将当前树保持在内存中。没有保证的内存常驻组件，我们又回到了每次插入两次 I/O 的情况。

MD/OD R-Tree

MD/OD R-Tree

The MD/OD R-tree of Kolovson and Stonebraker [15] is comparable to the TSB-tree, in that it uses a two dimensional access method (R-tree) variant to cluster and index historical records by timestamp range and keyvalue. The important R-tree variation introduced is that the structure is meant to span magnetic disk (MD) and optical disk (OD); the ultimate object is to eventually migrate outmoded records to an archive R-tree on inexpensive write-once optical storage. This migration occurs by means of a Vacuum Cleaner Process (VCP). As with the TSB-tree, there is no claim that the MD/OD R-tree accelerates insert performance. Without a guaranteed memory resident component, we return to two I/Os per insert.

Kolovson 和 Stonebraker [15] 的 MD/OD R-tree 与 TSB-tree 类似，它使用二维访问方法（R-tree）变体按时间戳范围和键值聚簇和索引历史记录。引入的重要 R-tree 变体是该结构旨在跨越磁盘（MD）和光盘（OD）；最终目标是将过时的记录迁移到廉价的只写光学存储上的归档 R-tree 中。此迁移通过真空清理进程（VCP）完成。与 TSB-tree 一样，MD/OD R-tree 未声称能加速插入性能。没有保证的内存常驻组件，我们又回到了每次插入两次 I/O。

Differential File

差分文件

The Differential File approach [25] starts with a main data file which remains unchanged over an extended period, while newly added records are placed into a specific overflow area known as a Differential File. At some future point it is assumed that the changes will be amalgamated with the main data file, and a new Differential File will be started. The concept of a Bloom filter is suggested as the main mechanism to avoid double accesses. Once again, the Differential File makes no provision to keep the Differential File memory resident. It corresponds to maintaining a C0 component in memory while C1 is merged with C2, but the presentation assumes relatively slow insert rates. It is not suggested that a differential-differential file should be kept memory resident at all times and no mention is made of I/O savings for insert operations.

差分文件方法 [25] 从一个长期保持不变的主数据文件开始，新添加的记录放入称为差分文件的特定溢出区域。假设在未来某个时点，变更将与主数据文件合并，并启动新的差分文件。建议使用布隆过滤器作为避免双重访问的主要机制。同样，差分文件没有规定将差分文件保持在内存中。它对应于在 C1 与 C2 合并时在内存中维护 C0 组件，但其表述假设相对较慢的插入速率。没有建议差分-差分文件应始终常驻内存，也没有提到插入操作的 I/O 节省。

Selective Deferred Text Index Updates

选择性延迟文本索引更新

The text index maintenance method of Dadum, Lum, Praedel, and Schlageter [7] is also designed to improve system performance in index updates by deferring the actual disk writes. Index updates are cached in memory until forced out by conflicts with queries or trickled out by a background task. After the update, the query runs off of the index on disk. Thus the memory cache is not part of the authoritative index, unlike the LSM-Tree. The deferral method allows some batching of updates in both the forced and trickled cases. However the pattern of updates still looks like that of a Continuum Structure.

Dadum、Lum、Praedel 和 Schlageter [7] 的文本索引维护方法也旨在通过延迟实际磁盘写入来改善索引更新的系统性能。索引更新在内存中缓存，直到被与查询的冲突强制推出或由后台任务滴出。更新后，查询在磁盘上的索引上运行。因此内存缓存不是权威索引的一部分，这与 LSM-Tree 不同。延迟方法在强制和滴出两种情况下都允许一定的更新批处理。然而更新的模式仍然看起来像连续体结构。

6. Conclusions and Suggested Extensions

6. 结论与扩展建议

A B-tree, because it has popular directory nodes buffered in memory, is really a hybrid data structure which combines the low cost of disk media storage for the majority of the data with the high cost of memory accessibility for the most popular data. The LSM-tree extends this hierarchy to more than one level and incorporates the advantage of merge I/O in performing multi-page disk reads.

B-tree 由于其热门目录节点缓冲在内存中，实际上是一种混合数据结构，它将大部分数据的低成本磁盘介质存储与最热门数据的高成本内存可访问性结合在一起。LSM-tree 将这种层次结构扩展到多个级别，并融入了在执行多页磁盘读取时合并 I/O 的优势。

The effect of buffering on a B-tree is to flatten the graph as the rate of access enters the Hot Data region, so that more frequent access doesn't result in ever higher costs extending the slope of the rising line for Warm Data. With a bit of thought, it can be seen that the effect of the LSM-tree is to reduce the cost of access, for any realistic rate of access for mergeable operations such as insert and delete, strongly towards that of cold data. Further, many cases of access rate that would indicate memory residence of the B-tree, the cases labeled "Hot Data" in Figure 6.1, can be accommodated mostly on disk with the LSM-tree. In these cases, the data is hot in terms of logical access rate (inserts/sec) but only warm in terms of physical disk access rate because of the batching effect of the LSM tree. This is an extremely significant advantage for applications that have a great preponderance of mergeable operations.

缓冲对 B-tree 的效果是在访问速率进入热数据区域时使图形变平，使得更频繁的访问不会导致成本不断上升延伸温数据上升线的斜率。稍加思考可以看出，LSM-tree 的效果是将可合并操作（如插入和删除）在任何现实访问速率下的访问成本大幅降低，趋向于冷数据的成本。此外，许多在 B-tree 中需要内存驻留的访问速率情况（图 6.1 中标记为"热数据"的情况）在 LSM-tree 中大部分可以在磁盘上容纳。在这些情况下，数据在逻辑访问速率（插入/秒）上是热的，但由于 LSM-tree 的批处理效应，在物理磁盘访问速率上仅是温的。这对于可合并操作占绝对主导的应用来说是一个极其重要的优势。

6.1 Extensions of LSM-tree Application

6.1 LSM-tree 应用的扩展

To begin with, it should be clear that the LSM-tree entries could themselves contain records rather than RIDs pointing to records elsewhere on disk. This means that the records themselves can be clustered by their keyvalue. The cost for this is larger entries and a concomitant acceleration of the rate of insert R in bytes per second and therefore of cursor movement and total I/O rate H. However, as we saw in Example 3.3 a three component LSM-tree should be able to provide the necessary circulation at a cost of the disk media to store the records and index, and all of this disk media would be needed in any event to store the rows in a non-clustered manner.

首先，应当清楚 LSM-tree 条目本身可以包含记录而非指向磁盘上其他位置记录的 RID。这意味着记录本身可以按键值聚簇。代价是更大的条目以及插入速率 R（字节/秒）的随之加速，因而游标移动和总 I/O 速率 H 也加速。然而正如我们在例 3.3 中看到的，三组件 LSM-tree 应能以存储记录和索引所需磁盘介质的成本提供必要的循环，而这些磁盘介质在非聚簇方式下存储行时无论如何都是需要的。

Advantages of clustering might have quite important performance implications. For example, consider the Escrow transactional method [20], which serves as a good layer to support workflow management because of the non-blocking nature of long-lived updates. Using LSM-trees to cluster Escrow logs first by TID, then by FID when the associated field is not in memory, will save a large number of I/Os where long-lived transactions make large numbers of updates to cold or warm data.

聚簇的优势可能具有相当重要的性能含义。例如，考虑 Escrow 事务方法 [20]，由于长寿命更新的非阻塞特性，它很适合作为支持工作流管理的层。使用 LSM-tree 先按 TID 然后按 FID 聚簇 Escrow 日志（当关联字段不在内存中时），将在长寿命事务对冷数据或温数据进行大量更新时节省大量 I/O。

Another possible variation is the possibility of retaining recent entries (generated in the last τi seconds) in component Ci rather than letting them migrate out to Ci+1. One variation suggests that during cursor circulation, a time-key index such as that provided by the TSB-tree might be generated. The rolling merge can be used to provide great efficiency for new version inserts, and the multi-component structure suggests a final component migration to write-once storage, with a good deal of control over archival time-key indexing.

另一种可能的变体是在组件 Ci 中保留最近的条目（在最近 τi 秒内生成的）而非让它们迁移到 Ci+1。一种变体建议在游标循环期间，可以生成类似 TSB-tree 提供的时间键索引。滚动合并可用于为新版本插入提供极高效率，多组件结构暗示最终组件可迁移到只写存储，对归档时间键索引有很好的控制。

Other ideas for further research include the following: (1) Extend the cost analysis approach of Theorem 3.1 and Example 3.3 to situations where some proportion of find operations must be balanced with the merge for purposes of I/O balancing. (2) It is clear that we can offload the CPU work to maintain the LSM-tree so that this doesn't have to be done by the CPU that produces the log records. We merely need to communicate the logs to the other CPU and then communicate later find requests as well. The design for such distributed work needs to be carefully thought out.

进一步研究的其他思路包括：(1) 将定理 3.1 和例 3.3 的成本分析方法扩展到需要为 I/O 平衡而将一定比例的查找操作与合并平衡的情况。(2) 很明显我们可以将维护 LSM-tree 的 CPU 工作卸载到其他处理器，使得产生日志记录的 CPU 不必承担此任务。我们只需将日志传输到另一个 CPU，然后也传输后续的查找请求。这种分布式工作的设计需要仔细考虑。
