几个月前【按真实时间改】,我需要把 agent 能力接进一个生产系统。技术栈 Java/Spring Boot,场景是高并发多租户,做垂直领域 SaaS 的 agent 平台。我的第一反应跟大多数人一样:这种基础设施别自己造,用官方的。于是认真评估了 Claude Agent SDK。

评估的结果是,我自己用 200 行 Java 写了个裸循环,SDK 没有进生产。

这篇文章不是教你怎么写 agent loop 的,那个东西没什么可教的,贴出来你会觉得"就这?"。我想讲的是这个决策是怎么做出来的:SDK 到底替你做了什么,哪些是你真需要的,哪些钱不该花。这个账算清楚了,你会发现"要不要用 agent 框架"在你自己的场景下也就有答案了。

## SDK 替你做了什么

我没有翻两页文档就下结论。Python 版 SDK 的源码我通读了一遍,先说公道话:代码写得不错。单读者多路分发、请求响应配对(request_id 加事件加结果表,Java 人看了会心一笑,Netty 配 CompletableFuture 就是同款)、流式全程无囤积、关闭语义把生产者和消费者拆开处理。看得出是正经工程师写的正经东西。

它给你的能力也是实打实的:上下文管理和自动压缩、工具执行(文件、bash、MCP 全套)、权限回调、hooks、session 的持久化和恢复、subagent 编排、错误重试。你写十几行 Python,后面这一整套就都有了。

但读源码的时候有一个事实让我停下来了:**这个 SDK 不是一个库,是一个进程包装器。**

它的本质是包了一层 claude CLI,每个 session spawn 一个子进程,通过 stdin/stdout 上的 JSON 行协议双向通信。Python 侧做的事情是协议路由、消息解析、回调分发。真正的 agent 运行时(上面列的那一整套能力)全部活在那个子进程里。

这个架构对它的出身来说完全合理,它就是从 Claude Code 这个开发者工具里长出来的,单用户、单会话、跑在开发者自己的机器上。但放到我的场景里,高并发多租户意味着进程数随会话数线性增长。每个子进程的内存、冷启动时间、生命周期管理(挂了谁拉起来,泄漏了谁回收),全都要自己兜。这些问题不是不能解,但解它们的工作量,比我要省掉的那个循环大一个量级。

有人读过源码可能会说,Transport 是抽象的,官方留了扩展缝,可以自己注入实现。对,但注入自定义 transport 消除不了那个 CLI 进程,只是把它挪到另一台机器上。agent 运行时就是那个进程本身,每 session 一个的模型没有变,变的只是它跑在哪。

你可能还会说,这本来就不是 SDK 的目标场景,你评估它干嘛?没错,这正是评估得出的结论之一。但官方把它作为构建生产 agent 的推荐路径来推,那"它的形状适合哪种生产"就值得有人认真读完源码之后说清楚,而不是靠感觉。

## 真正难的部分,框架帮不了

放弃 SDK 之后,我面对的问题是:自己写,到底要写多少东西?

把 agent loop 拆开看,循环本身是这样的:调一次模型 API,返回里带 tool_use 就执行工具,把结果塞回消息列表,再调一次,直到模型不再要工具。就这么多。任何一个写过生产代码的人半天写完。

难的部分在别处,而且我发现这三样东西,用不用框架都得自己做:

**工具设计。**我们有二十多个工具,怎么切分粒度、描述怎么写模型才不会用错、返回结果给多少细节,这些决定了 agent 的实际表现。这是领域知识,SDK 不可能替你懂你的业务。

**上下文工程。**什么信息进 window,什么时候裁,裁掉哪些,出错的工具结果要不要留着给模型看。SDK 有自动压缩,但压缩策略是为编码会话调的,不是为你的业务会话调的。

**错误恢复。**工具执行失败,是重试,是把错误包给模型让它自己换路,还是直接终止本轮?限流了退避多久?这些策略和你的 SLA、你的成本预算绑死。

【这里最好各举一个你踩过的真实例子,一两句就够,是全文最不可伪造的部分】

我以前学物理的,对这种局面有个熟悉的感觉:换坐标系不改变物理。框架就是一套坐标系,它能让某些项看起来简单,但系统的总复杂度是守恒的,消掉的那些项只是被搬到了你看不见的地方。生产环境里,看不见的复杂度有个别名,叫事故。【类比候选,不喜欢就换】

所以账变成了:难的三样横竖自己做,框架能替我做的只剩那个循环。为了一个半天能写完的循环,引入一个每 session 一个子进程的运行时,这笔交易不成立。

## 那为什么不做个 Python 子系统

写到这肯定有人想说:你的问题不就是 Java 栈用不了它吗,把 agent 拆成独立的 Python 服务不就完了,微服务时代跨语言算什么硬伤。

这个方案我认真考虑过,账是这么算的。

首先,子进程模型的问题跟语言没关系。拆成 Python 服务,SDK 在那边还是每 session 起一个 CLI 子进程,高并发下的进程管理问题原样存在,只是从我的 Java 服务里挪到了那个 Python 服务里,还是我兜。

其次,多一个服务不是白多的。部署、监控、告警、值班,一样不少。我们团队【按真实规模改】不到十个人,后端就我,引入第二套技术栈意味着这个服务的 bus factor 是 1,而且这个 1 还是个主业在 Java 那边的 1。

最关键的是切分方向。agent loop 需要跟什么贴身?跟工具实现、跟沙箱编排、跟业务逻辑、跟权限。这些全在 Java 侧。把整个系统里最薄的一层(200 行循环)单独切出去,让它跟最厚的部分隔一层网络,session 状态还要跨服务管理。这个切法方向反了。

所以结论不是"Python 不行",是这笔账算下来,为了省 200 行代码,开一个跨语言子系统,收益盖不住成本。

## 200 行长什么样

【以下是结构示意,发布前必须换成真实代码,并按真实代码调整讲解】

```java
List<Message> messages = contextBuilder.initial(session);

for (int turn = 0; turn < maxTurns; turn++) {
    // 重试策略在这一层:429/5xx 指数退避,4xx 直接失败
    ModelResponse resp = modelClient.call(messages, toolRegistry.specs());
    messages.add(resp.asAssistantMessage());

    if (resp.stopReason() != StopReason.TOOL_USE) {
        return resp;
    }

    for (ToolUse call : resp.toolUses()) {
        // 工具失败不抛异常:包成带 error 标记的 result 回灌,
        // 让模型自己决定重试还是换路
        ToolResult result = toolRegistry.execute(session, call);
        messages.add(result.asUserMessage());
    }

    // 上下文裁剪:超过阈值时按策略压缩早期轮次
    contextManager.trim(messages);
}
```

对,就这。你可能觉得"就这?",这正是我想说的:循环本身就这么点东西。前面说的三样难的,你在代码里也能看见它们在哪:重试策略在 API 调用那一层,错误恢复策略在工具执行的包装里,上下文策略在 trim 背后。这几个地方每一个都比循环本身的代码多,也都跟我们的业务绑死。它们不会因为我用了 SDK 就消失,只会变成我跟 SDK 的抽象打架的地方。

## 什么时候你该反过来选 SDK

说了这么多不用的理由,得说清楚这个决策的边界在哪,不然就成抬杠了。

你在做开发者工具或者内部工具,单用户单会话,每个用户桌面上跑一个进程完全没问题:用 SDK,别自己写。你需要的就是 Claude Code 那套完整能力,文件编辑、bash、subagent 编排、权限系统,而不是自己的一套业务工具:用 SDK,自己重造这些是发疯。你在做原型,下周要 demo:用 SDK。你的团队本来就是 TS 或 Python 栈,或者本来就打算为 agent 建独立服务:那前面那笔边界成本对你根本不存在,账要重算。

我的结论只对我的前提成立:高并发多租户、agent 必须跟业务逻辑贴身、团队没有余量养第二套栈。前提变了,结论跟着变。

如果这篇文章有什么可以带走的,不是"别用框架",而是一个问题的问法。评估任何 agent 框架的时候别问"它功能全不全",问两件事:**它替我做的事情里,哪件是我自己做不了或不想做的?它的运行模型,跟我的部署形状合不合?**第二个问题几乎没人问,但我这次评估里,决定性的就是它。
